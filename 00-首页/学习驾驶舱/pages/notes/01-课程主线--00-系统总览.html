2. 四类概念不要混在一起

I2C / Platform 不是 Camera 功能
V4L2 / Media Controller 也不是物理传输协议
CSI-2 / D-PHY 不是驱动类型

3. Linux 驱动模型：谁负责找到设备

Linux 不会根据驱动文件名猜它是什么类型，而是看驱动注册到哪一种总线框架：

struct platform_driver   // SoC 内部固定控制器
struct i2c_driver        // I2C 外设
struct spi_driver        // SPI 外设
struct usb_driver        // USB 外设
当前 Camera 中的对应关系
RK3568 D-PHY 控制器
    → platform_device
    → platform_driver

IMX415 Sensor
    → i2c_client
    → i2c_driver

所以：

Platform Driver 通常负责 SoC 内部固定硬件控制器；挂在控制器总线上的具体外设，再使用 I2C、SPI、USB 等对应的驱动模型。

4. DTS 是设备档案，不是驱动实现

DTS 主要描述：

板子上有什么设备
设备地址在哪里
需要什么寄存器、时钟、GPIO、电源域
设备之间如何连接

例如 D-PHY：

csi2_dphy0: csi2-dphy0 {
    compatible = "rockchip,rk3568-csi2-dphy";
    rockchip,hw = <&csi2_dphy_hw>;
};

这里的 compatible 负责提供匹配标识：

DTS 节点
    ↓
Platform Device
    ↓
compatible 与驱动 match 表比较
    ↓
匹配成功
    ↓
probe()

DTS 不会直接把节点标成“V4L2 设备”或“Camera Sensor”。这些身份由驱动代码决定：驱动在 probe() 中调用 V4L2 和 Media Controller 接口，才把硬件接入 Camera 框架。

5. Linux 框架与厂商驱动的关系

Linux 提供规则和通用接口：

Device Model
Platform Driver Framework
I2C Driver Framework
V4L2
Media Controller
Async Framework

厂商或社区驱动负责真正理解硬件：

IMX415 Driver       → 读取 Sensor ID、写寄存器、设置曝光和开流
RK3568 D-PHY Driver → 配置 D-PHY 寄存器、管理 Lane 和数据接收
RK3568 ISP Driver   → 处理 RAW 图像并输出视频节点

驱动通过 Linux 提供的接口接入框架，例如：

v4l2_subdev_init()
media_entity_pads_init()
v4l2_async_register_subdev()
media_create_pad_link()

一句话：

Linux 定义统一规则，厂商驱动填写具体硬件行为。

6. 一个模块有两个身份

IMX415

从 Linux 设备模型看：

IMX415
    → I2C Device
    → I2C Driver

从 Camera 框架看：

IMX415
    → V4L2 Sensor Subdev
    → /dev/v4l-subdev3
D-PHY

从 Linux 设备模型看：

D-PHY
    → Platform Device
    → Platform Driver

从 Camera 框架看：

D-PHY
    → V4L2 Subdev
    → Media Entity
    → Sink / Source Pad

因此：

I2C / Platform
    解决“Linux 怎么找到和管理设备”

V4L2 / Media Controller
    解决“Camera 模块怎样统一表示和连接”

7. V4L2 与 V4L2 Subdev

V4L2 是 Video4Linux2，属于 Linux 内核中的 Video / Camera 功能框架，不是 Rockchip 私有库，也不是用户态第三方库。

Linux Kernel
    ↓
V4L2 Framework
    ↓
统一管理 Camera 和 Video 设备

Camera 流水线不是单一设备：

Sensor → D-PHY → CSI → ISP

因此这些内部模块通常表示为 V4L2 Subdev：

IMX415                  → /dev/v4l-subdev3
rockchip-csi2-dphy0     → /dev/v4l-subdev2
rkisp-csi-subdev        → /dev/v4l-subdev1
rkisp-isp-subdev        → /dev/v4l-subdev0

Subdev 主要负责：

支持哪些格式和分辨率
有什么输入 / 输出端口
怎样设置曝光、增益和时序
怎样设置格式
怎样开流和停流

它不是主要给应用直接取 Frame Buffer 的节点；最终给用户态取图的是 /dev/video0。

8. Media Controller：把模块连成图

V4L2 Subdev 能描述一个个模块，但还需要描述模块之间的连接，这由 Media Controller 完成。

核心对象只有三个：

Entity = 一个 Camera 模块
Pad    = 模块的输入 / 输出端口
Link   = 两个 Pad 之间的连接

当前链路可以理解为：

IMX415
  pad0: Source
       ↓
rockchip-csi2-dphy0
  pad0: Sink
  pad1: Source
       ↓
rkisp-csi-subdev
       ↓
rkisp-isp-subdev
       ↓
rkisp_mainpath
       ↓
/dev/video0
media-ctl -p

看到的就是 Media Controller 在运行时维护的 Entity / Pad / Link 拓扑。

9. DTS endpoint 与 Media Graph 的区别

DTS 中的：

remote-endpoint = <&imx415_out>;

只是静态连接描述，表达：

这两个硬件端点应该连接。

运行时还要经过驱动和异步框架：

DTS endpoint
    ↓
Driver probe()
    ↓
V4L2 Subdev 注册
    ↓
Media Entity / Pad 初始化
    ↓
Async match
    ↓
.bound()
    ↓
media_create_pad_link()
    ↓
运行时 Media Graph

所以不能把 remote-endpoint 理解成“DTS 编译时已经创建了 Media Link”。

10. D-PHY 的两个对象：HW 与逻辑 D-PHY

RK3568 D-PHY 驱动拆成两个容易混淆的对象：

csi2_dphy_hw

表示底层真实硬件资源：

寄存器
Clock
GRF
stream_on / stream_off
csi2_dphy0

表示 Camera 链路中的逻辑 D-PHY：

Platform Device
V4L2 Subdev
Media Entity
Sink / Source Pad
Sensor 异步绑定关系

两者通过 DTS 关联：

rockchip,hw = <&csi2_dphy_hw>;

驱动中的关系大致是：

of_parse_phandle()
    ↓
of_find_device_by_node()
    ↓
platform_get_drvdata()
    ↓
dphy->dphy_hw

也就是：DTS 中的静态 phandle，最终变成 C 结构体之间的指针关系。

11. IMX415 与 D-PHY 的共同驱动模板

虽然两者的底层总线不同：

IMX415 → I2C Driver
D-PHY  → Platform Driver

但进入 Camera 框架后的套路相近：

Driver Match
    ↓
probe()
    ↓
初始化时钟、GPIO、寄存器等硬件资源
    ↓
初始化 V4L2 Subdev
    ↓
初始化 Media Entity / Pad
    ↓
注册 Async
    ↓
匹配上下游
    ↓
创建 Media Link

真正的差别在于：

各自初始化什么硬件
各自提供几个 Pad
各自有哪些 ops
如何与上下游绑定

12. 当前最值得记住的面试表达

RK3568 Camera 需要分三层理解。第一层是 Linux 设备模型：IMX415 挂在 I2C 总线上，D-PHY、CSI 和 ISP 这类 SoC 内部控制器通常由 Platform Driver 管理。第二层是 Camera 功能框架：Sensor、D-PHY、CSI、ISP 都可以表示为 V4L2 Subdev。第三层是 Media Controller：通过 Entity、Pad 和 Link 把这些 Subdev 组织成完整的 Camera Pipeline。DTS 只描述设备资源和静态连接，驱动在 probe 中初始化硬件、注册 Subdev，异步框架匹配上下游后，再由 .bound() 调用 media_create_pad_link() 建立运行时链路，最后通过 /dev/video0 给用户态取帧。

实板验证

当前证据包括运行时 I2C client、IMX415 Sensor ID、Media Graph 和抓帧结果。它们分别证明链路的不同层次，任何单项都不能替代完整开流验证。

常见故障

先按供电/时钟/复位、I2C 匹配与 ID、endpoint 与异步绑定、D-PHY/CSI、RKISP、video node 分层定位，不从 /dev/video0 缺失直接跳到某个驱动函数。

面试表达

RK3568 Camera 不是单个驱动，而是由 Sensor、MIPI 接收、ISP 和 V4L2/Media 框架组成的 pipeline；DTS 描述设备和连接，驱动模型完成匹配与 probe，运行时 Media Graph 表达数据链。
