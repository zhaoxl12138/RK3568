# Media Graph 生命周期：Async 怎样让独立 probe 的对象相遇

> [[02-源码陪读/06-Media-Controller/00-源码陪读索引|返回源码陪读索引]]

## 本篇先解决什么问题

不同驱动的 `probe()` 不是一条函数直接调用链。IMX415、D-PHY、RKISP 都可能由不同的总线和初始化时机触发，因此它们可能“各自先完成自己的 probe”，之后再由 V4L2 Async 框架按照 endpoint 和 notifier 条件把真实 `struct v4l2_subdev` 找到一起。

这里的“异步”不是创建一个线程，也不是简单地 sleep 等待。它更像一个登记表：

```text
notifier：我正在等待一个满足条件的 subdev
subdev：我已经注册，但暂时还没有找到等待我的 notifier
Async Core：两边都出现后尝试 match
match 成功：调用 .bound()
全部依赖满足：调用 .complete()
```

所以本篇先看**对象什么时候登记、进入哪条链表、谁触发匹配回调**，再看 `.bound()` 和 `.complete()` 做了什么。不要把“调用 notifier 注册函数”和“已经完成 Media 建链”当成同一个动作。

本篇先固定三个源码坐标，避免只搜到同名符号：

- Async Core：`drivers/media/v4l2-core/v4l2-async.c`
- D-PHY notifier 的创建与 `.bound()`：`drivers/phy/rockchip/phy-rockchip-csi2-dphy.c`
- RKISP 根 notifier 的 `.bound/.complete`：`drivers/media/platform/rockchip/isp/dev.c`

Source Insight 应先在 Project Files 中打开这些精确文件，再搜索下面的函数；不要全工程搜索 `.bound` 或 `notifier` 后从几百个结果中猜。

## 先建立五个容器的类型意识

| 容器 | 在哪里 | 元素类型 | 含义 |
|---|---|---|---|
| `notifier->subdevs[]` | 每个 notifier | `struct v4l2_async_subdev *` | 驱动配置出的全部匹配描述符数组 |
| `notifier->waiting` | 每个 notifier | `struct v4l2_async_subdev` | 还没找到真实设备的匹配条件 |
| `notifier->done` | 每个 notifier | `struct v4l2_subdev` | 已 probe、已匹配、已 bound 的真实 subdev |
| `notifier_list` | Async Core 全局 | `struct v4l2_async_notifier` | 已登记、可被后到 subdev 扫描的 notifier |
| `subdev_list` | Async Core 全局 | `struct v4l2_subdev` | 已登记但尚未命中 notifier 的真实 subdev |

最容易错的点：`waiting` 里不是 Sensor 实例，而是 `asd` 匹配条件；`done` 里才是真实 `sd`。匹配时不是把同一种节点从 waiting 移到 done，而是**删除 asd 的 waiting 节点，同时把 sd 的 async_list 链入 done**。若 sd 先到，它原来在全局 `subdev_list`；若 notifier 先到，sd 的链表节点此前只是初始化后的空节点。

## 路径 A：notifier 先注册，Sensor 后注册

以 D-PHY 等待 IMX415 为例：

```text
D-PHY probe                                         [Platform 框架回调]
 └─ rockchip_csi2dphy_media_init()                  [直接调用]
    ├─ parse_fwnode_endpoints_by_port(...)          [直接调用]
    │   └─ 生成 asd：match_type=FWNODE，保存远端 Sensor fwnode
    ├─ notifier.ops = &rockchip_csi2_dphy_async_ops [对象关联]
    │   └─ .bound = rockchip_..._notifier_bound     [函数指针赋值]
    └─ v4l2_async_subdev_notifier_register(...)     [直接调用]
        └─ __v4l2_async_notifier_register()
           ├─ asd 加入 notifier->waiting
           ├─ 扫描 subdev_list：此时可能没有 IMX415
           └─ notifier 加入 notifier_list

稍后 IMX415 probe
 └─ v4l2_async_register_subdev_sensor_common(sd)    [直接调用 helper]
    └─ v4l2_async_register_subdev(sd)
       ├─ 扫描 notifier_list
       ├─ v4l2_async_find_match(): fwnode 相等
       └─ v4l2_async_match_notify()
          ├─ v4l2_device_register_subdev(...)
          ├─ ops->bound(...)                        [框架回调]
          ├─ asd 从 waiting 删除
          └─ sd 的空 async_list 节点链入 done
```

`v4l2_async_register_subdev_sensor_common()` 返回不等于“Sensor 已 bound”。若当时没有匹配 notifier，`v4l2_async_register_subdev()` 会把 `sd->async_list` 加到 `subdev_list`，仍然成功返回，等待未来事件。

## 路径 B：Sensor 先注册，notifier 后注册

```text
IMX415 先 probe
 └─ v4l2_async_register_subdev(sd)
    ├─ 扫 notifier_list：没有 D-PHY notifier
    └─ sd 加入 subdev_list

稍后 D-PHY notifier 注册
 └─ __v4l2_async_notifier_register()
    ├─ asd 加入 waiting
    ├─ v4l2_async_notifier_try_all_subdevs()
    │   └─ 扫 subdev_list 找到 IMX415
    └─ v4l2_async_match_notify()：bound + waiting/done 迁移
```

所以“谁先注册都能匹配”不是口号，而是两个对称扫描：

`subdev` 是已经注册到 V4L2 框架中的真实子设备对象；`notifier` 是某个驱动向 Async Core 登记的等待条件和回调表。两者无论谁先注册，Async Core 都会扫描另一方的登记表，匹配成功后再调用 `.bound()`

- subdev 后到：`v4l2_async_register_subdev()` 扫 `notifier_list`；
- notifier 后到：`__v4l2_async_notifier_register()` 经 `try_all_subdevs()` 扫 `subdev_list`。

它是事件驱动的集合配对，不是某个 probe 线程睡眠等待另一个 probe。

## 本轮回答与批改：D-PHY 为什么同时有 notifier 和 sd

### 问题 1：D-PHY 为什么既有 notifier，又有 sd？

**我的回答：** 因为 D-PHY 既要去匹配 IMX415 Sensor，又要给注册接口去匹配 ISP，处于中间层。

<mark>正确答案：主线正确。D-PHY 的 notifier 面向上游，用来等待 IMX415 subdev；D-PHY 的 sd 是 D-PHY 自己的真实 V4L2 subdev，注册后可被下游 RKISP notifier 匹配。更准确地说，不是 sd 作为“注册接口”去主动匹配 ISP，而是 RKISP notifier 等待并匹配已注册的 csi2_dphy.sd。</mark>

```text
上游：csi2_dphy.notifier ↔ imx415.subdev

下游：rkisp_device.notifier ↔ csi2_dphy.sd
```

### 问题 2：port = 0 在本次 endpoint 解析中表示什么？

**我的回答：** 只解析 D-PHY 的 port@0，输入端口。

<mark>正确答案：正确。D-PHY 的 port@0 是接收 Sensor 的输入侧，解析它的 endpoint 可以找到远端 IMX415 endpoint，并生成等待这个 Sensor 的 Async 匹配条件。</mark>

### 问题 3：v4l2_async_subdev_notifier_register() 返回 0，能证明 IMX415 → D-PHY link 已创建吗？

**我的回答：** 不能，只是匹配成功，并没有 link。

<mark>正确答案：不能据此断言 link 已创建，但原因要补全：返回 0 只保证 notifier 注册流程没有报错。若 IMX415 尚未注册，D-PHY 只是进入等待，当然还没有 link；若 IMX415 已经在 subdev_list，注册函数内部就可能马上匹配并触发 .bound()，此时 link 可能已经创建。最终必须通过 .bound() 路径或 media-ctl -p 中的 [ENABLED] link 验证。</mark>

## match_notify：匹配成功后到底做了什么

按源码顺序读 `v4l2_async_match_notify()`：

1. `v4l2_device_register_subdev(v4l2_dev, sd)`：把真实 subdev 接到根 `v4l2_device`；在 Media Controller 配置下，这会让其内嵌 entity 接入同一 `media_device`。这是**直接调用**。
2. `v4l2_async_notifier_call_bound(...)`：进入包装函数，再执行 `n->ops->bound(...)`。后者是经函数指针发生的**框架回调**。
3. `list_del(&asd->list)`：匹配条件不再 waiting。
4. `sd->asd = asd; sd->notifier = notifier`：保存对象关联，供 unbind 和调试使用。
5. `list_move(&sd->async_list, &notifier->done)`：真实 subdev 进入该 notifier 的已绑定集合。若 sd 先注册，节点从 `subdev_list` 移来；若 notifier 先注册，节点此前只是空链表节点。
6. 若该 subdev 自己还带子 notifier，则设置 `subdev_notifier->parent = notifier` 并继续匹配子树。

`.bound` 失败时不会继续迁移列表：框架先注销刚注册的 subdev 并返回错误。因此 `done` 表示 `.bound` 已成功，不只是 fwnode 比较相等。

## 本轮回答与批改：`match_notify()` 完成了什么

### 问题 1：为什么 Async Core 不直接调用 `media_create_pad_link()`？

**我的回答：** 只负责匹配对象，不负责 link。

<mark>正确答案：正确。Async Core 是通用框架，只知道 notifier、真实 subdev 和匹配条件，不知道具体硬件的 pad 编号、输入输出方向或应建立哪一条 Camera link。匹配成功后，它只能回调驱动自己的 `.bound()`；D-PHY 驱动在 `.bound()` 中根据自己的硬件语义调用 `media_create_pad_link()`。</mark>

### 问题 2：`.bound()` 返回成功后，`waiting` 和 `done` 分别存什么？

**我的回答：** waiting 存 0，done 存 1。

<mark>正确答案：不是 0/1 状态位，而是两个链表。`waiting` 保存尚未匹配到真实设备的 `struct v4l2_async_subdev`，也就是“我要等谁”的匹配条件；`done` 保存已经匹配并且 `.bound()` 成功的真实 `struct v4l2_subdev`，例如 IMX415 subdev。匹配后，`asd` 从 `waiting` 删除，`sd` 的 `async_list` 链入 `done`。</mark>

### 问题 3：`v4l2_device_register_subdev()` 成功，能否说明 IMX415 → D-PHY link 已建立？

**我的回答：** 不能。

<mark>正确答案：正确。`v4l2_device_register_subdev()` 只把真实 subdev 接到根 `v4l2_device`；之后还必须成功执行 notifier 的 `.bound()`。对 D-PHY 而言，只有 `.bound()` 内的 `media_create_pad_link()` 成功，才有 IMX415 → D-PHY 的 Media link。</mark>

## `.bound` 与 `.complete` 不是同一个时机

| 回调          | 触发条件                                           |                 次数 | 当前板上典型职责                                                                                        |
| ----------- | ---------------------------------------------- | -----------------: | ----------------------------------------------------------------------------------------------- |
| `.bound`    | 某个 `asd` 与某个真实 `sd` 匹配，且 subdev 注册成功           |    每个命中的 subdev 一次 | D-PHY 保存 Sensor/lane/mbus，并直接调用 `media_create_pad_link()` 建 Sensor→D-PHY link；RKISP 保存上游 subdev |
| `.complete` | 根 notifier 整棵树的 `waiting` 都为空，且根 `v4l2_dev` 可用 | 根 notifier 达成完成条件时 | RKISP 直接调用 `rkisp_create_links()`、注册 subdev nodes、更新 active sensor、设置默认格式                       |

`v4l2_async_notifier_try_complete()` 先检查当前 waiting，再沿 `parent` 找根，递归检查子 notifier。只有最后才调用 `v4l2_async_notifier_call_complete()`，由包装函数通过 `ops->complete` 形成框架回调。D-PHY 的 ops 表在本驱动中只有 `.bound/.unbind`，没有 `.complete`；RKISP 根 notifier 才提供 `.complete`。

## 本轮回答与批改：`.bound()` 和 `.complete()` 的职责

### 问题 1：`.bound()` 是整条 Camera 链路只执行一次，还是每匹配到一个 subdev 都可能执行一次？

**我的回答：** 每匹配到一个 subdev 都可能执行一次。

<mark>正确答案：正确。`.bound()` 是“某一对 notifier + subdev 匹配成功”的回调，不是整条 Camera 管线的总完成回调。D-PHY 匹配到 IMX415 时会执行一次 D-PHY 的 `.bound()`；RKISP 再匹配到 D-PHY subdev 时，会执行 RKISP notifier 自己的 `.bound()`。</mark>

### 问题 2：已有 IMX415 → D-PHY link，但 RKISP 还没完成匹配，此时能否证明 `/dev/video0` 可以出帧？

**我的回答：** 不能。

<mark>正确答案：正确。此时最多证明上游第一段 Media link 已建立；还缺 D-PHY → CSI → ISP → mainpath/video node 的对象、链路、格式、开流和 DMA 条件。`/dev/video0` 是否出现或能否出帧，必须看 RKISP 根 notifier 的完成、Media Graph、`STREAMON` 和实际帧证据。</mark>

### 问题 3：为什么 D-PHY 驱动通常只需要 `.bound()`，而 RKISP 根 notifier 还需要 `.complete()`？

**我的回答：** 不知道。

<mark>正确答案：D-PHY 是中间节点，它只需在自己的上游 Sensor 到位时建立局部的 Sensor → D-PHY link，并把自己作为下游可匹配的 subdev 继续交接。RKISP 是这条 Camera 管线的根管理者：只有它确认整棵 Async 依赖树都就绪后，才能统一建立剩余 links、注册 video nodes、确定 active sensor 和默认格式。因此 D-PHY 用 `.bound()` 做“局部接线”，RKISP 用 `.complete()` 做“整条管线收口”。</mark>

## 本轮回答与批改：D-PHY `.bound()` 怎样建立一条 link

源码入口：`drivers/phy/rockchip/phy-rockchip-csi2-dphy.c` → `rockchip_csi2_dphy_notifier_bound()`。

### 问题 1：为什么保存 `sensor->sd`、`sensor->lanes`、`sensor->mbus`？

**我的回答：** 上下联通。为后续开流做准备。

<mark>正确答案：方向正确，但要具体。`sensor->sd` 保存“当前 D-PHY 的远端是哪一个真实 Sensor”，以后可通过它取得 link frequency、调用 Sensor 的 subdev ops；`lanes` 保存 CSI-2 使用几条 Lane；`mbus` 保存总线类型和标志。D-PHY 后续要依据这些信息配置自身物理接收器、查询/更新总线配置，而不只是抽象地“上下联通”。</mark>

### 问题 2：为什么遍历所有 Sensor pad 找 `MEDIA_PAD_FL_SOURCE`，不直接写 `pad0`？

**我的回答：** 不清楚，难道是防止错误么？

<mark>正确答案：是为了让 D-PHY 驱动不绑定某一款 Sensor 的 pad 编号。IMX415 当前确实只有 `pad0`，但 D-PHY 是通用接收驱动，其他 Sensor 或桥接器可能有多个 pad，Source pad 不一定编号为 0。按 `MEDIA_PAD_FL_SOURCE` 查找既确认数据方向，也能在上游实体没有正确声明输出端时及时报错。</mark>

### 问题 3：多个 Sensor 时，为什么不能默认把所有 Link 都设为 `ENABLED`？

**我的回答：** 不清楚。

<mark>正确答案：一个 D-PHY Sink 在同一时刻只能选择一条上游图像来源。若多条 Sensor → 同一 Sink link 同时启用，管线不知道应接收谁的数据，实际硬件/路由也可能冲突。这个驱动把第一个匹配到的 Sensor link 作为默认 Enabled，其余 link 先创建但 Disabled，后续由配置选择要使用的输入。</mark>

## 本轮回答与批改：DTS endpoint 与运行时 Media Link

### 问题 1：`media_create_pad_link()` 创建的是 MIPI 物理连线，还是 Linux 中的 Media Graph 软件 link？

**我的回答：** 是 Linux 中的 Media Graph 软件 link。

<mark>正确答案：正确。它创建的是内核对象之间的运行时拓扑关系，供 Media Controller 查询、格式协商和路由管理使用；不会焊接线路、不会改变板上的 MIPI 差分线，也不等于 RAW 数据已经在传输。</mark>

### 问题 2：这条 Link 已 `ENABLED`，能否证明 Sensor 已经输出 RAW 数据？

**我的回答：** 不能。

<mark>正确答案：正确。`[ENABLED]` 只证明软件 Media Graph 选择了这条路径。还需要 Sensor 成功上电、配置寄存器、开始 stream、D-PHY 锁定信号、CSI/ISP/DMA 正常，才能证明 RAW 数据真的到达。</mark>

### 问题 3：DTS 的 `remote-endpoint` 和 `media_create_pad_link()`，分别负责什么？

**我的回答：** 发现上下端口，建立数据输入输出口。

<mark>正确答案：前半句接近，但三个动作必须分开。`remote-endpoint` 在 DTS 中声明“我的硬件对端是谁”，供 fwnode 解析和 Async 匹配发现远端 subdev；`media_entity_pads_init()` 先创建每个 entity 的 Source/Sink 软件端口；匹配成功后，`media_create_pad_link()` 才把两个已经存在的 pad 建成运行时 Media Graph link。它不创建 pad，也不直接让数据流动。</mark>

## 本轮回答与批改：Entity、Pad、Video Node 的边界

### 问题 1：为什么 D-PHY 需要两个 pad，而 IMX415 通常只有一个 pad？

**我的回答：** D-PHY 需要从 415 拿数据并传输给 ISP，所以需要两个。

<mark>正确答案：正确。D-PHY 的 `pad0` 是 Sink，接收 IMX415 的 RAW 数据；`pad1` 是 Source，把接收到的数据继续输出给下游 CSI/RKISP。IMX415 是链路起点，通常没有上游图像输入，因此只需要一个 Source pad。</mark>

### 问题 2：`pad` 和 `/dev/video0` 都能叫“端口”吗？两者本质区别是什么？

**我的回答：** pad 是拓扑图中的端口。video0 是应用代码的调用接口。

<mark>正确答案：正确。pad 是内核 Media Graph 中 entity 的逻辑输入/输出端，不是文件、没有 buffer 队列，应用不能对它直接取帧；`/dev/video0` 是 V4L2 video node，应用通过 open/ioctl/REQBUFS/QBUF/STREAMON/DQBUF 从它获取图像 buffer。两者可能在图上有关联，但层次完全不同。</mark>

### 问题 3：`media-ctl -p` 显示某条 link `[ENABLED]`，对排障最准确能证明什么？

**我的回答：** 该通道物理连接没有问题。

<mark>正确答案：不对。`[ENABLED]` 只能证明 Linux Media Graph 中该 Source pad → Sink pad 的软件 link 已创建且被选中；不能证明线缆、Lane 极性、电源、时钟、Sensor 实际 RAW 输出或 D-PHY 锁定都正常。物理通道是否正常还要结合 dmesg、CSI 错误计数和实际抓帧验证。</mark>

## Sensor helper 与 D-PHY endpoint notifier 的职责边界

这两个名字都含 Async，但等待对象不同：

| 维度           | Sensor helper                                     | D-PHY endpoint notifier                                                                                        |
| ------------ | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 入口           | `v4l2_async_register_subdev_sensor_common(sd)`    | `v4l2_async_notifier_parse_fwnode_endpoints_by_port(..., 0, ...)` + `v4l2_async_subdev_notifier_register(...)` |
| 谁拥有 notifier | Sensor helper 为 Sensor 分配 `sd->subdev_notifier`   | `struct csi2_dphy` 内嵌 `notifier`                                                                               |
| 解析什么         | Sensor 节点的 `flash-leds`、`lens-focus`、`ir-cut` 等引用 | D-PHY `port@0` endpoint 与远端 Sensor endpoint                                                                    |
| 等待谁          | 镜头、闪光灯、IR-cut 等 Sensor 辅助 subdev                  | 图像源 Sensor subdev                                                                                              |
| 附加信息         | 通用 Sensor 辅助关系                                    | `sensor_async_subdev` 额外保存 `mbus` 和 `lanes`                                                                    |
| bound 后动作    | 由相应父子 notifier 关系管理辅助设备                           | D-PHY `.bound` 保存 `sensor->sd` 并创建 Sensor→D-PHY Media Link                                                     |
| 是否也注册自身      | 是，helper 最后调用 `v4l2_async_register_subdev(sd)`    | 是，D-PHY 初始化最后也调用 `v4l2_async_register_subdev(&dphy->sd)`                                                       |

白话：Sensor helper 像 Sensor 报到时顺便登记“我的镜头/闪光灯配件”；D-PHY endpoint notifier 像接收端登记“我的输入口应该等哪台 Sensor”。它们最终都使用 Async Core，但不是同一张等待清单，更不是同一个 Media Link 创建动作。

## 根图何时可查询

`struct media_device` 是图的聚合根；`struct v4l2_device` 通过 `mdev` 指针关联它。`media_device_init()` 初始化根图内部列表和锁；entity 注册、pad/link 创建逐步填充图；`media_device_register()` 让 media devnode 对用户态可见。具体 Rockchip 驱动中的先后要以 `rkisp_plat_probe()` 实码为准，不能用 API 文档的推荐顺序替代当前实现事实。

“可查询”仍不等于“可出帧”：Async complete 后只是对象到齐并完成驱动安排的建链/默认格式动作，STREAMON、runtime PM、Sensor 寄存器、CSI 中断和 DMA 属于后续阶段。

## 白话与证据边界

大白话：两个登记台都准备一本名单。谁先来就先在全局候车区等，后来的登记台或设备会主动扫描候车区。配上一对就执行 `.bound`，整棵预约树清空才执行根 `.complete`。

- `waiting` 为空能证明该 notifier 的条件已匹配；若存在子 notifier，还不能单凭局部为空断言根 `.complete` 已执行。
- `.bound` 日志能证明某一对已绑定；不能自动证明 `.complete` 已执行。
- `Async subdev notifier completed` 能证明 RKISP 完成回调已走到日志；不能证明 `_set_pipeline_default_fmt()` 之后 STREAMON 成功或已经有帧 DMA。

## 面试问题

为什么 Async 能容忍 Sensor 与 D-PHY probe 顺序不固定？

**我的回答：**

>

<mark>高亮正确答案：因为框架同时维护全局 notifier_list 和 subdev_list。subdev 后到就扫描 notifier_list；notifier 后到就把 asd 放入 waiting，再扫描 subdev_list。命中统一进入 match_notify，先回调 .bound，再删除 waiting 中的 asd，并把真实 sd 移入 done；整棵树 ready 后根 notifier 才回调 .complete。</mark>
