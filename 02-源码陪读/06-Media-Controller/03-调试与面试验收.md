# Media Controller 调试与面试验收

> [[02-源码陪读/06-Media-Controller/00-源码陪读索引|返回源码陪读索引]]

## 验收前先明确：Media Graph 能证明到哪一步

`media-ctl -p` 是观察 Media Controller 软件图的工具。它能帮助你确认 entity、pad、link、格式和 `[ENABLED]` 状态，但它不是示波器，也不是帧计数器。

```text
看到 Sensor entity       → 说明 Sensor subdev 已注册
看到 D-PHY entity        → 说明 D-PHY subdev 已注册
看到 [ENABLED] link      → 说明软件连接已建立并启用
看到 RAW 格式             → 说明当前 pad 的媒体总线格式记录如此
```

它还不能单独证明：

```text
Sensor 一定在输出时钟和数据
MIPI 差分信号质量一定合格
ISP 一定收到有效帧
DMA 一定完成
/dev/video0 一定能 DQBUF
```

因此本篇的排查方法是：先用 Media Graph 证明“软件拓扑”，再把证据交给第 07 阶段验证 ISP，最后由第 08 阶段验证用户态是否真的拿到帧。

## 大白话：Source Insight 实操，从对象定义走到板端 link

每一步都写下“代码类型、读什么、改什么、证据是什么”，不要只记函数名。

## 一行代码四问法

遇到“看起来都像注册”的代码，用这四问拆开：

1. **此刻执行了吗？** `.bound = fn` 没执行 `fn`；`ops->bound(...)` 才执行。
2. **改了什么？** 是指针/flags/链表/计数，还是硬件寄存器？
3. **谁拥有对象？** 内嵌成员、外部数组指针、链表成员分别由谁释放？
4. **下一步谁触发？** 当前函数直接调用、总线回调、Async 匹配回调，还是用户态 ioctl？

示例：

| 代码 | 类型 | 此刻状态变化 | 没发生什么 |
|---|---|---|---|
| `imx415->subdev.ops = ops`（由初始化函数完成） | 对象关联/函数表指针赋值 | subdev 记住 ops 表地址 | 没执行 `.s_stream` |
| `.bound = rockchip_csi2_dphy_notifier_bound` | 函数指针赋值 | notifier ops 表保存入口地址 | 没保存 Sensor，也没建 link |
| `media_entity_pads_init(...)` | 直接调用 | entity↔pads、index、可能的 graph object | 没匹配远端 |
| `v4l2_async_register_subdev(sd)` | 直接调用 | 扫描现有 notifier，或把 sd 放进 `subdev_list` | 成功返回也不保证已经 bound |
| `n->ops->bound(...)` | 框架回调 | 进入具体驱动 bound；成功后框架迁移列表 | 不等于整棵 notifier complete |
| `media_create_pad_link(...)` | 直接调用 | 创建 link/backlink/reverse 与计数 | 不启动数据流 |

## 板端命令与每条证据的上限

```bash
dmesg | grep -E "dphy[0-9]+ matches|Async registered subdev|Async subdev notifier completed"
media-ctl -p
media-ctl -e "m00_b_imx415 4-001a-1"
v4l2-ctl --list-devices
v4l2-ctl -d /dev/video0 --all
```

| 证据 | 能证明 | 不能证明 |
|---|---|---|
| `dphy0 matches ...` | D-PHY `.bound` 至少走到该日志，Sensor 对象与 lane/mbus 已被读取 | `media_create_pad_link()` 后续一定成功；需结合返回/拓扑 |
| `Async registered subdev` | RKISP `.bound` 接纳了一个上游 subdev | 根 `.complete` 已经执行 |
| `Async subdev notifier completed` | RKISP 根 `.complete` 走过建链、subdev node、sensor info、默认格式主路径并到达日志 | STREAMON、MIPI、帧中断、DMA 正常 |
| `media-ctl -p` 有 entity | entity 已进入可查询 Media Graph | 其所有 pads/links 都正确 |
| 有 Source/Sink pad | pad 初始化和方向字段可查询 | 对端 link 必然存在 |
| 有 link `[ENABLED]` | 软件图有一条启用边 | 数据已通过该边 |
| pad 显示 `SGBRG10_1X10` | 当前 subdev pad 总线格式 | `/dev/video0` 内存格式是 NV12，更不证明 Bayer 顺序实测正确 |
| `v4l2-ctl --all` 显示 NV12 | video node 当前内存格式 | Sensor 原始输出或 MIPI 电气质量 |
| `DQBUF` 连续成功 | 至少有 buffer 完成并交给用户态 | 长时间无丢帧或图像内容正确；还需计数与画面证据 |

## 按最早缺失证据定位

```text
没有 Sensor entity
 ├─ 查 IMX415 probe 是否到 v4l2_async_register_subdev_sensor_common
 └─ 注意 helper 成功也可能只是进入 subdev_list

有 Sensor entity，没有 Sensor→D-PHY link
 ├─ 查 D-PHY port@0 endpoint 是否生成正确 asd.match.fwnode
 ├─ 查 v4l2_async_find_match 是否命中
 ├─ 查 rockchip_csi2_dphy_notifier_bound 是否执行
 └─ 查 Sensor Source pad 与 media_create_pad_link 返回值

有 Sensor→D-PHY，没有 D-PHY→CSI/ISP/mainpath
 ├─ 查 RKISP notifier waiting 是否清空
 ├─ 查 subdev_notifier_complete 是否执行
 └─ 查 rkisp_create_links 返回值

图完整，STREAMON 失败
 ├─ 查 link validate、pad 格式一致性、pipeline start
 └─ 再查 runtime PM 与各 subdev .s_stream

STREAMON 成功，DQBUF 超时
 └─ 查 Sensor 输出、MIPI/CSI 错误、帧中断、ISP 状态和 DMA
```

故障树的原则是先找**最早缺失的可观测状态**。Media Graph 缺边时，不要先调曝光或应用层 GStreamer；图完整但没 buffer 时，也不要仅靠 `[ENABLED]` 宣布硬件链路正常。

## 当前板拓扑逐节点读法

### Sensor

```text
entity: m00_b_imx415 4-001a-1
type: V4L2 subdev Sensor
pad0: Source [fmt:SGBRG10_1X10/3864x2192]
  -> rockchip-csi2-dphy0:0 [ENABLED]
```

读法：Sensor 内嵌 entity 已注册；pad0 是相对 Sensor 的数据出口；D-PHY `.bound` 已有机会创建软件边。不能据此断言 `imx415_s_stream(1)` 已执行。

### D-PHY

```text
entity: rockchip-csi2-dphy0
pad0: Sink   <- IMX415:0 [ENABLED]
pad1: Source -> rkisp-csi-subdev:0 [ENABLED]
```

读法：D-PHY entity 有两个 pad，输入边和输出边都在图中；Source/Sink 是相对当前 entity 的数据方向。不能据此证明 lane 数、电气时序或 CRC/ECC 无错。

### ISP 与 mainpath

```text
rkisp-csi-subdev: Sink -> Source
rkisp-isp-subdev: Sink RAW10 -> Source YUYV mbus
rkisp_mainpath: Sink <- ISP Source
/dev/video0: capture node, memory FourCC separately queried
```

读法：`media-ctl` 展示图和 pad-level bus format；`v4l2-ctl` 展示 video node memory format。不要把 YUYV mbus 和 NV12 memory FourCC 当成同一字段。

## 本次验收记录：Media Controller 基础与证据边界

> 验收结论：**暂不通过**。已经能说出 D-PHY 的中间层角色和 Async 是软件流程；但仍把 Media Graph 的软件对象误当成实际数据通道，也没有说清 Async 四张表与“最早缺失证据”的排查顺序。先复核本节，再做一次短验收。

### 1. 请分别定义 `media_entity`、`media_pad`、`media_link`；再说明 RAW 像素实际由谁产生、经过什么硬件路径传输，以及这三个 Media Graph 软件对象在其中负责什么、明确不负责什么？

**我的回答：** 实例 输入输出端口 连接线 RAW 从 entity 产生，从 pad 口按 link 方式流动。

<mark>正确答案：前半句基本对：entity 是一个媒体模块的软件对象，pad 是该对象的逻辑输入/输出端，link 是两个 pad 的软件拓扑关系。但 RAW 不是由 entity 这个内核对象“产生”，也不是沿软件 link 被复制流动；RAW 由 IMX415 硬件产生，经物理 MIPI/片内硬件数据通路传输。Media Graph 只是内核对这条硬件管线的描述、配置和查询模型。</mark>

### 2. 对比 `media_entity_pads_init(&entity, num_pads, pads)` 与 `media_create_pad_link(source, source_pad, sink, sink_pad, flags)`：请分别说明它们的调用前提、源码中具体修改了哪些对象/字段或链表、各自产生的结果，以及各自明确没有完成哪些动作（方向设置、远端匹配、link 创建、开流、RAW/DMA 传输分别由谁负责）？

**我的回答：** 实例和端口初始化；连接实例之间的传输方向和连接状态。

<mark>正确答案：`media_entity_pads_init()` 让 entity 记住调用者准备的 pad 数组，并填写每个 pad 的归属 entity 与 index；它不设置 Source/Sink flags、不匹配远端、不建 link。`media_create_pad_link()` 在指定 Source pad 与 Sink pad 间创建运行时 link/backlink，并保存 flags（可包含 ENABLED）；它不初始化 pad、不启动 Sensor、不让图像开始传输。方向是调用者先通过 pad flags 定义，再由 link 连接两个已有 pad。</mark>

### 3. 从 IMX415 的 DTS `remote-endpoint` 开始，完整说明“原理图物理连线、DTS endpoint 对端声明、D-PHY endpoint 解析、V4L2 Async fwnode 匹配、D-PHY `.bound()`、`media_create_pad_link()`”的先后顺序和职责；其中哪一步首次出现真实 IMX415 subdev，哪一步首次出现运行时 Media Graph link？

**我的回答：** remote-endpoint 是物理接口连接；V4L2 Async 是平台注册 sensor 变成可用的 camera 接口；media link 是一种数据拓扑结构。

<mark>正确答案：`remote-endpoint` 不是物理连线本身，物理连线要看原理图；它是 DTS 对“硬件对端是谁”的声明。D-PHY 解析 endpoint 后生成 fwnode 匹配条件；V4L2 Async 用该条件把真实 IMX415 subdev 与 D-PHY notifier 配对；D-PHY `.bound()` 最后调用 `media_create_pad_link()`，把已存在的两个 pad 写入运行时 Media Graph。顺序是：DTS 声明 → endpoint 解析/Async 匹配 → `.bound()` → runtime link。</mark>

### 4. 请写清 V4L2 Async 的 `notifier->waiting`、`notifier->done`、全局 `subdev_list`、全局 `notifier_list` 分别保存的 C 对象类型和状态；并分别说明“notifier 后注册”和“subdev 后注册”时，入口函数如何扫描另一侧链表、匹配成功后 `asd` 与真实 `sd` 怎样迁移？

**我的回答：** 等待匹配的表、已经匹配完成的表、子设备列表、通知器连表，注册扫描先后顺序。

<mark>正确答案：`waiting` 放尚未匹配的 `struct v4l2_async_subdev`（asd，等待条件）；`done` 放已匹配且 `.bound()` 成功的真实 `struct v4l2_subdev`；全局 `subdev_list` 放已注册但未命中 notifier 的真实 subdev；全局 `notifier_list` 放已注册的 notifier。notifier 后到时扫描 `subdev_list`；subdev 后到时扫描 `notifier_list`。</mark>

### 5. 结合你的 RK3568 链路，解释为什么 `struct csi2_dphy` 同时拥有 `dphy->notifier` 和 `dphy->sd`：它们各自由哪个函数注册、上游/下游各匹配谁、匹配成功后分别做什么？请明确这不是同一次 Async 匹配，也不是重复注册。

**我的回答：** DPHY 作为上下游中间的节点承上启下。上游设备准备好等 DPHY 去匹配；往下是注册节点让别人去匹配。

<mark>正确答案：正确。D-PHY notifier 向上游等待并匹配 IMX415 subdev；D-PHY 自己的 `dphy->sd` 向下游注册，供 RKISP notifier 匹配。前者解决“谁输入给我”，后者解决“我输出给谁”。</mark>

### 6. 当 `media-ctl -p` 显示 `m00_b_imx415 4-001a-1:pad0 Source -> rockchip-csi2-dphy0:pad0 Sink [ENABLED]` 时，最严格能证明的内核软件事实是什么？请至少列出五项它仍然不能证明的硬件或出帧事实，并说明应分别靠什么证据继续验证。

**我的回答：** 证明 IMX415 的数据端口输出到 DPHY 口。

<mark>正确答案：只能证明 Linux Media Graph 中 `IMX415 Source pad → D-PHY Sink pad` 的软件 link 已创建且当前被选中。不能证明 IMX415 已开流并输出 RAW，也不能证明 MIPI Lane、电源、时钟、D-PHY 锁定、CSI/ISP/DMA 正常。</mark>

### 7. 板端 `media-ctl -p` 已看到 IMX415 entity 与 Source pad，却没有 `IMX415 → D-PHY` 的 link。请按“最早缺失证据”给出完整排查顺序：先看哪个 entity/pad，再追哪个 DTS `port@0`/endpoint，再看哪个 Async 匹配函数与 D-PHY `.bound()`，最后检查哪一个创建 link 的 API 和哪些失败条件；同时说明此时为什么不该先查 ISP、曝光或 `/dev/video0`。

**我的回答：** 先排查 DPHY 有没有注册成功，然后排查 415 到 DPHY 的匹配。

<mark>正确答案：方向对，但要按最早缺失证据展开：先确认 D-PHY entity/pad 是否存在；再确认 D-PHY `port@0` 已解析出远端 endpoint 和 asd 条件；接着查 `v4l2_async_find_match()` 是否命中、`rockchip_csi2_dphy_notifier_bound()` 是否执行；最后检查 IMX415 是否有 Source pad，以及 `media_create_pad_link()` 是否返回错误。不要先跳到 ISP、曝光或用户态抓帧。</mark>

### 8. dmesg 出现 `Async subdev notifier completed` 时，请说明 RKISP 根 notifier 的 `.complete()` 已完成了哪些软件层步骤；再从应用取流角度列出它之后仍必须发生的完整链路：`open/REQBUFS/QBUF/STREAMON`、各 subdev 开流、IMX415 输出、D-PHY/CSI/ISP、DMA、`DQBUF`。最后说明哪一项证据才能直接证明用户态实际拿到帧。

**我的回答：** 只能说明软件方面跑通了，并不能说明物理接口能通。

<mark>正确答案：正确，面试时还应补全：它说明 RKISP 根 notifier 已完成其 Async 收口和软件建链/默认格式主路径；但不证明 `STREAMON` 已成功、不证明 Sensor 寄存器已配置并开始输出、不证明 MIPI/CSI 无错，也不证明 ISP 中断、DMA buffer 与 `DQBUF` 连续正常。</mark>

## 面试问题：压轴题

Sensor 已经调用 helper 注册，为什么 D-PHY 仍然需要自己的 endpoint notifier？

**我的回答：**

>

<mark>高亮正确答案：Sensor helper 一方面把 Sensor 本体放入 Async 可匹配集合，另一方面解析 Sensor 的 flash/lens/ir-cut 等辅助引用；它不知道哪个接收端 pad 要连接自己。D-PHY endpoint notifier 从自己的 port@0 解析远端 Sensor fwnode和 lane/mbus，建立 waiting 条件；匹配后由 D-PHY .bound 保存真实 Sensor，并直接调用 media_create_pad_link 创建 Sensor→D-PHY 边。两者处在配对的不同侧，职责不能互相替代。</mark>
