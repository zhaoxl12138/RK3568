# Media Device、Entity、Pad、Link：对象怎样真正组成图

> [[02-源码陪读/06-Media-Controller/00-源码陪读索引|返回源码陪读索引]]

## 阅读前先做一个生活化翻译

把 Media Graph 想成工厂地图：

```text
media_device = 整个厂区的总图
media_entity = 一个工位或设备
media_pad    = 工位的入口/出口
media_link   = 两个工位之间的道路
```

例如 IMX415 是一个 `entity`，它的 `pad0` 是输出端；D-PHY 也是一个 `entity`，它的 `pad0` 是输入端。`media_create_pad_link()` 建立的是“地图上的道路”，不是马上向 Sensor 写寄存器，也不是把一帧 RAW 数据复制到 D-PHY。

读到 `media-ctl -p` 时，先按下面顺序翻译：

```text
entity → 这是什么模块
pad    → 这个模块的哪个端口
Source → 从当前模块向外输出
Sink   → 当前模块接收输入
link   → 两个端口之间的连接关系
ENABLED → 这条软件连接当前被启用
```

这一步只建立“看图能力”。格式协商、Sensor 寄存器写入、MIPI 电气信号和最终 DMA 取帧，分别属于后续的 V4L2 Subdev、Sensor 驱动、D-PHY/CSI/ISP 硬件和 VB2 取流流程。

## 大白话：不是四个名词，而是四层索引

## 对象关系逐行注释

先只看“谁包含谁”，不要把它误读成函数调用：

```c
struct rkisp_device
 ├─ struct media_device media_dev
 │    // RKISP 逻辑实例的 Media 根图，管理整张 entity/pad/link 图。
 ├─ struct v4l2_device v4l2_dev
 │    // V4L2 设备集合对象，不等于 /dev/video0。
 │    └─ v4l2_dev.mdev ──> &media_dev
 │         // 指针关联：告诉 V4L2 使用哪一个 Media 根图。
 └─ struct v4l2_async_notifier notifier
      // 等待 Sensor、D-PHY 等 subdev 的匹配清单。

struct imx415
 └─ struct v4l2_subdev subdev
      // 把 IMX415 包装成 V4L2 Camera 子设备。
      └─ struct media_entity entity
           // subdev 内嵌的 Media 图节点，表示“IMX415 在图中是谁”。

struct csi2_dphy
 ├─ struct v4l2_subdev sd
 │    └─ struct media_entity entity
 │         // D-PHY 也作为一个 Media/V4L2 子模块加入图中。
 ├─ struct media_pad pads[2]
 │    // D-PHY 的输入/输出端口，不是图像 buffer。
 └─ struct v4l2_async_notifier notifier
      // 等待远端 Sensor；匹配后 .bound() 才可能创建 link。
```

对应的 C 代码动作：

| 写法                                  | 含义                      |
| ----------------------------------- | ----------------------- |
| `struct media_entity entity;`       | 在外层对象内部嵌入 entity        |
| `sd = &imx415->subdev;`             | 取已有成员地址，不是创建新对象         |
| `v4l2_dev.mdev = &media_dev;`       | 建立对象指针关系，不是函数调用         |
| `container_of(member, type, field)` | 由成员地址找回外层对象             |
| `media_entity_pads_init()`          | 初始化 entity 的 pad 数组     |
| `media_create_pad_link()`           | 在软件 Media Graph 中登记一条连接 |
|                                     |                         |

所以这张对象图回答的是“内核对象怎样互相找到”，并不表示像素已经经过这些对象。真实数据仍由 Sensor、MIPI、D-PHY、CSI、ISP 和 DMA 硬件完成。

```text
struct media_device
 ├─ entities 全局链表 ──> struct media_entity
 ├─ pads     全局链表 ──> struct media_pad.graph_obj
 └─ links    全局链表 ──> struct media_link.graph_obj

struct media_entity
 ├─ pads 指针 + num_pads ──> 调用者拥有的 pad 数组
 └─ links 链表
     ├─ Source 侧：正向 link
     └─ Sink 侧：backlink

struct media_pad
 ├─ entity ──> 反向指回所属方框
 ├─ index
 └─ flags: SOURCE / SINK / MUST_CONNECT

struct media_link
 ├─ source ──> Source pad
 ├─ sink   ──> Sink pad
 ├─ reverse ──> 另一侧的内核表示
 ├─ flags
 └─ is_backlink
```

这种设计同时服务两种查询：从根图枚举全部对象；从任意 entity 沿本地 `links` 遍历邻居。backlink 是为第二种查询付出的索引成本。

## 为什么 entity 常被内嵌

`struct v4l2_subdev` 内嵌 `struct media_entity entity`，`struct video_device` 也有自己的 media entity。这样 V4L2 对象和 Media 图节点共享生命周期与地址关系：

- `&sd->entity` 是取 subdev 内部 entity 的地址，不是复制；
- `media_entity_to_v4l2_subdev(entity)` 可依据对象类型和 `container_of()` 找回外层 subdev；
- 驱动私有对象还可能继续内嵌 subdev，例如 `struct imx415` 内嵌 `subdev`，形成 `imx415 → subdev → entity`；
- 内嵌只解决“对象在哪里、由谁拥有”，不会自动设置 `ops`、不会自动初始化 pads，也不会自动注册 Async。

`ops` 也是分层的：`sd->ops` 指向 V4L2 subdev 操作表，`entity->ops` 指向 Media entity 操作表，`notifier->ops` 指向 Async 回调表。给它们赋值只是**函数指针赋值**，不是执行回调。

## `media_entity_pads_init()`：逐字段状态变化

Source Insight 打开 `drivers/media/media-entity.c`，搜索 `media_entity_pads_init`，逐行做账：

| 源码动作 | 改变前 | 改变后 | 为什么需要 |
|---|---|---|---|
| 检查 `num_pads` | 数量未经核心校验 | 超过上限返回 `-E2BIG` | 防止图对象数量不受控 |
| `entity->num_pads = num_pads` | entity 不知道端口个数 | 保存数组有效元素数 | 后续遍历和下标校验依赖它 |
| `entity->pads = pads` | entity 没有端口数组入口 | 指向调用者准备的数组 | 建立 entity→pads 对象关联；这里没有分配或复制数组 |
| `pads[i].entity = entity` | pad 未知归属 | 每个 pad 反向指回 entity | 从 link 拿到 pad 后可继续找到方框 |
| `pads[i].index = i` | 下标未写入 | 0..n-1 稳定编号 | 用户态拓扑和 link 参数都按 pad index 表示 |
| 若 `mdev != NULL` 则 `media_gobj_create(...)` | pad 还不是根图全局对象 | pad 加入 media_device 的图对象集合 | 兼容“entity 已注册后再初始化 pad”的路径 |

注意三条源码事实：

1. 函数不修改 `pads[i].flags`。Source/Sink 必须由调用者在进入函数前赋值。
2. 函数不调用 `media_create_pad_link()`。端口存在不等于端口已有对端。
3. 若调用时 entity 尚未挂到 `media_device`，`mdev` 为空，函数不会创建 pad graph object；后续 `media_device_register_entity()` 会遍历 `entity->pads` 补建 graph object。

因此下面不是一句“注册 V4L2”，而是四个可分开的动作：

```c
dphy->pads[SOURCE].flags = MEDIA_PAD_FL_SOURCE;       // 字段赋值：方向
dphy->pads[SINK].flags = MEDIA_PAD_FL_SINK;           // 字段赋值：方向
dphy->sd.entity.function = MEDIA_ENT_F_VID_IF_BRIDGE; // 字段赋值：方框功能
ret = media_entity_pads_init(&dphy->sd.entity, 2, dphy->pads); // 直接调用：建立归属/下标
```

## `media_create_pad_link()`：一条逻辑边为何创建两个对象

函数接收 Source entity/index、Sink entity/index 和 flags。它的内部不是“给两个 pad 打一个 connected 标志”，而是分配两份 `struct media_link`：

### 第一步：创建 Source 侧正向 link

```c
link = media_add_link(&source->links);
link->source = &source->pads[source_pad];
link->sink = &sink->pads[sink_pad];
link->flags = flags & ~MEDIA_LNK_FL_INTERFACE_LINK;
media_gobj_create(source->graph_obj.mdev, MEDIA_GRAPH_LINK,
                  &link->graph_obj);
```

`media_add_link()` 直接分配一个零初始化对象，并把 `link->list` 挂到 `source->links`。随后保存两端 pad 地址和 flags，并把内嵌 `graph_obj` 注册到 `media_device`。这份对象是用户态所见逻辑 link 的正向表示。

### 第二步：创建 Sink 侧 backlink

```c
backlink = media_add_link(&sink->links);
backlink->source = &source->pads[source_pad];
backlink->sink = &sink->pads[sink_pad];
backlink->flags = flags;
backlink->is_backlink = true;
```

第二个对象挂到 `sink->links`，两端 pad 指针仍描述 Source→Sink，不是反过来填。`is_backlink = true` 表明它是反向遍历索引，不向用户态重复报告成第二条边。若分配失败，函数会删除刚创建的正向 link，避免半条连接残留。

### 第三步：互指并更新计数

```c
link->reverse = backlink;
backlink->reverse = link;
sink->num_backlinks++;
sink->num_links++;
source->num_links++;
```

`reverse` 让任一表示都能找到配对对象。Sink 同时增加总 link 数和 backlink 数；Source 只增加总 link 数。以后从 Source 或 Sink 开始图遍历都能遇到这条逻辑边。

白话：道路只修一条，但道路管理系统在道路两端各放一张索引卡。Sink 侧那张卡叫 backlink；两张卡互相写着对方编号。不能因为内核分配了两个 `struct media_link` 就说物理上或用户态出现两条线。

## 从 DTS endpoint 到 Sensor→D-PHY link

```text
DTS endpoint                                  [固件对象关联]
  ↓ parser 读取 local/remote endpoint         [直接调用]
asd.match_type = V4L2_ASYNC_MATCH_FWNODE      [字段赋值]
asd.match.fwnode = remote port parent          [对象关联]
  ↓ Async 找到 sd->fwnode 相同的 Sensor
v4l2_async_match_notify()                     [Async 内部直接调用]
  ↓ notifier->ops->bound(...)                 [框架回调]
rockchip_csi2_dphy_notifier_bound()
  ├─ sensor->sd = sd                          [对象关联]
  ├─ 找 Sensor 的 MEDIA_PAD_FL_SOURCE         [字段读取]
  └─ media_create_pad_link(...)               [直接调用]
```

DTS endpoint 不是运行时 `struct media_link`；`asd.match.fwnode` 也不是 link。前者提供静态连接描述，后者提供身份匹配键，`.bound` 才拿到两端真实 entity/pad，最后直接调用 `media_create_pad_link()` 创建运行时边。

当前 D-PHY 驱动把第一个绑定的 Sensor link 设为 `MEDIA_LNK_FL_ENABLED`，后续候选 Sensor 的 link 初始 flags 为 0。`[ENABLED]` 来自 link flags，不来自 pad 的 Source/Sink flags。

## 当前板子的主数据链如何映射对象

```text
IMX415 entity / pad0 Source / SGBRG10
  └─ link: Sensor pad0 → D-PHY pad0 [ENABLED]
D-PHY entity / pad0 Sink / pad1 Source
  └─ link: D-PHY pad1 → rkisp-csi-subdev pad0
rkisp-csi-subdev / pad0 Sink / pad1 Source
  └─ link: CSI pad1 → rkisp-isp-subdev pad0
rkisp-isp-subdev / pad0 Sink / pad2 Source
  └─ link: ISP pad2 → rkisp_mainpath pad0
rkisp_mainpath / pad0 Sink / /dev/video0
```

每个箭头都必须能追到某次 `media_create_pad_link()` 或等价建链路径；entity 内部的 Sink→Source 只是该硬件方框的处理关系，不是 `media_create_pad_link()` 创建的一条跨 entity link。

Media bus code（如 `SGBRG10_1X10`）描述 subdev pad 间总线数据；内存 FourCC（如 NV12）描述 video node buffer。拓扑、pad 格式和内存格式是三层证据。

## 白话与证据边界

- 看见 `entity->pads = pads`，能证明对象关联被建立；不能证明 entity 已进入根图。
- 看见 `media_entity_pads_init()` 返回 0 数组，能证明 pad归属/下标初始化成功；不能证明任意 link 存在。
- 看见 `media_create_pad_link()` 返回 0，能证明内核建立了正向对象、backlink、reverse 和计数；不能证明硬件端口真实连通。
- `media-ctl -p` 看见双方 pad 与 `[ENABLED]`，能证明用户态查询到启用的软件边；不能证明包经过、格式正确到每一层或 DMA 完成。

## 面试问题

为什么 `media_create_pad_link()` 要创建 source link 和 sink backlink？

**我的回答：**

>

<mark>高亮正确答案：entity 各自维护本地 links 链表。正向对象挂在 Source entity，backlink 挂在 Sink entity，使图遍历从任一端出发都能找到同一逻辑边。两者保存相同 source/sink pad，is_backlink 区分反向索引，reverse 互相配对；用户态不会把 backlink 当成第二条独立连接。</mark>
