# 06 Media Controller：源码陪读入口

>

## 这一章只解决一个问题

> IMX415、D-PHY、RKISP 各自完成 probe 后，Linux 是怎样把它们组织成一张 Media Graph 的？

**大白话：**先不要把它理解成“Media Controller 传输图像”。

```text
Media Controller
    = 管理模块之间的连接关系

/dev/video0
    = 应用程序最后取帧的出口
```

**板端证据边界：**`media-ctl -p` 中出现并启用 Media Link，能证明软件拓扑已经建立；不能证明 MIPI 像素已经稳定传输，也不能证明应用能够持续取帧。

## 先看一张主线图

```text
D-PHY 逻辑驱动 probe
        ↓
初始化 V4L2 subdev
        ↓
初始化 Sink/Source pads
        ↓
解析 DTS endpoint
        ↓
注册 Async notifier
        ↓
等待 IMX415 subdev
        ↓
Async Core 匹配双方
        ↓
回调 .bound()
        ↓
media_create_pad_link()
        ↓
Sensor → D-PHY 的 Media link 建立
```

这里有两个必须分开的概念：

```text
直接调用：
probe() 内部主动调用下一个函数

框架回调：
Platform Core / V4L2 Async Core
在条件满足后反过来调用驱动函数
```

例如：

```text
rockchip_csi2_dphy_probe()
    → media_entity_pads_init()
```

是直接调用。

```text
V4L2 Async Core
    → rockchip_csi2_dphy_notifier_bound()
```

是框架回调。

## 你现在先追哪一段

当前只追这一条，不要一次打开所有源码：

```text
rockchip_csi2_dphy_probe()
    ↓
rockchip_csi2dphy_media_init()
    ↓
media_entity_pads_init()
    ↓
v4l2_async_notifier_parse_fwnode_endpoints_by_port()
    ↓
v4l2_async_subdev_notifier_register()
```

追到这里先停住。你要回答：

### 问题 1：probe() 是谁调用的？

**我的回答：** 平台驱动调用的 probe。

<mark>正确答案：不是 platform_driver 自己普通地直接调用。Platform Core 先把 platform_device 和 platform_driver 匹配成功，再通过驱动模型回调该 driver 的 .probe，也就是 rockchip_csi2_dphy_probe(pdev)。</mark>

### 问题 2：media_entity_pads_init() 初始化了什么对象？

**我的回答：** 声明端口对象，还有数据和数据传输流向。

<mark>正确答案：前半句基本正确，但它主要初始化 entity 与 pad 数组的对象关系，例如保存 num_pads、pads 指针，并为每个 pad 设置所属 entity 和 index。数据流向还要看调用者给 pad 设置的 MEDIA_PAD_FL_SINK 或 MEDIA_PAD_FL_SOURCE 标志；它本身不负责搬运数据，也不单独创建两端 link。</mark>

### 问题 3：endpoint 解析从 DTS 取出了什么？

**我的回答：** 解析了 pad。

<mark>正确答案：不仅是 pad。它从 DTS 的 port/endpoint 中读取远端 endpoint 引用，并转换成 V4L2 Async 可以使用的匹配条件；同时会涉及端口关系、总线类型以及 data-lanes 等 endpoint 信息。pad 是驱动内部的端口对象，endpoint 是 DTS 中描述硬件连接的固件节点，两者不能直接画等号。</mark>

### 问题 4：notifier 注册后为什么不会立刻执行 .bound()？

**我的回答：** 需要等待匹配成功后才能执行 .bound，也就是 D-PHY 和 I2C 驱动节点的匹配。

<mark>正确答案：等待匹配成功这一点正确，但“注册后一定不会立刻执行 .bound()”不准确。注册 notifier 时，Async Core 会立刻尝试扫描已有 subdev：如果 IMX415 已经在 subdev_list 中，本次 v4l2_async_subdev_notifier_register() 调用过程中就可能直接触发 .bound()；如果 IMX415 尚未注册，notifier 才进入等待状态，等它以后注册时再匹配。匹配对象是 notifier 保存的远端 endpoint/fwnode 条件，与已注册到 V4L2 Async 框架的 IMX415 V4L2 subdev；这里不是重新匹配 I2C driver。匹配成功后，由 .bound() 内部调用 media_create_pad_link()。</mark>

本轮结论：

- 问题 1：理解了“平台驱动”和 probe 的关系，但要补上 Platform Core 回调。
- 问题 2：知道 pad 是端口，但要区分“pad 初始化”和“pad 方向/Media link”。
- 问题 3：需要重点区分 DTS endpoint、Media pad、V4L2 subdev。
- 问题 4：主线理解正确，下一步要把 Async 的匹配对象说准确。

## 本轮问题与批改：I2C、Platform、Async 的匹配关系

### 我的疑问

```text
I2C 匹配：
imx415@1a
    ↔
imx415_i2c_driver

Async 匹配：
csi2_dphy.notifier
    ↔
imx415.subdev

Async 匹配：
rkisp_device.notifier
    ↔
csi2_dphy.sd
```

这是不是三个对象按顺序完成？是不是只有 I2C 匹配从 DTS 开始？

### 先给结论

<mark>正确答案：不是三方依次进行同一种匹配，而是三种不同层次的匹配。I2C 匹配负责把 IMX415 硬件绑定到 IMX415 I2C 驱动；Platform 匹配负责启动 D-PHY 和 RKISP 驱动；V4L2 Async 匹配负责把已经注册好的 Sensor、D-PHY、RKISP subdev 按 DTS endpoint 连接起来。</mark>

## 一、DTS 是共同信息来源，但由不同框架分别使用

```text
DTS
├── I2C4 的 imx415@1a
│   ├── compatible = "sony,imx415"
│   ├── reg = <0x1a>
│   └── 创建 i2c_client：4-001a
│       └── I2C Core 匹配 imx415_i2c_driver
│           └── 调用 imx415_probe()
│               └── 注册 imx415.subdev
│
├── csi2_dphy0
│   ├── compatible = "rockchip,rk3568-csi2-dphy"
│   └── 创建 platform_device
│       └── Platform Core 匹配 D-PHY platform_driver
│           └── 调用 rockchip_csi2_dphy_probe()
│               └── 注册 csi2_dphy.sd 和 csi2_dphy.notifier
│
└── RKISP 节点
    ├── compatible
    └── 创建 platform_device
        └── Platform Core 匹配 RKISP platform_driver
            └── 调用 RKISP probe
                └── 创建 rkisp_device 和 rkisp_device.notifier
```

<mark>正确答案：三者都和 DTS 有关，只是读取的属性不同：I2C 主要使用 compatible 和 reg；Platform 主要使用 compatible；Async 主要使用 port、endpoint、remote-endpoint 和 fwnode。</mark>

所以不能理解成“只有 I2C 匹配从 DTS 开始”，而应该理解成：

```text
同一份 DTS
    ↓ 被不同框架分别解析
I2C Core       → 创建 I2C client 并匹配 I2C driver
Platform Core  → 创建 platform_device 并匹配 platform_driver
V4L2 Async     → 根据 endpoint/fwnode 匹配已经注册的 subdev
```

## 二、两个 Async 匹配不是同一个动作

### 1. D-PHY 等待 IMX415

```text
csi2_dphy.notifier
    = D-PHY 的等待清单

imx415.subdev
    = 已注册到 V4L2 框架的真实 Sensor 子设备
```

匹配关系：

```text
csi2_dphy.notifier
        ↕
imx415.subdev
```

匹配成功后：

```text
V4L2 Async Core
    ↓
调用 D-PHY notifier 的 .bound()
    ↓
rockchip_csi2_dphy_notifier_bound()
    ↓
media_create_pad_link()
```

建立：

```text
IMX415 pad0 Source
    → D-PHY pad0 Sink
```

这里匹配的不是 imx415_i2c_driver，因为 I2C driver 在更早的 I2C 总线匹配阶段已经完成了自己的工作。Async 阶段面对的是 IMX415 的 V4L2 subdev。

### 2. RKISP 等待 D-PHY/CSI

```text
rkisp_device.notifier
    = RKISP 的等待清单

csi2_dphy.sd
    = 已注册到 V4L2 框架的 D-PHY 子设备
```

匹配关系：

```text
rkisp_device.notifier
        ↕
csi2_dphy.sd
```

匹配成功后：

```text
RKISP 的 .bound()
    ↓
保存或关联 D-PHY/CSI subdev
    ↓
所有依赖满足
    ↓
RKISP 的 .complete()
    ↓
继续建立 D-PHY/CSI → RKISP 的后半段 Media link
```

注意：

```text
rkisp_device.media_dev
    = Media Graph 的根对象
    = 不是 Async 匹配对象

真正参与第二次 Async 匹配的是：
rkisp_device.notifier ↔ csi2_dphy.sd
```

## 三、它们是不是严格按顺序完成？

逻辑依赖可以这样记：

```text
I2C 匹配
    ↓
imx415_probe()
    ↓
注册 imx415.subdev
    ↓
D-PHY notifier ↔ IMX415 subdev
    ↓
建立 IMX415 → D-PHY link
    ↓
RKISP notifier ↔ D-PHY/CSI subdev
    ↓
RKISP .complete()
    ↓
建立后半段 Media link
```

但是，实际注册时间不保证严格按照这条线执行。

因为：

```text
Sensor probe 可能先执行
D-PHY probe 可能先执行
RKISP probe 也可能先执行
```

Async 框架专门处理这种先后不确定的情况：

```text
notifier 先注册
    ↓
保存等待条件
    ↓
扫描已经注册的 subdev

subdev 先注册
    ↓
暂存到 subdev_list
    ↓
等待后来的 notifier 扫描
```

<mark>正确答案：依赖关系相对稳定，但实际时间顺序可能交错。Async 通过 notifier_list 和 subdev_list 保存“先到的一方”，等另一方出现后再匹配。</mark>

## 四、三种匹配分别能证明什么

| 匹配 | 主要证明 | 不能直接证明 |
|---|---|---|
| I2C client ↔ imx415_i2c_driver | Sensor 找到了负责控制它的 I2C 驱动 | MIPI、ISP 和最终出图正常 |
| platform_device ↔ D-PHY/RKISP platform_driver | SoC 内部控制器驱动开始初始化 | Sensor 一定已经连接 |
| notifier ↔ subdev | V4L2 子设备之间满足匹配条件，可以进入 .bound() | 像素已经通过 MIPI，DMA 已经得到帧 |

### 最后压成一句面试表达

<mark>DTS 是共同的硬件描述来源，但 I2C、Platform 和 V4L2 Async 分别消费其中不同的信息。I2C 匹配先负责把 Sensor 绑定到 I2C 驱动，Platform 匹配负责启动 D-PHY 和 RKISP 控制器，Async 匹配再把已经注册好的 Sensor、D-PHY 和 RKISP subdev 按 endpoint 关系组织成 Media Graph。它们存在逻辑依赖，但实际 probe 和匹配的时间顺序可能交错。</mark>
