# V4L2/VB2 取流调试与面试验收

## 本篇只在“源码链已看完”后使用

这是验收页，不再重复函数逐行陪读。最常见的实板问题是 **DQBUF 超时**：
不要从应用端猜，按 `mi_frame_end → vb2_buffer_done(DONE) → done_list → DQBUF`
从右向左补证据。前两篇分别解释“怎样分发到函数”和“buffer 怎样换手”。

## 先建立“取不到图”的分层判断

用户只看到一个现象：程序没有拿到图像。但内核实际可能卡在完全不同的位置：

```text
设备节点不存在           → 注册/枚举问题
格式设置失败             → V4L2/ISP 格式协商问题
REQBUFS 失败             → VB2 内存或队列配置问题
QBUF 成功但 STREAMON 失败 → 管线、Sensor 或硬件启动问题
STREAMON 成功但 DQBUF 超时 → IRQ、DMA、帧结束或上游无数据
DQBUF 成功但画面异常     → 格式、stride、plane 或图像处理问题
```

这就是本篇的核心：不要把所有故障都叫“Camera 驱动没起来”，而是用每一个 ioctl、VB2 状态和中断证据，把问题定位到具体一层。

## Source Insight 精确入口与大白话解释

通用 ioctl 从 `drivers/media/v4l2-core/v4l2-ioctl.c` 进入；buffer 状态在 `drivers/media/common/videobuf2/videobuf2-core.c` 改变；RKISP 的 STREAMON 与 frame-end 在 `drivers/media/platform/rockchip/isp/capture_v21.c`。大白话：先确认应用发对命令，再确认 VB2 真的把 buffer 交给驱动，最后确认帧结束路径把它放回完成队列。

## 白话调试原则

不要用“抓不到图”概括所有故障。把链路切成七张收据：格式、分配、查询、映射、入队、开流、完成出队。每张收据只证明它以下的一小段；前一步成功不能替后一步背书。

## Source Insight 调试搜索表

| 现象 | 搜索符号 | 调用类型 | 重点变量/语句 |
|---|---|---|---|
| ioctl 没到目标实现 | `video_ioctl2`、`__video_do_ioctl`、`v4l2_ioctls` | VFS 回调 + 命令表回调 | `cmd`、`info->func`、`vfd->ioctl_ops` |
| S_FMT 返回异常 | `rkisp_s_fmt_vid_cap_mplane`、`rkisp_set_fmt` | ioctl_ops 函数指针回调后直接调用 | `streaming`、FourCC、`num_planes/bytesperline/sizeimage` |
| REQBUFS 失败 | `vb2_ioctl_reqbufs`、`vb2_core_reqbufs`、`rkisp_queue_setup` | 适配层直接调用，Core 回调驱动 | owner、memory、`num_buffers/num_planes/sizes[]` |
| QUERYBUF/mmap 失败 | `vb2_ioctl_querybuf`、`vb2_fop_mmap`、`vb2_mmap` | ioctl 回调 / fops 回调 | index、plane length、offset、VMA |
| QBUF 后驱动无 buffer | `vb2_core_qbuf`、`__enqueue_in_driver`、`rkisp_buf_queue` | Core 直接调用后函数指针回调 | `start_streaming_called`、`QUEUED/ACTIVE`、DMA 地址 |
| STREAMON 失败 | `vb2_core_streamon`、`vb2_start_streaming`、`rkisp_start_streaming` | 直接调用后 `q->ops` 回调 | type、`num_buffers`、`queued_count`、link/input、pipeline |
| DQBUF 卡住 | `rkisp_mi_v21_isr`、`mi_frame_end`、`vb2_buffer_done`、`__vb2_wait_for_done_vb` | 中断直接调用 + 等待队列 | IRQ status、curr_buf、`done_list/done_wq` |

用 Source Insight 看函数指针时，至少留下三类证据：表在哪里赋值、框架在哪里解引用、运行时对象怎样从 `file` 或 `queue->drv_priv` 找回。只看函数定义不能回答“谁调用”。

## 最小板端命令

```bash
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoX --all
v4l2-ctl -d /dev/videoX --list-formats-ext
v4l2-ctl -d /dev/videoX \
  --set-fmt-video=width=3840,height=2160,pixelformat=NV12 \
  --stream-mmap=4 --stream-count=30 \
  --stream-to=/tmp/imx415-30f.nv12 --stream-poll --verbose
stat -c '%s bytes' /tmp/imx415-30f.nv12
dmesg | tail -n 200
```

先确认 `/dev/videoX` 的真实节点名是 `rkisp_mainpath` 或目标 path，不要把 raw write、statistics、params node 当成 mainpath。`V4L2_CAP_VIDEO_CAPTURE_MPLANE` 表示接口结构是 mplane；实际 buffer 的 API plane 数仍以 `S_FMT/G_FMT` 返回的 `num_planes` 为准。

## 一步一证据：能证明与不能证明

| 观察 | 能证明 | 不能证明 |
|---|---|---|
| `open` 成功 | node 存在且 `v4l2_open → rkisp_fh_open` 没报错 | 格式、buffer、DMA、首帧 |
| `S_FMT` 成功并读回 | RKISP 接受后的宽高/FourCC/`num_planes/sizeimage` | 内存已分配、硬件已按此出帧 |
| `REQBUFS` 返回 count | `queue_setup` 与 buffer 分配完成，queue owner 建立 | mmap 成功、QBUF、物理连续 |
| 每个 `QUERYBUF` 成功 | index/plane offset 与 length 可查询 | 用户 VMA 已建立、DMA 已写 |
| 每个 `mmap` 成功 | CPU 用户虚拟映射建立 | buffer 已 `QUEUED/ACTIVE`，DMA 连续性 |
| `QBUF` 成功 | buffer 至少进入 VB2 `QUEUED` | 一定已到 RKISP；未开流时可能还不是 `ACTIVE` |
| `STREAMON` 成功 | VB2/RKISP 启动路径返回 0，`q->streaming` 已置位 | 帧结束中断已到、buffer 已 DONE |
| `vb2_buffer_done(DONE)` trace/断点命中 | 驱动已把某 ACTIVE buffer 放进完成路径 | 用户已经执行 DQBUF、图像内容正确 |
| `DQBUF` 成功且元数据合理 | `done_list` 有项并已返回应用 | 色彩、曝光、30 帧连续、长期稳定、物理连续 |

这就是“能证明/不能证明”的边界。为什么这样设计证据阶梯：异步 DMA 把“请求已接受”“硬件已启动”“一帧已完成”“应用已领取”分成不同时间点，合并判断会把问题定位到错误层。

## 每个 ioctl 的断点与状态预期

### S_FMT

调用链：`__video_do_ioctl → v4l_s_fmt → rkisp_s_fmt_vid_cap_mplane → rkisp_set_fmt`。

观察：返回后的 `stream->out_fmt`，尤其 `num_planes` 和每个 `plane_fmt[]`。状态变化不在 buffer；若 queue 正在 streaming，应在 RKISP 回调返回 `-EBUSY`。

### REQBUFS

调用链：`vb2_ioctl_reqbufs → vb2_core_reqbufs → q->ops->queue_setup → __vb2_queue_alloc`。

观察：`q->memory`、`q->num_buffers`、`q->bufs[]`、`q->owner`。失败先区分另一个 file handle 持有 queue、buffer 仍 mmap/in use、分配器失败还是 `queue_setup` 拒绝。

### QUERYBUF 与 mmap

调用链分别是 `vb2_ioctl_querybuf → vb2_querybuf → vb2_core_querybuf`，以及 `v4l2_mmap → vb2_fop_mmap → vb2_mmap`。

观察：应用给对 `type/index/length/m.planes`；多平面 API 需要为 `v4l2_buffer.m.planes` 提供数组。QUERYBUF 只返回 offset，mmap 才建立 VMA；二者都不把 buffer 交给驱动。

### QBUF

调用链：`vb2_ioctl_qbuf → vb2_qbuf → vb2_core_qbuf`。首个关键断点是 `vb->state = VB2_BUF_STATE_QUEUED`；第二个是 `__enqueue_in_driver()` 中 `ACTIVE`；第三个是 `rkisp_buf_queue()` 取得 DMA 地址。

若 QBUF 成功但没进 `rkisp_buf_queue`，先看是否尚未 STREAMON；若已开流，看 `q->start_streaming_called` 和 queue error。不要把 `QUEUED` 误报成驱动已经持有。

### STREAMON

调用链：`vb2_ioctl_streamon → vb2_streamon → vb2_core_streamon → vb2_start_streaming → q->ops->start_streaming → rkisp_start_streaming`。

本树 `min_buffers_needed` 实际可为 0；检查实际值，不背固定数字。观察 `num_buffers/queued_count/owned_by_drv_count/start_streaming_called/streaming`，再看 RKISP 的 link/input、pipeline power、MI 配置和 subdev `set_stream` 返回。

### DQBUF

调用链：`vb2_ioctl_dqbuf → vb2_dqbuf → vb2_core_dqbuf → __vb2_get_done_vb`。阻塞 fd 睡在 `done_wq`；`O_NONBLOCK` 且 `done_list` 空时应返回 `-EAGAIN`。

如果一直阻塞，逆向检查：

```text
done_list 为空
  ← vb2_buffer_done(DONE) 是否命中
  ← mi_frame_end() 是否有 curr_buf
  ← rkisp_mi_v21_isr() 是否收到目标 frame_end_id
  ← MI/DMA 是否写入有效地址
  ← rkisp_buf_queue() 是否拿到 ACTIVE buffer
  ← 上游 sensor/CSI/ISP pipeline 是否真正开流
```

## DMA 何时完成，谁调用 vb2_buffer_done

RKISP 的 `rkisp_buf_queue()` 只取得并排队 DMA 地址，不代表 DMA 已完成。`rkisp_start_streaming()` 配置和启动 pipeline，也不代表首帧已结束。真正的软件完成点在 MI frame-end 中断：`rkisp_mi_v21_isr()` 根据中断状态调用 `mi_frame_end()`；后者给当前 buffer 写 `bytesused/sequence/timestamp`，正常 streaming 分支直接调用 `vb2_buffer_done(vb2_buf, VB2_BUF_STATE_DONE)`。

VB2 Core 随后把 buffer 从驱动拥有的 `ACTIVE` 变成 `DONE`，加入 `done_list`，减少 `owned_by_drv_count`，唤醒 `done_wq`。这回答了 DQBUF 为什么可返回：它等待的条件被驱动的完成调用改变了，而不是轮询像素内存猜测 DMA 是否结束。

正常完成与清理要区分：停流或启动失败时，驱动也会调用 `vb2_buffer_done(..., ERROR/QUEUED)` 归还 buffer；看到函数命中不自动等于抓到有效帧，必须同时看传入 state。

## NV12 专项验收

- `V4L2_PIX_FMT_NV12`：2 个颜色 component plane，但在本树 `mplanes = 1`，即 1 个 API plane；Y 后面按 stride/height 偏移得到 UV。
- `V4L2_PIX_FMT_NV12M`：2 个颜色 component plane，也有 2 个 API plane，应用处理两组 `v4l2_plane` 描述。
- `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`：选择 mplane API，不承诺实际 `num_planes` 一定为 2。
- API plane 不能证明物理连续：dma-contig、dma-sg、IOMMU/IOVA 是分配和映射层结论。查看 `q->mem_ops`、`is_dma_sg_ops/is_dma_contig`、DMA 地址获取分支；不能由 FourCC 推断。

理论单帧 `3840 × 2160 × 1.5 = 12,441,600` bytes 只适用于紧密布局。文件大小校验应汇总实际 DQBUF 的 `bytesused`；若工具按固定 `sizeimage` 写出，还要确认是否包含 stride/padding。

## 常见故障到第一检查点

| 现象 | 第一检查点 | 下一层证据 |
|---|---|---|
| `S_FMT -EINVAL` | node 类型、FourCC 是否在当前 stream 的 format 表 | `find_fmt` 与实际回填格式 |
| `REQBUFS -EBUSY` | queue 是否 streaming、是否已有 owner/mmap 引用 | `q->owner/memory/num_buffers` |
| `QUERYBUF/mmap -EINVAL` | index、plane 数组 length、offset 是否对应 | `num_planes` 和每 plane length |
| `QBUF -EINVAL` | buffer 是否真为 `DEQUEUED/PREPARED` | `vb->state` 与 plane 参数 |
| `STREAMON` 失败 | type、已分配 buffer、RKISP link/input | `rkisp_start_streaming` 错误分支 |
| `STREAMON` 成功但 DQBUF 超时 | 中断 → `mi_frame_end` → `vb2_buffer_done(DONE)` | `curr_buf`、IRQ status、DMA 地址、上游 s_stream |
| DQBUF 有帧但紫绿 | NV12/NV21、单/多 API plane、stride | viewer 参数、UV 顺序、ISP 参数 |
| 文件大小异常 | 每次 `bytesused` 与 `sizeimage` | 丢帧、padding、工具写文件策略 |

## 30 秒面试答案

> 注册时 RKISP 把 `rkisp_fops`、`rkisp_v4l2_ioctl_ops` 和 `vb2_queue` 挂到同一个 `video_device`，queue 又通过 `drv_priv` 和 `vb2_ops` 指回 `rkisp_stream`。应用 ioctl 经 `video_ioctl2/__video_do_ioctl` 的命令表和 ioctl_ops 两级分发进入 RKISP 或 VB2。REQBUFS 建池，QUERYBUF/mmap 建用户映射，QBUF 使 buffer 从 DEQUEUED 经 PREPARED 到 QUEUED；`__enqueue_in_driver` 再改为 ACTIVE 并回调 `rkisp_buf_queue`。STREAMON 回调 `rkisp_start_streaming` 启动 pipeline。DMA 帧结束中断中的 `mi_frame_end` 调 `vb2_buffer_done(DONE)`，它把 buffer 放入 `done_list` 并唤醒 `done_wq`，所以 DQBUF 能取出并把状态改回 DEQUEUED。NV12 的颜色 plane、API plane 与物理连续性是三个层次，必须以驱动实际 `num_planes/mem_ops` 为证据。

## 面试问题：常见陷阱

STREAMON 返回 0，是否等于已经抓到一帧？

**我的回答：**

>

<mark>高亮正确答案：不等于。它只能证明 VB2/RKISP 的启动路径成功返回并设置 streaming 状态。至少要看到 RKISP 帧结束路径以 DONE 调用 `vb2_buffer_done`，或用户成功 DQBUF 得到合理元数据，才能证明某个 buffer 完成；图像内容和长期稳定还要更高一层验收。</mark>
