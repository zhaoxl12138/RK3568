# 从 video_device 注册到 ioctl 回调

## 本篇边界：注册时挂表，运行时查表

这一篇只回答：应用拿到一个 `fd` 后，为什么能从通用 V4L2 框架走到
RKISP 的格式函数或 VB2 的 ioctl 函数。

```text
注册时挂表：vdev 保存 fops / ioctl_ops / queue 的指针
运行时查表：V4L2 Core 从 file 找 vdev，再经函数表回调
```

不要在这里追 `ACTIVE → DONE`、IRQ 或 NV12 内存布局；那是
[[02-源码陪读/08-V4L2用户态取流/02-对象与数据链|02-对象与数据链]] 的问题。

## 本篇先回答：/dev/video0 到底是什么

/dev/video0 是 Linux 为一个 `struct video_device` 注册出来的字符设备节点。它不是 Sensor 本身，也不是一块保存图像的内存；它更像应用和 Camera 驱动之间的“服务窗口”。

应用发起：

```text
open / ioctl / mmap / poll
```

V4L2 Core 再通过 `video_device` 中保存的函数表，把请求转给 RKISP 的具体实现：

```text
应用
  ↓
VFS + V4L2 Core
  ↓
video_device 的 fops/ioctl_ops
  ↓
RKISP 格式处理或 VB2 通用队列
```

因此“注册 video node”和“应用已经拿到图像”是两个时间点：注册只让设备节点出现，真正取帧还要经过后续 ioctl 和 buffer 完成链。

## Source Insight 精确入口与大白话解释

先在 `drivers/media/platform/rockchip/isp/capture.c` 看注册期对象赋值，再到 `drivers/media/v4l2-core/v4l2-dev.c` 看文件入口，最后在 `drivers/media/v4l2-core/v4l2-ioctl.c` 看命令分发。大白话：注册期只是把三张“转接表”挂到 video_device；用户真正 open/ioctl 时，V4L2 Core 才沿函数指针逐级找到 RKISP 或 VB2。

## 本篇要回答什么

应用只拿到一个 `fd`，内核为什么能找到 RKISP 的格式函数和 VB2 队列函数？答案不在某一个函数里，而在“注册时挂表、运行时查表”的对象关系里。

白话：注册期像给柜台装好“总服务手册”和“业务手册”；运行期 `open/ioctl/mmap` 先找到柜台对象，再照表转接，不靠函数名猜驱动。

## Source Insight：先找赋值，再跟调用

| 查找目标          | 搜索式                                  | 调用类型              | 应记录的对象                                                      |
| ------------- | ------------------------------------ | ----------------- | ----------------------------------------------------------- |
| video node 组装 | `rkisp_register_stream_vdev`         | 直接调用              | `rkisp_stream`、`rkisp_vdev_node`、`video_device`、`vb2_queue` |
| 文件操作表         | `rkisp_fops`                         | 函数指针赋值            | `.open`、`.unlocked_ioctl`、`.mmap`                           |
| ioctl 业务表     | `rkisp_v4l2_ioctl_ops`               | 函数指针赋值            | `.vidioc_s_fmt_*` 与 `.vidioc_*buf/streamon`                 |
| 字符设备入口        | `v4l2_open`、`v4l2_ioctl`、`v4l2_mmap` | VFS 直接进入 V4L2，再回调 | `video_devdata(file)` 得到的 `vdev`                            |
| 通用 ioctl 分发   | `video_ioctl2`、`__video_do_ioctl`    | 直接调用 + 函数指针回调     | `v4l2_ioctls[]` 和 `vfd->ioctl_ops`                          |

函数指针的 Call Graph 往往不完整。比如 `v4l2_ioctl()` 源码只写 `vdev->fops->unlocked_ioctl(...)`，真正目标 `video_ioctl2` 要从 `rkisp_fops` 的赋值反推。

## 1. 注册期：一个 video_device 挂三条边

`capture.c::rkisp_register_stream_vdev()` 中的关键关系是：

```c
vdev->ioctl_ops = &rkisp_v4l2_ioctl_ops;
vdev->fops = &rkisp_fops;
vdev->queue = &node->buf_queue;
video_set_drvdata(vdev, stream);
video_register_device(vdev, VFL_TYPE_GRABBER, -1);
```

对象含义：

- `struct video_device`：一个 V4L2 video node 的内核对象，保存设备名、minor、锁、能力、两张操作表和队列指针。
- `struct v4l2_file_operations`：`open/release/unlocked_ioctl/poll/mmap` 这类“文件行为”函数表。
- `struct v4l2_ioctl_ops`：`VIDIOC_*` 这类“视频业务”函数表。
- `struct vb2_queue`：这个节点的 buffer 集合、内存模型、状态链表、等待队列及驱动回调表。
- `video_set_drvdata(vdev, stream)`：让 `video_drvdata(file)` 能从当前 node 找回所属 `rkisp_stream`。

为什么分两张 V4L2 表：文件系统只认识少数 file operations，而 V4L2 有大量可选业务命令；拆开后 V4L2 Core 能统一接收系统调用，又能按设备能力选择性暴露 `vidioc_*`。

这段能证明对象关联在注册前已建立；不能证明 `/dev/videoX` 一定是 `/dev/video0`，minor 由注册结果和系统枚举决定，也不能证明 pipeline 已能出帧。

## 2. open：从 inode/file 找到同一个 vdev

```text
用户 open("/dev/videoX")
  → VFS 的 video_fops.open = v4l2_open()
  → video_devdata(file) 得到 struct video_device
  → vdev->fops->open(file)                     [函数指针回调]
  → rkisp_fh_open(file)
  → v4l2_fh_open(file) + v4l2_pipeline_pm_use(..., 1)
```

这里有两层 file operations，容易混淆：VFS 注册的是 V4L2 Core 的 `video_fops`，它先找到具体 `video_device`；`video_device.fops` 才是 RKISP 注册的 `rkisp_fops`。`file->private_data` 随后保存本次打开对应的 `v4l2_fh`，用于优先级、事件和 queue owner 等每文件上下文。

`open` 成功能证明 node 未注销、RKISP open 回调和 pipeline PM use 返回成功；不能证明 `S_FMT` 会接受目标 FourCC，更不能证明 DMA 已启动。

## 3. ioctl 第一跳：file_operations 只负责进总入口

```c
static const struct v4l2_file_operations rkisp_fops = {
    .open = rkisp_fh_open,
    .release = rkisp_fop_release,
    .unlocked_ioctl = video_ioctl2,
    .poll = vb2_fop_poll,
    .mmap = vb2_fop_mmap,
};
```

```text
sys_ioctl(fd, cmd, user_arg)
  → v4l2_ioctl(file, cmd, arg)
  → vdev->fops->unlocked_ioctl(file, cmd, arg)   [函数指针回调]
  → video_ioctl2(file, cmd, arg)
```

`video_ioctl2()` 不是每条命令的实现。它直接调用：

```c
video_usercopy(file, cmd, arg, __video_do_ioctl);
```

`video_usercopy` 负责用户/内核地址空间边界：按 `_IOC_SIZE/_IOC_DIR` 复制主参数；对 mplane 的 `QUERYBUF/QBUF/DQBUF`，`check_array_args()` 还复制 `v4l2_buffer.m.planes` 指向的 `v4l2_plane[]`。然后它调用作为参数传入的 `__video_do_ioctl`。整帧像素不经过这次 `copy_from_user/copy_to_user`；MMAP 模式只复制控制结构，图像留在映射的 buffer 内存。

这一步能证明参数经过 V4L2 用户拷贝框架；不能证明参数语义已经被驱动接受。

## 4. ioctl 第二、三跳：cmd 表与驱动表

`v4l2-ioctl.c` 有一张全局命令描述表：

```c
IOCTL_INFO(VIDIOC_S_FMT,    v4l_s_fmt,    ...)
IOCTL_INFO(VIDIOC_REQBUFS,  v4l_reqbufs,  ...)
IOCTL_INFO(VIDIOC_QUERYBUF, v4l_querybuf, ...)
IOCTL_INFO(VIDIOC_QBUF,     v4l_qbuf,     ...)
IOCTL_INFO(VIDIOC_DQBUF,    v4l_dqbuf,    ...)
IOCTL_INFO(VIDIOC_STREAMON, v4l_streamon, ...)
```

`__video_do_ioctl()` 先执行：

```c
ops = vfd->ioctl_ops;
info = &v4l2_ioctls[_IOC_NR(cmd)];
ret = info->func(ops, file, fh, arg);
```

这是第一张“cmd → V4L2 包装函数”表。包装函数检查 buffer type、优先级和字段后，再执行 `ops->vidioc_*`；这是第二张“统一业务字段 → 本设备回调”表：

| 命令                | `v4l2_ioctls[]` 包装函数 | `rkisp_v4l2_ioctl_ops` 最终字段    | 最终实现                         |
| ----------------- | -------------------- | ------------------------------ | ---------------------------- |
| `VIDIOC_S_FMT`    | `v4l_s_fmt`          | `.vidioc_s_fmt_vid_cap_mplane` | `rkisp_s_fmt_vid_cap_mplane` |
| `VIDIOC_REQBUFS`  | `v4l_reqbufs`        | `.vidioc_reqbufs`              | `vb2_ioctl_reqbufs`          |
| `VIDIOC_QUERYBUF` | `v4l_querybuf`       | `.vidioc_querybuf`             | `vb2_ioctl_querybuf`         |
| `VIDIOC_QBUF`     | `v4l_qbuf`           | `.vidioc_qbuf`                 | `vb2_ioctl_qbuf`             |
| `VIDIOC_STREAMON` | `v4l_streamon`       | `.vidioc_streamon`             | `vb2_ioctl_streamon`         |
| `VIDIOC_DQBUF`    | `v4l_dqbuf`          | `.vidioc_dqbuf`                | `vb2_ioctl_dqbuf`            |

为什么要两级分发：命令编号的解码、公共检查与参数打印只写一次；设备差异留给 `v4l2_ioctl_ops`。这也解释了“谁调用”：应用不直接调用 `vb2_ioctl_qbuf`，而是系统调用经 V4L2 Core 的两级函数指针回调到它。

## 5. S_FMT 到底改变了什么

```text
VIDIOC_S_FMT
  → v4l_s_fmt()
  → ops->vidioc_s_fmt_vid_cap_mplane()
  → rkisp_s_fmt_vid_cap_mplane()
  → 若 vb2 queue 正在 streaming：-EBUSY
  → rkisp_set_fmt(stream, &f->fmt.pix_mp, false)
```

`rkisp_set_fmt()` 查 `capture_fmt`，钳制宽高，设置 `pixm->num_planes`，计算每个 API plane 的 `bytesperline/sizeimage`；非 TRY 且尚未启动时，把结果保存到 `stream->out_isp_fmt` 与 `stream->out_fmt`。所以状态改变在 RKISP 的 stream 格式对象，不在某个 `vb2_buffer`；此时还没有 `REQBUFS`，也没有 DMA 地址。

`S_FMT` 返回值和回填结构能证明驱动接受后的实际格式，包括可能被调整的宽高、`num_planes` 和 `sizeimage`；不能证明应用原请求被原样采用，不能证明内存已分配，也不能证明 sensor/ISP 输出内容正确。

## 调用类型速答

| 表达式 | 类型 | 白话 |
|---|---|---|
| `video_register_device(...)` | 直接调用 | RKISP 主动向框架注册 node |
| `vdev->fops = &rkisp_fops` | 对象关联/函数表赋值 | 把文件行为表挂到 node |
| `vdev->fops->unlocked_ioctl(...)` | 函数指针回调 | V4L2 Core 运行时调用当前驱动填的入口 |
| `video_usercopy(..., __video_do_ioctl)` | 直接调用并传函数指针 | 通用复制器处理边界后再调用分发器 |
| `info->func(...)` | 命令表回调 | cmd 选择公共包装函数 |
| `ops->vidioc_qbuf(...)` | 驱动业务表回调 | 公共包装函数选择当前 node 的 QBUF 实现 |

## 本篇证据边界

看到 `rkisp_v4l2_ioctl_ops` 的赋值，能证明“若命令到达并通过公共检查，将调用哪个实现”；不能证明运行时真的调用过。`strace -e openat,ioctl,mmap` 能证明应用发过系统调用和返回码；不能单独证明内核中间经过了哪一条函数指针，需要 ftrace、tracepoint、dynamic debug、断点或源码结构共同佐证。

## 面试问题

`.unlocked_ioctl = video_ioctl2` 是否意味着所有 `VIDIOC_*` 都由 `video_ioctl2` 实现？

**我的回答：**

>

<mark>高亮正确答案：不是。`video_ioctl2` 只把用户参数交给 `video_usercopy` 和 `__video_do_ioctl`；后者用 `v4l2_ioctls[]` 选公共包装函数，再由包装函数通过当前 `video_device.ioctl_ops` 回调 RKISP 或 VB2。它是通用分发入口，不是所有命令的硬件实现。</mark>
