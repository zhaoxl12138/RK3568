## 先把“用户态取流”讲清楚

第 08 阶段研究的不是新的 Camera 硬件，而是应用程序如何使用 Linux 已经创建好的 /dev/videoX。它位于整条链路的最末端：

```text
Sensor / D-PHY / CSI / ISP
        ↓ 产生并处理图像
DMA 把一帧写入内核 buffer
        ↓
VB2 把 buffer 标为 DONE
        ↓
应用通过 DQBUF 取回这一帧
```

这里要分清三类接口：

```text
Media Controller  = 查看/配置媒体管线连接关系
V4L2 ioctl        = 应用向 video node 发出的控制命令
VB2               = 内核中管理 buffer 生命周期和 DMA 交接的框架
```

所以 `open("/dev/video0")` 不是打开 Sensor 的 I2C 文件，`VIDIOC_STREAMON` 也不是简单地把一个布尔变量改成 true。它们会经过 V4L2 Core、驱动的 ioctl 表、VB2 队列和 RKISP 的启动路径，最终触发上游管线和硬件。

本阶段的最小目标是能解释：应用为什么要先设置格式、申请 buffer、映射 buffer、QBUF，再 STREAMON，最后通过 DQBUF 等待 DMA 完成。

> 目标不是背七个 ioctl，而是从一个 `fd` 连续追到一个被 DMA 写完、最终能被 `DQBUF` 取走的 `vb2_buffer`。

## 先记住一条完整主线

```text
open("/dev/videoX")
  → V4L2 字符设备层 v4l2_open()
  → vdev->fops->open()                           [函数指针回调]
  → rkisp_fh_open()

ioctl(fd, VIDIOC_*)
  → v4l2_ioctl()
  → vdev->fops->unlocked_ioctl = video_ioctl2   [函数指针回调]
  → video_usercopy(..., __video_do_ioctl)        [直接调用 + 回调参数]
  → __video_do_ioctl()
  → v4l2_ioctls[cmd].func()                      [命令分发表]
  → vdev->ioctl_ops->vidioc_*()                  [函数指针回调]
  → RKISP 格式回调，或 vb2_ioctl_* 通用回调
  → vb2_*() → vb2_core_*()                       [直接调用]
  → q->ops->buf_queue/start_streaming()          [函数指针回调]
  → RKISP 把 DMA 地址写入硬件并启动 pipeline
  → RKISP MI 帧结束中断 → mi_frame_end()
  → vb2_buffer_done(DONE)
  → done_list + done_wq
  → vb2_core_dqbuf() → DQBUF 返回用户态
```

大白话：`video_device` 是 `/dev/videoX` 背后的“柜台对象”，两张 V4L2 函数表决定柜台把业务转给谁；`vb2_queue` 是这个节点的“周转箱系统”，`vb2_ops` 决定周转箱怎样交给 RKISP 硬件。应用提交空箱，RKISP/DMA 装帧，驱动宣布装完，VB2 才允许应用领回。

## 四个对象怎样关联

```text
rkisp_stream
  └─ rkisp_vdev_node
      ├─ video_device vdev
      │   ├─ fops      ──→ rkisp_fops : struct v4l2_file_operations
      │   ├─ ioctl_ops ──→ rkisp_v4l2_ioctl_ops : struct v4l2_ioctl_ops
      │   └─ queue     ──→ node->buf_queue
      └─ vb2_queue buf_queue
          ├─ drv_priv  ──→ rkisp_stream
          ├─ ops       ──→ rkisp_vb2_ops : struct vb2_ops
          └─ mem_ops   ──→ dma-contig 或 dma-sg 分配器操作表
```

这些不是“函数作用”的描述，而是注册期建立的对象关系：

- `capture.c` 的 `rkisp_register_stream_vdev()` 给 `vdev->fops`、`vdev->ioctl_ops`、`vdev->queue` 赋值，再直接调用 `video_register_device()`。
- `capture_v21.c` 的 `rkisp_init_vb2_queue()` 给 `q->drv_priv`、`q->ops`、`q->mem_ops` 赋值，再直接调用 `vb2_queue_init()`。
- 运行时框架只持有通用对象指针；需要硬件行为时，再通过函数指针回调 RKISP。为什么这样设计：V4L2/VB2 可以复用参数检查、锁、队列和状态机，具体驱动只实现设备差异。

## 七步取流与状态速查

| 用户动作       | 实际入口                                            | 主要对象/状态变化                                                                                     |
| ---------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `S_FMT`    | `rkisp_s_fmt_vid_cap_mplane()`                  | 校验并写 `stream->out_fmt/out_isp_fmt`；不分配 buffer                                                 |
| `REQBUFS`  | `vb2_ioctl_reqbufs()` → `vb2_core_reqbufs()`    | 调 `queue_setup`、分配 `q->bufs[]`，设置 `q->num_buffers/memory` 和 queue owner；buffer 初始为 `DEQUEUED` |
| `QUERYBUF` | `vb2_ioctl_querybuf()` → `vb2_core_querybuf()`  | 把 plane 的 `length/mem_offset` 填给应用；buffer 状态不变                                                |
| `mmap`     | `v4l2_mmap()` → `vb2_fop_mmap()` → `vb2_mmap()` | 建立用户 VMA 到已分配 plane 的映射；buffer 状态不变                                                           |
| `QBUF`     | `vb2_ioctl_qbuf()` → `vb2_core_qbuf()`          | 首次准备经过 `PREPARING/PREPARED`，随后进入 `QUEUED`；若驱动已开流则立刻进入 `ACTIVE`                                |
| `STREAMON` | `vb2_ioctl_streamon()` → `vb2_core_streamon()`  | 满足条件时，先把已排队 buffer 变为 `ACTIVE` 并回调 `buf_queue`，再回调 `start_streaming`，最后 `q->streaming = 1`    |
| `DQBUF`    | `vb2_ioctl_dqbuf()` → `vb2_core_dqbuf()`        | 等 `done_list`；取出 `DONE/ERROR`，复制元数据，最终回到 `DEQUEUED`                                           |

## 证据边界

- `open` 成功能证明字符设备和 open 回调可走通；不能证明格式、buffer 或 DMA 正常。
- `S_FMT` 成功能证明驱动接受并回写了某组格式；不能证明硬件已经按该格式产帧。
- `REQBUFS/QUERYBUF/mmap` 成功能证明队列内存建立且可映射；不能证明 DMA 写过它。
- `QBUF` 成功能证明 VB2 接受了 buffer；开流前它可能仍只是 `QUEUED`，不能证明驱动已经持有它。
- `STREAMON` 成功能证明启动路径成功返回；不能证明已经发生帧结束中断。
- 成功 `DQBUF` 且有合理的 `bytesused/sequence/timestamp`，能证明驱动向 VB2 完成了一个 buffer；不能单独证明画面颜色、曝光、帧连续性或物理内存连续。

## 面试问题与自测

为什么 `vb2_buffer_done()` 不是用户态 `DQBUF` 的直接下半段？

**我的回答：**

>

<mark>高亮正确答案：两者通常处在不同执行上下文。RKISP 的帧结束中断路径确认 DMA 完成后调用 `vb2_buffer_done()`，它把 ACTIVE buffer 放进 `done_list` 并唤醒 `done_wq`；用户进程中的 `DQBUF` 之后才从该队列取走它。中间的完成队列解耦了异步硬件和同步/阻塞的系统调用。</mark>
