# VB2 对象、Buffer 状态与 DMA 完成链

## 本篇边界：一个 buffer 的三次换手

把状态先按“谁拥有它”读，而不是先记 ioctl 名称：

```text
应用拥有：DEQUEUED，应用可填写参数或在 DQBUF 后读取帧
驱动/DMA 拥有：PREPARED → QUEUED → ACTIVE，硬件正在等待或写入
已完成待应用领取：DONE / ERROR，位于 done_list，DQBUF 才会取走
```

本篇只追 `vb2_queue`、状态变化、`rkisp_buf_queue()`、帧结束 IRQ 和
`vb2_buffer_done()`；注册期的 `fops/ioctl_ops` 挂表回到
[[02-源码陪读/08-V4L2用户态取流/01-生命周期|01-生命周期]]。

## 先用“周转箱”理解 VB2

`VB2` 是 `Videobuf2` 的缩写，是 Linux V4L2 中通用的 buffer 管理框架。它不负责理解 IMX415 的寄存器，也不负责做 ISP 算法；它只负责管理“哪块内存属于谁、当前处于什么状态、什么时候可以交给硬件、什么时候可以交还应用”。

```text
应用准备空 buffer
    ↓ QBUF
VB2 把 buffer 交给驱动/DMA
    ↓
硬件写入图像
    ↓ 中断
驱动调用 vb2_buffer_done(DONE)
    ↓
应用 DQBUF 取回已完成 buffer
```

因此 `QBUF` 不等于“已经有图”，`vb2_buffer_done()` 也不等于应用已经执行了 `DQBUF`。前者是交付，后者是内核宣布完成，真正取回还要经过完成队列和等待唤醒。

## Source Insight 精确入口与大白话解释

VB2 通用状态机在 `drivers/media/common/videobuf2/videobuf2-core.c`，V4L2 参数适配在 `drivers/media/common/videobuf2/videobuf2-v4l2.c`，RKISP 的队列与中断交接在 `drivers/media/platform/rockchip/isp/capture_v21.c`。大白话：VB2 管“箱子归谁、排在哪、谁能领取”，RKISP 管“把哪只箱子的 DMA 地址交给硬件、什么时候确认装帧完成”。

## 白话总览

`vb2_queue` 是一套周转箱账本；`vb2_buffer` 是一个箱子的内核状态；`v4l2_buffer/v4l2_plane[]` 是应用交单和领单时使用的 API 表格；`rkisp_buffer` 在 `vb2_v4l2_buffer` 外再包一层，保存 RKISP 私有链表节点和 DMA 地址。

驱动何时得到 buffer，不等于应用何时 QBUF：VB2 先把它记为 `QUEUED`，只有 `__enqueue_in_driver()` 把状态改成 `ACTIVE` 并回调 `q->ops->buf_queue` 时，RKISP 才得到可编程给 DMA 的 buffer。驱动完成 DMA 后调用 `vb2_buffer_done()`；它不是 DQBUF，而是让未来的 DQBUF 有东西可取。

## queue 怎样连接到 RKISP

```c
q->type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE;
q->io_modes = VB2_MMAP | VB2_USERPTR | VB2_DMABUF;
q->drv_priv = stream;
q->ops = &rkisp_vb2_ops;
q->mem_ops = stream->ispdev->hw_dev->mem_ops;
q->min_buffers_needed = CIF_ISP_REQ_BUFS_MIN;
q->dma_attrs = DMA_ATTR_FORCE_CONTIGUOUS; /* 仅 is_dma_contig 时 */
vb2_queue_init(q);
```

`q->drv_priv` 让驱动回调从通用 queue 找回 `rkisp_stream`；`q->ops` 是 VB2 调驱动的行为表；`q->mem_ops` 是 VB2 调分配器的内存表。为什么这样设计：buffer 状态机不应复制到每个驱动，物理内存实现也不应写死在状态机里。

本树 `capture_v21.c` 的 `CIF_ISP_REQ_BUFS_MIN` 实际定义为 `0`。因此能证明的通用逻辑是 `vb2_core_streamon()` 按 `q->min_buffers_needed` 判定；不能把别的驱动“至少 N 个”的值强套到这里。应用仍应先 QBUF 再 STREAMON，因为真实 buffer 会在启动前交给 RKISP；无可用 buffer 时这份驱动可能使用 dummy buffer 并统计丢帧，STREAMON 成功不代表用户 buffer 已完成。

## 七步状态逐行追踪

### 1. S_FMT：格式对象改变，buffer 尚不存在

`rkisp_s_fmt_vid_cap_mplane()` 调 `rkisp_set_fmt(..., false)`，设置 `stream->out_fmt`、`stream->out_isp_fmt`，并把实际 `num_planes/bytesperline/sizeimage` 回填。正在 streaming 时返回 `-EBUSY`。

能证明：驱动接受后的格式布局。不能证明：REQBUFS 已分配内存或 DMA 已配置。

### 2. REQBUFS：建立 buffer 池

```text
vb2_ioctl_reqbufs(file, ..., req)
  → video_devdata(file)->queue
  → 检查 queue owner
  → vb2_core_reqbufs(q, memory, &count)
  → q->memory = memory
  → q->ops->queue_setup(...)                    [函数指针回调]
  → __vb2_queue_alloc(...)
  → q->num_buffers = allocated_buffers
  → q->waiting_for_buffers = true               [capture queue]
  → vdev->queue->owner = file->private_data
```

新建 `vb2_buffer` 初始可由用户掌控，表现为 `DEQUEUED`。`REQBUFS(0)` 是释放路径，也会清除 owner。`owner` 防止另一个 file handle 抢同一 queue。

能证明：分配器成功建立了规定数量和 plane 数的 buffer。不能证明：用户已获得映射，驱动已拿到 buffer，或 buffer 物理连续。

### 3. QUERYBUF：只把账本信息交给应用

`vb2_ioctl_querybuf()` 直接调用 `vb2_querybuf()`/`vb2_core_querybuf()`，由 `fill_user_buffer` 填 `v4l2_buffer` 和每个 `v4l2_plane` 的 `length`、MMAP `mem_offset`、flags 等。状态不变，仍是 `DEQUEUED`。

能证明：指定 index/plane 存在，并取得后续 mmap 所需 offset。不能证明：已经建立 VMA，更不能证明硬件写过内存。

### 4. mmap：建立 CPU 用户虚拟地址映射

```text
mmap(fd, ..., offset)
  → v4l2_mmap()
  → vdev->fops->mmap = vb2_fop_mmap             [函数指针回调]
  → vb2_mmap(vdev->queue, vma)
  → vb2_core_mmap()/q->mem_ops->mmap             [内存操作表回调]
```

MMAP 连接的是应用 VMA 与已分配 plane；不把整帧通过 ioctl 拷贝，也不改变 `vb2_buffer.state`。

能证明：CPU 侧映射建立成功。不能证明：DMA 侧地址是物理连续、IOMMU 连续或 SG；这些要看 `q->mem_ops`、DMA API 返回和平台配置。

### 5. QBUF：先排 VB2 队列，再视时机交给驱动

首次 QBUF 的状态为：

```text
DEQUEUED
  → __buf_prepare(): PREPARING
  → 内存模型准备 + q->ops->buf_prepare（若实现）
  → PREPARED
  → 加入 q->queued_list，q->queued_count++
  → QUEUED
```

随后分两种情况：

- 尚未调用驱动 start：保持 `QUEUED`，等 `vb2_start_streaming()` 扫 `queued_list`。
- `q->start_streaming_called == 1`：马上调用 `__enqueue_in_driver()`，状态变 `ACTIVE`，`owned_by_drv_count++`，然后函数指针回调 `q->ops->buf_queue(vb)`。

RKISP 的 `rkisp_buf_queue()` 把 `vb2_buffer` 转成外层 `rkisp_buffer`，通过 dma-contig 或 dma-sg helper 取得每个 memory plane 的 DMA 地址，再放进 `stream->buf_queue`。所以“驱动得到 buffer”的可验证边界是 `rkisp_buf_queue()` 被调用，不只是 QBUF 返回成功。

### 6. STREAMON：先交 buffer，再启动硬件

```text
vb2_ioctl_streamon
  → vb2_streamon
  → vb2_core_streamon
      检查 type、q->num_buffers、q->min_buffers_needed
      若 queued_count 达标：vb2_start_streaming(q)
        → 对 queued_list 中每个 buffer 调 __enqueue_in_driver()
          → ACTIVE → q->ops->buf_queue() → rkisp_buf_queue()
        → q->start_streaming_called = 1
        → q->ops->start_streaming(q, owned_count)
          → rkisp_start_streaming()
      q->streaming = 1
```

`rkisp_start_streaming()` 从 `queue->drv_priv` 找回 stream，检查 link/input，开 power/clock，配置 MI，启动 subdev/pipeline。调用失败时驱动必须把已经 ACTIVE 的 buffer 以 `QUEUED` 交回 VB2，否则 Core 会告警并强制回收。

为什么先 `buf_queue` 后 `start_streaming`：驱动启动 DMA 前必须先知道可写地址，避免硬件开始产数据却没有目标。能证明：STREAMON 返回 0 表示这条启动调用链成功返回。不能证明：DMA 已完成任何一帧，也不能证明 `q->streaming` 的置位时刻等于硬件首帧时刻。

### 7. 帧完成与 DQBUF：完成生产者唤醒等待消费者

在这份 RKISP v2.1 路径中：

```text
MI frame-end IRQ
  → rkisp_mi_v21_isr(mis_val, dev)
  → mi_frame_end(stream)
  → 给 curr_buf 塞 payload、sequence、timestamp
  → vb2_buffer_done(vb2_buf, VB2_BUF_STATE_DONE)
      要求旧状态是 ACTIVE
      → list_add_tail(..., q->done_list)
      → vb->state = DONE
      → owned_by_drv_count--
      → wake_up(&q->done_wq)
```

谁调用 `vb2_buffer_done`：不是 V4L2 Core 凭空知道 DMA 完成，而是掌握硬件完成条件的 RKISP 驱动；正常 capture 路径由 MI 帧结束中断中的 `mi_frame_end()` 调用，停流/失败清理也可能用 `ERROR/QUEUED` 状态调用。

`DQBUF` 为什么可返回：

```text
vb2_core_dqbuf()
  → __vb2_get_done_vb()
    → 阻塞模式在 done_wq 睡眠，条件包含 done_list 非空
    → 非阻塞模式无完成项则返回 -EAGAIN
    → 从 done_list 取第一个 DONE/ERROR buffer
  → q->ops->buf_finish（若实现）
  → fill_user_buffer：回填 index/bytesused/sequence/timestamp
  → 从 queued_list 删除，queued_count--
  → __vb2_dqbuf(): state = DEQUEUED
```

`vb2_buffer_done()` 的 `list_add_tail + wake_up` 正是 DQBUF 能结束等待的因果证据。DQBUF 返回后所有权回到应用，应用读完必须再次 QBUF 才能循环采集。

## NV12：三个“plane”层次必须拆开

| 层次 | NV12 的含义 | 本树证据 |
|---|---|---|
| 颜色 component plane | Y 与 UV 交错，共 2 个颜色分量区域 | `capture_fmt.cplanes = 2` |
| V4L2 API plane / memory plane | `v4l2_plane[]` 中有几个可独立分配/映射的内存对象 | `V4L2_PIX_FMT_NV12` 的 `mplanes = 1`；`V4L2_PIX_FMT_NV12M` 的 `mplanes = 2` |
| DMA 物理布局 | 每个 memory plane 背后是单段、SG 列表还是 IOMMU 映射后的连续 IOVA | 由 `q->mem_ops`、`is_dma_sg_ops/is_dma_contig` 和 DMA API 决定 |

因此 `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE` 只说明 API 使用 `v4l2_pix_format_mplane` 与 `v4l2_buffer.m.planes`，不保证 `num_planes > 1`。在本树中，普通 `V4L2_PIX_FMT_NV12` 是一个 API plane：`plane_fmt[0].sizeimage` 是 Y+UV 总大小，RKISP 用 `Y DMA 地址 + bytesperline * height` 推导 UV 地址；`V4L2_PIX_FMT_NV12M` 才是两个 API plane，各自给 DMA 地址。

API plane 数不能证明物理连续性：一个 API plane 在 dma-sg 后端可以由多个物理页组成，却给设备连续 DMA/IOVA 视图；两个 API plane 也可能分别连续，但彼此不相邻。本树只有 `is_dma_contig` 时设置 `DMA_ATTR_FORCE_CONTIGUOUS`，同时又支持 dma-sg 分支。必须查实际 `mem_ops` 和平台 DMA/IOMMU 配置，不能由 NV12 或 mplane 名字下结论。

对 3840×2160 8-bit NV12，`width * height * 3 / 2 = 12,441,600` 只是无 stride/padding 的理论有效量。验收应以 `S_FMT/G_FMT` 返回的每 plane `bytesperline/sizeimage` 和 DQBUF 的 `bytesused` 为准。

## 本篇证据边界

- 看见 `ACTIVE → DONE`、加入 `done_list` 并唤醒 `done_wq`，能证明 VB2 的完成协议；不能单靠 Core 源码证明哪个 RKISP IRQ 位代表目标 stream，需继续看 `rkisp_mi_v21_isr` 的 `mis_val/frame_end_id`。
- 看见 RKISP 在 `mi_frame_end()` 调 `vb2_buffer_done(DONE)`，能证明软件把该 buffer 宣告完成；不能独立证明 DMA 写入内容没有硬件错误，需结合 IRQ/error status、payload 和图像检查。
- DQBUF 成功能证明一个完成项穿过 VB2 返回；不能证明 NV12 的颜色解释、曝光、连续 30 帧无丢帧或底层物理连续。

## 面试问题

QBUF 返回成功后，buffer 一定已归驱动 DMA 所有吗？

**我的回答：**

>

<mark>高亮正确答案：不一定。`vb2_core_qbuf()` 先把它变成 `QUEUED`；只有 `__enqueue_in_driver()` 把它改为 `ACTIVE` 并通过 `q->ops->buf_queue` 回调 RKISP 后，才算交给驱动。未开流时通常等 STREAMON 才交；已开流时 QBUF 可立即触发这一步。</mark>
