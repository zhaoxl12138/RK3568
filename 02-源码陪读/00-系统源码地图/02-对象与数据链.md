# 00-02 对象与数据链：不要把“软件对象”当成“图像经过”

## Source Insight 定位

| 观察对象 | 文件 | 搜索符号 |

## 三张图必须分开

### 1. 控制流

```text
用户/框架请求 → V4L2 ops → IMX415 驱动 → I2C 寄存器读写
```

### 2. 图像数据流

```text
IMX415 RAW10 → MIPI Lane → D-PHY → CSI-2 Receiver
              → RKISP → mainpath → VB2 buffer → /dev/video0
```

### 3. 软件对象关系

```text
struct imx415
 ├─ client ───────────→ struct i2c_client
 ├─ subdev.entity ────→ struct media_entity
 └─ pad[Source] ─link→ D-PHY pad[Sink]
```

Media Link 表示拓扑关系，不是图像内存拷贝函数；I2C client 保存 Sensor 控制档案，也不承载 RAW 帧。

## 带注释代码

```c
struct imx415 {
    struct i2c_client *client;  // 对象关系：以后通过它做 I2C 控制
    struct v4l2_subdev subdev;  // 包含关系：IMX415 在 Camera 框架中的身份
    struct media_pad pad;       // 数据端口描述：Sensor 只有 Source Pad
};

sd = &imx415->subdev;           // 字段取地址，不是注册，也不是开流
v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops); // 直接调用：组装对象关系
```

### C 基础：包含、指针和取地址

`subdev` 直接嵌在 `struct imx415` 里，属于**包含关系**；`client` 是指针，指向另一个对象。`&imx415->subdev` 只是取得成员地址，不会自动执行该对象的 ops。

## 调用类型检查

- `sd = &imx415->subdev`：字段赋值和对象关系。
- `v4l2_i2c_subdev_init(...)`：直接调用。
- `sd->ops = ops`：保存函数表地址。
- 以后框架调用 `sd->ops->video->s_stream(...)`：函数指针框架回调。
- RAW10 从 Lane 进入 RKISP：硬件数据链，不是上述 C 函数的参数传递。

## 大白话解释

同一颗 IMX415 在不同系统里有不同“证件”：I2C client 是总线档案，`struct imx415` 是驱动私有工作台，V4L2 subdev 是 Camera 框架证件，Media Entity/Pad 是拓扑图里的方框和端口。证件之间互相引用，但 RAW 图像走的是 MIPI 硬件数据通道。

## 板端证据边界

```bash
ls -l /dev/v4l-subdev*
media-ctl -p
v4l2-ctl -d /dev/video0 --all
```

- `/dev/v4l-subdev3` 能证明 Sensor subdev 节点存在，不能证明它是取帧节点。
- `[ENABLED]` Link 能证明运行时拓扑建立，不能证明 Lane 上正在传有效包。
- `/dev/video0` 能证明 video_device 已注册，不能单独证明 STREAMON 能得到正确帧。

## 面试问题

为什么 `/dev/v4l-subdev3` 不能像 `/dev/video0` 一样直接读取图像？

**我的回答：**


<mark>高亮正确答案：subdev 主要表示并控制流水线内部模块，保存格式、控制和开停流等 ops；最终承载帧缓冲队列的是 RKISP 注册的 video node，应用通过 /dev/video0 和 VB2 队列取帧。</mark>
