## 三段生命周期

```text
阶段 A：描述变对象
DTB → unflatten_device_tree() → device_node
    → platform_device 或 i2c_client

阶段 B：驱动登记
initcall → *_driver_register() → driver_register()

阶段 C：汇合
driver_match_device() → really_probe()
    → bus->probe() → 具体驱动 probe()
```

设备支线和驱动支线不是彼此直接调用，而是都加入同一条 bus 的对象集合。后到的一方触发扫描。

## 代码片段与调用类型

```c
static int really_probe(struct device *dev, struct device_driver *drv)
{
    dev->driver = drv;               // 对象关系：设备记住匹配到的驱动

    if (dev->bus->probe)
        ret = dev->bus->probe(dev);  // I2C 等总线可在 bus_type 中提供统一入口
    else if (drv->probe)
        ret = drv->probe(dev);       // Platform 把 platform_drv_probe 挂在通用 driver 上
}
```

| 代码 | 调用类型 | 含义 |
|---|---|---|
| `dev->driver = drv` | 字段赋值/对象关系 | 把匹配结果保存在设备对象里 |
| `really_probe(...)` | Driver Core 的直接调用 | match 成功后进入真正绑定 |
| `dev->bus->probe(dev)` | 函数指针/框架回调 | I2C 路径进入 `i2c_device_probe()` |
| `drv->probe(dev)` | 函数指针/框架回调 | Platform 路径先进入通用层保存的 `platform_drv_probe()` |
| `driver->probe(client, id)` | 总线框架回调厂商驱动 | 最终进入 IMX415 probe |

### C 基础：`->` 和函数指针

`dev->bus` 等价于 `(*dev).bus`；`dev->bus->probe` 是从 `dev` 找到 bus，再取 bus 中保存的函数指针。`dev->bus->probe(dev)` 才执行该函数。

## 大白话解释

内核启动不是一列只能按固定车次前进的火车，更像两个部门分别录入“设备”和“驱动”。一旦同一总线上两份资料都出现，通用驱动模型就做匹配；匹配成功后经总线包装入口，把正确参数转换给具体厂商的 `probe()`。

## 板端证据：能证明什么

```bash
cat /sys/bus/i2c/devices/4-001a-1/uevent
readlink -f /sys/bus/i2c/devices/4-001a-1/driver
dmesg | grep 'Detected imx415'
```

- client 目录能证明设备对象已创建。
- driver 符号链接能证明匹配和绑定成功。
- Sensor ID 日志能证明 `imx415_probe()` 已走到 I2C 读 ID。
- 这些都不能证明图像数据已穿过 D-PHY、CSI 和 RKISP。

## 面试问题

为什么在 `imx415.c` 里搜索不到谁直接调用 `imx415_probe()`？

**我的回答：**


<mark>高亮正确答案：因为它是函数指针回调。驱动把地址保存在 i2c_driver.probe；Driver Core 匹配后进入 really_probe()，再由 i2c_bus_type.probe 指向的 i2c_device_probe() 调用 driver->probe(client, id)。</mark>
