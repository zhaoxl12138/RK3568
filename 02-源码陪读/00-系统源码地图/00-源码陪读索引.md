## 总调用图：先分支，后汇合

```text
设备支线：DTB → device_node → platform_device / i2c_client ─┐
                                                              ├→ bus match → really_probe()
驱动支线：内核配置 → initcall → driver_register() ───────────┘
                                                              ↓
                                      具体 bus 的 probe 包装函数
                                                              ↓
                                                厂商驱动 probe()
                                                              ↓
                                           V4L2 / Media 对象注册
```

> [!important] 调用类型
> - `driver.probe = imx415_probe`：**字段赋值/函数指针保存**，没有执行函数体。
> - `i2c_add_driver(...)`：源码当前路径中的**直接调用**。
> - I2C Core 之后调用 `imx415_probe(...)`：**框架回调**。
> - `client->dev.of_node`：C 对象之间的**对象关系**。

## 代码片段：为什么 `.probe` 不是调用

```c
static struct i2c_driver imx415_i2c_driver = {
    .driver.of_match_table = imx415_of_match, // 保存匹配表地址
    .probe = imx415_probe,                    // 保存函数地址，不执行 probe
};

static int __init sensor_mod_init(void)
{
    return i2c_add_driver(&imx415_i2c_driver); // 直接调用：把整张登记表交给 I2C Core
}
```

### C 基础

结构体中的 `.probe = imx415_probe` 是**指定初始化器**；函数名在此处会转换为函数指针。只有出现 `imx415_probe(client, id)` 这种带括号的表达式，才是普通直接调用。

## 大白话解释

设备树像“设备档案”，驱动结构体像“工程师履历”。Linux 总线框架像人事系统：两份资料都到齐后按规则配对，配对成功才通知工程师去现场，也就是回调 `probe()`。Camera 数据不会因为登记完成就自动流动；还要完成 Subdev、Media Graph、ISP、缓冲队列和 STREAMON。

## 板端证据边界

```bash
test -d /sys/bus/i2c/devices/4-001a-1 && echo client-ok
readlink -f /sys/bus/i2c/devices/4-001a-1/driver
dmesg | grep -E 'imx415|csi2-dphy|rkisp'
media-ctl -p
```

- 能证明：对应的运行时对象、绑定或拓扑确实存在。
- 不能证明：单凭某一条输出就证明 Sensor、MIPI、ISP、缓冲区和画质全部正常。

## 面试问题

Camera 启动是不是严格按照“先注册设备、再注册驱动”的单线程顺序执行？

**我的回答：**


<mark>高亮正确答案：不是。设备和驱动可以按不同 initcall 顺序到达；哪一方后到，框架都会在双方同时存在时尝试 match。真正需要记住的是两条支线在 bus match 和 really_probe() 汇合，而不是死背唯一时间顺序。</mark>
