## 二、箭头类型：完整生命周期不能只画一个 `→`

### 先记住五种箭头

| 标记 | 含义 | 例子 |
|---|---|---|
| `[赋值]` | 保存数据或函数地址，不执行回调 | `.probe = rockchip_csi2_dphy_hw_probe` |
| `[注册]` | 把 driver、subdev 或 notifier 交给框架管理 | `platform_driver_register()` |
| `[框架回调]` | 框架匹配成功后通过函数指针调用 | Platform 总线框架回调 `.probe` |
| `[直接调用]` | 当前函数源码里明确写出了被调用函数 | `probe()` 调用 `attach_hw()` |
| `[DTS引用]` | 描述对象关系，不是 C 函数调用 | `rockchip,hw = <&csi2_dphy_hw>` |

必须形成三个稳定结论：

> **函数指针赋值不是调用。** `.probe = fn` 和 `.bound = fn` 都只保存入口地址。

> **DTS 引用不是调用。** `compatible` 用于匹配，phandle 用于引用对象，DTS 本身不会主动执行驱动函数。

> **V4L2 Async 注册不阻塞。** 没匹配到 Sensor 时把条件放进 `waiting` 后返回；对象出现后再触发 `.bound()`。

## 三、对象关系验收：每一层到底保存了什么

### 1. 两个 Platform 对象

```text
HW DTS node
└─ HW platform_device
   └─ drvdata → struct csi2_dphy_hw
                ├─ regs / GRF / clocks
                ├─ stream_on / stream_off
                ├─ lane_mode
                └─ dphy_dev[] → 逻辑 D-PHY 实例

逻辑 DTS node：csi2_dphy0
└─ 逻辑 platform_device
   └─ 驱动创建 struct csi2_dphy
                    ├─ dev
                    ├─ dphy_hw ─────────→ struct csi2_dphy_hw
                    ├─ sd               V4L2 身份
                    │  └─ entity         Media Graph 节点
                    ├─ pads[0]           Sink
                    ├─ pads[1]           Source
                    ├─ notifier          等上游 Sensor
                    └─ sensors[]         bound 后保存真实 Sensor
```

关键点：`struct csi2_dphy` 不复制 HW 寄存器资源，只保存 `dphy_hw` 指针并复用物理对象的能力。

### 2. `sd`、`ops` 和 notifier

```text
sd = sub-device
ops = operations

dphy->sd.ops
└─ csi2_dphy_subdev_ops
   ├─ core  → 电源等基础回调
   ├─ video → 开流/停流、总线等回调
   └─ pad   → 格式和 selection 回调
```

`v4l2_subdev_init()` 的核心业务动作确实包括 `sd->ops = ops`，但 list、name、flags、entity type/function 等初始化保证它是一个合法、可注册、可进入 Media Graph 的框架对象。

```text
dphy->sd.subdev_notifier ──→ dphy->notifier
dphy->notifier.sd        ──→ dphy->sd
dphy->notifier.ops       ──→ bound / unbind 回调表
```

endpoint parser 决定“等谁”，notifier ops 决定“匹配后做什么”，notifier register 负责把等待关系交给 V4L2 Async。

### 3. `waiting` 和 `done`

```text
endpoint 解析后：
notifier->subdevs[] = IMX415 fwnode 匹配条件

notifier 注册且 IMX415 尚未出现：
waiting = [IMX415 匹配条件]
done    = []

IMX415 匹配成功后：
waiting = []
done    = [IMX415 subdev]
```

如果 IMX415 已经先注册，notifier register 会立即尝试匹配并可能在当前注册路径中调用 `.bound()`；如果 IMX415 尚未注册，登记 `waiting` 后函数返回，未来 IMX415 注册时再匹配。两种情况都不是睡眠或循环阻塞等待。

#### 1. 为什么要拆成 HW 对象和逻辑 D-PHY 对象？两个 probe 分别负责什么？

> [!question] 我的回答
> 从架构的角度考虑，HW 集中管理资源。逻辑层负责把 `csi2_dphy0/1/2` 表示成 Camera 管线中的 V4L2/Media 对象。

**判定：基本正确（约 85%）。** 已经抓住“物理资源层”和“Camera 逻辑层”的边界，还缺两个 probe 的具体职责。

> [!success] 高亮正确答案
> ==`HW probe` 负责初始化物理 D-PHY：取得并集中管理 MMIO 寄存器、时钟、GRF、Lane 模式和硬件开停能力，并把 `struct csi2_dphy_hw` 保存进 HW `platform_device` 的 `drvdata`。逻辑 D-PHY probe 负责为 `csi2_dphy0/1/2` 创建 `struct csi2_dphy`，关联已有 HW 对象，再初始化 V4L2 Subdev、Media Pads、Endpoint 和 Async Notifier。它们对应两个 DTS 节点、两个 `platform_device` 和两个对象，不是同一个设备重复 probe。==

面试短句：**HW 层管共享物理资源，逻辑层管 Camera 管线身份。**

#### 2. 逻辑 D-PHY 怎样从 `rockchip,hw` 取得 HW 对象？

> [!question] 我的回答
> `platform_get_drvdata()`。

**判定：方向正确，但只答了最后一步（约 60%）。** `platform_get_drvdata()` 本身不知道要取哪个设备，前面必须先根据 phandle 找到 HW 节点和对应的 `platform_device`。

> [!success] 高亮正确答案
> ==完整路径是：`of_parse_phandle(dev->of_node, "rockchip,hw", 0)` 取得 HW `device_node` → `of_find_device_by_node(np)` 找到 HW `platform_device` → `platform_get_drvdata(plat_dev)` 取回 HW probe 先前用 `platform_set_drvdata()` 保存的 `struct csi2_dphy_hw`。最后把该指针保存到逻辑对象的 `dphy->dphy_hw`。==

```text
rockchip,hw phandle
    → HW device_node
    → HW platform_device
    → platform_get_drvdata()
    → struct csi2_dphy_hw
```

#### 3. `v4l2_subdev_init()` 做了什么、没做什么？

> [!question] 我的回答
> 把 415 注册成 Camera 框架认识的节点。

**判定：当前回答不正确。** 这里调用的是 D-PHY 驱动中的 `v4l2_subdev_init()`，操作对象是 D-PHY 的 `sd`，不是 IMX415；而且 `init` 不等于向框架完成注册。

> [!success] 高亮正确答案
> ==`v4l2_subdev_init(sd, &csi2_dphy_subdev_ops)` 初始化 D-PHY 的 `struct v4l2_subdev`，并通过 `sd->ops = ops` 挂上回调能力，同时初始化 list、name、flags 和 Media Entity 的基础状态。它没有执行 ops、没有注册 IMX415、没有创建 Sensor→D-PHY Link，也没有把 D-PHY 正式注册进异步框架；后面的 `v4l2_async_register_subdev(&dphy->sd)` 才负责登记 D-PHY subdev。==

面试短句：**`v4l2_subdev_init()` 是“组装对象并挂能力表”，不是“执行能力”或“完成注册”。**

#### 4. 为什么 V4L2 Async 不是阻塞等待？

> [!question] 我的回答
> 驱动注册成功过会扫描 probe 一次。

**判定：混淆了 Platform probe 与 V4L2 Async 匹配。** Async 匹配的对象是已经注册或以后注册的 `v4l2_subdev`，不是反复扫描并执行设备的 probe。

> [!success] 高亮正确答案
> ==Notifier 注册时会先尝试匹配当前已经注册的 subdev：如果 IMX415 已存在，可以立即触发 `.bound()`；如果尚不存在，就把 IMX415 的 fwnode 匹配条件放入 `waiting`，然后函数立即返回。以后 IMX415 subdev 注册时，Async 框架再次做匹配，成功后把它移到 `done` 并回调 `.bound()`。整个过程没有循环等待、睡眠等待，也不会卡住 D-PHY probe。==

```text
IMX415 已注册：notifier register → 立即匹配 → bound
IMX415 未注册：notifier register → waiting → 立即返回
                                      ↓
                         IMX415 以后注册 → bound
```

#### 5. 精确读出 Sensor 到 D-PHY 的 Entity / Pad / Link

> [!question] 我的回答
> 1. IMX415 输出，SCI2。

**判定：方向正确，但对象和端口没有说完整。** `SCI2` 应为 `CSI-2`，但这行输出里真正的下游 Entity 名称是 `rockchip-csi2-dphy0`。排查 Media Graph 时必须保留 Entity、Pad 编号和方向。

> [!success] 高亮正确答案
> ==IMX415 Entity 的 `pad0 Source` 输出 RAW 图像数据，连接到 `rockchip-csi2-dphy0` Entity 的 `pad0 Sink`。Source 表示这一级的数据输出端，Sink 表示下一级的数据输入端。完整读法是：`IMX415 pad0 Source → rockchip-csi2-dphy0 pad0 Sink`。==

```text
m00_b_imx415 4-001a-1
    pad0 Source
         │
         │ Media Link
         ▼
rockchip-csi2-dphy0
    pad0 Sink
```

#### 6. `[ENABLED]` 能证明什么，不能证明什么？

> [!question] 我的回答
> 2. 开启该通道。
> 3. 不能证明该通道一定是通的。

**判定：核心方向正确，但“通道”太模糊。** `[ENABLED]` 描述的是 Media Controller 中的软件 Link 状态，不是对 MIPI 物理信号做出的测试结论。

> [!success] 高亮正确答案
> ==`[ENABLED]` 能证明：Sensor 与 D-PHY 之间的 Media Link 已经在软件拓扑中创建并处于启用状态。它不能证明：① IMX415 已执行 `s_stream(1)` 并真正输出数据；② MIPI Lane 上存在正确、稳定的物理信号；③两端格式、Lane 映射和时序一致；④没有 CRC/ECC/FIFO 错误；⑤图像已经经过 RKISP 到达 `/dev/video0`。==

面试时不要说“`[ENABLED]` 证明通道已经打通”，应说：

> **它只证明软件拓扑 Link 已建立并启用，不证明图像数据面已经正常。**

## 四、误区诊断：判断后必须说出理由

先自己判断，再看“纠正”。

### 误区 1：编译系统直接找到并执行 probe

**判断：错误。**

纠正：Kconfig/Makefile 决定是否编译；模块 init 注册 driver；总线框架根据 `compatible` 匹配 device/driver；匹配成功后才回调 `.probe`。

回看：[[02-源码陪读/04-DPHY/01-生命周期|生命周期：HW Driver 注册与 Probe]]。

### 误区 2：`.probe = rockchip_csi2_dphy_probe` 是调用函数

**判断：错误。**

纠正：这是结构体成员赋值，保存函数地址。真正调用发生在 Platform 总线框架完成匹配以后。

回看：[[02-源码陪读/04-DPHY/01-生命周期|生命周期：HW Driver 注册与 Probe]]。

### 误区 3：HW probe 直接调用逻辑 probe

**判断：错误。**

纠正：HW probe 直接调用的是 `platform_driver_register()`；逻辑 driver 注册后仍由 Platform 总线框架完成第二次匹配，再回调逻辑 probe。

回看：[[02-源码陪读/04-DPHY/01-生命周期|生命周期：逻辑 D-PHY Probe 与 Attach HW]]。

### 误区 4：`rockchip,hw` 会调用 HW 驱动

**判断：错误。**

纠正：它只是 phandle。逻辑 probe 通过 `device_node → platform_device → platform_get_drvdata()` 取得 HW probe 已保存的对象。

回看：[[02-源码陪读/04-DPHY/01-生命周期|生命周期：逻辑 D-PHY Probe 与 Attach HW]]。

### 误区 5：`v4l2_subdev_init()` 会把 ops 里的函数全部执行一遍

**判断：错误。**

纠正：它初始化 `v4l2_subdev` 并挂接 ops 表。未来 V4L2 管线收到具体请求时才调用相应回调。

回看：[[02-源码陪读/04-DPHY/02-对象与数据链|对象与数据链：V4L2 Subdev 与 Pads]]。

### 误区 6：`media_entity_pads_init()` 创建了 Sensor 到 D-PHY 的连接

**判断：错误。**

纠正：`pads_init` 建立 entity 对 pads 的所有权和编号，不创建 link；真正的软件边由 `.bound()` 中的 `media_create_pad_link()` 创建。

回看：[[02-源码陪读/04-DPHY/02-对象与数据链|对象与数据链：Subdev、Pads、Bound 与 Link]]。

### 误区 7：Async notifier 会阻塞 D-PHY probe，直到 IMX415 出现

**判断：错误。**

纠正：Async 是非阻塞、顺序无关的延迟绑定。没有匹配对象时进入 `waiting` 后返回；后注册的一方触发重新匹配。

回看：[[02-源码陪读/04-DPHY/02-对象与数据链|对象与数据链：Endpoint 与 Async Notifier]]。

### 误区 8：一定是 IMX415 后注册才会触发 `.bound()`

**判断：错误。**

纠正：IMX415 已存在时，注册 notifier 就可能立即匹配；IMX415 尚未出现时，才在其后续注册路径中匹配。

回看：[[02-源码陪读/04-DPHY/02-对象与数据链|对象与数据链：Endpoint 与 Async Notifier]]。

### 误区 9：`[ENABLED]` 就证明已经稳定出帧

**判断：错误。**

纠正：`[ENABLED]` 证明 Media Graph 软件 link 已存在并启用，不证明 Sensor 已 streaming、MIPI 有有效数据、格式一致或没有 CRC/ECC 错误。

> **稳定结论：`[ENABLED]` 不证明出帧。**

回看：[[02-源码陪读/04-DPHY/02-对象与数据链|对象与数据链：Bound 与 Media Link]]。

### 误区 10：Sensor ID 成功就证明 MIPI 链路正常

**判断：错误。**

纠正：Sensor ID 成功主要证明供电、复位、时钟和 I2C 控制通道基本可用；Sensor ID 不证明 MIPI CSI-2 数据面、Lane 映射、D-PHY、CSI、ISP 或抓帧正常。

## 六、调试验收：永远寻找最早缺失的证据

核心原则：

> 不要从“没有图”直接猜 Lane 或 ISP。按层检查，找到**最早缺失的证据**，下一步只检查它的上游条件和当前函数。

### 五层证据矩阵

| 层级 | 目标证据 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 1. 运行时 DTS | HW/逻辑节点为 `okay`，属性与 endpoint 存在 | DTB 中确实有配置 | driver 已匹配、硬件工作 |
| 2. Platform probe | 两条 D-PHY probe 成功日志 | HW 和逻辑主线走到成功位置 | Sensor 已 bound、MIPI 有数据 |
| 3. Async match | `dphy0 matches m00_b_imx415...` | fwnode 匹配并进入 `.bound()` | link 创建一定成功、Sensor 已开流 |
| 4. Media Graph | Entity、pads、两侧 `[ENABLED]` link | 软件拓扑存在并启用 | 物理 Lane 信号和稳定出帧 |
| 5. 数据面 | STREAMON、帧计数、抓帧、无关键错误 | 图像数据实际到达用户态 | 长时间稳定性和所有场景都正常 |

### 场景 1：连 HW probe 日志都没有

检查：

```bash
find /sys/firmware/devicetree/base -iname '*csi2*dphy*'
dmesg | grep -Ei 'csi2.*dphy|dphy.*probe'
```

下一检查点：运行时 HW 节点是否存在、是否 `okay`、compatible 是否命中 HW match table、驱动是否参与编译和注册。

### 场景 2：有 HW probe，没有逻辑 D-PHY probe

下一检查点：HW probe 是否执行到 `platform_driver_register(&rockchip_csi2_dphy_driver)`；逻辑节点是否 `okay`；逻辑 compatible 是否匹配；`attach_hw()` 的 phandle、pdev、drvdata 和 Lane 模式是否正常。

### 场景 3：两个 probe 都成功，没有 `dphy0 matches`

检查：

```bash
dmesg | grep -E 'dphy0 matches|imx415|unready subdev'
```

下一检查点：IMX415 是否注册 V4L2 subdev；D-PHY port@0 与 IMX415 endpoint 是否互指；parser 是否生成正确 fwnode 等待项；notifier 的 `waiting` 是否仍有 IMX415。

### 场景 4：有 match 日志，但 Media Graph 没有 Sensor→D-PHY link

检查：

```bash
media-ctl -p
```

下一检查点：`.bound()` 是否找到 Sensor Source pad；两端 entity 是否已进入同一 `media_device`；`media_create_pad_link()` 返回值和 pad 索引是否正确。

### 场景 5：Link `[ENABLED]`，仍然抓不到帧

下一检查点已经进入数据面：

```text
Sensor 是否执行 s_stream(1)
格式、分辨率、Bayer code 是否沿各 pad 一致
data-lanes、Lane 映射、link frequency、pixel rate 是否正确
D-PHY/CSI 时钟和电源是否在开流时启用
是否存在 CRC、ECC、FIFO、超时或 frame start 错误
RKISP 输出节点是否正确配置并真正 STREAMON
```

此时不要回去反复证明 I2C Sensor ID，因为控制面已经通过，缺失证据位于数据面。

### 板端证据目标

```text
csi2 dphy hw probe successfully!
csi2 dphy0 probe successfully!
dphy0 matches m00_b_imx415 4-001a-1:bus type 4
```

```text
IMX415 pad0 Source
    → rockchip-csi2-dphy0 pad0 Sink [ENABLED]

    → rkisp-csi-subdev pad0 Sink [ENABLED]
```

## 七、面试验收

### 30 秒表达

回答结构只保留四步：

```text
1. 两层对象：物理 HW + 逻辑 D-PHY
2. 两次匹配：Platform 框架分别回调两个 probe
3. Camera 建图：Subdev/Pad + Endpoint/Async + Bound/Link
4. 分层验证：DTS → probe → match → graph → frame
```

> [!question] 我的 30 秒回答
> 一个是 IM415 probe，一个是 D-PHY 的物理 probe 和逻辑 probe。

**判定：目前只识别出函数数量，还没有形成 30 秒调用主线。** 这里实际提到了三个 probe，并且它们分属两条设备初始化支线：

```text
Sensor 支线（I2C 总线框架）
└─ imx415_probe()

D-PHY 支线（Platform 总线框架）
├─ rockchip_csi2_dphy_hw_probe()
└─ rockchip_csi2_dphy_probe()
```

本章所说的“两个 probe”只指 D-PHY 内部的两个 Platform probe，不包含 `imx415_probe()`。Sensor 与 D-PHY 的 probe 顺序不应被背成固定串行；两边分别完成注册后，由 V4L2 Async 根据 endpoint/fwnode 把它们绑定起来。

> [!success] 高亮正确答案
> ==DTS 中既有物理 D-PHY HW 节点，也有 `csi2_dphy0` 逻辑节点。HW Platform Driver 注册后，由 Platform 总线框架匹配并回调 `rockchip_csi2_dphy_hw_probe()`，它集中准备寄存器、时钟、GRF 等硬件资源并保存 HW 对象；随后逻辑 Driver 注册并再次匹配，框架回调 `rockchip_csi2_dphy_probe()`。逻辑 probe 通过 `rockchip,hw` 执行 `attach_hw` 取回共享 HW 对象，再初始化 D-PHY Subdev 和 Sink/Source Pads，并把 port@0 endpoint 解析成等待 IMX415 的 Async 条件。IMX415 自己则由 I2C 总线框架调用 `imx415_probe()` 并注册 Sensor subdev。两边出现后，V4L2 Async 回调 `.bound()`，其中 `media_create_pad_link()` 创建 `IMX415 pad0 Source → D-PHY pad0 Sink` 的软件 Link；`media-ctl -p` 中的 `[ENABLED]` 只能证明该软件 Link 已创建并启用，不能证明已经出帧。==

> [!warning] 本轮最需要纠正的一句话
> 不要说“先执行 IMX415 probe，再执行两个 D-PHY probe”。更准确的是：**Sensor 和 D-PHY 分属 I2C、Platform 两条初始化支线，最终通过 Endpoint + V4L2 Async 汇合。**

#### 追问：Async 是物理 D-PHY 与逻辑 D-PHY 的匹配机制吗？

> [!question] 我的疑问
> 这个是 D-PHY 物理和逻辑之间的匹配机制，跟 Sensor 有关系么？

**判定：混淆了 Platform 对象关联和 V4L2 Camera 异步绑定。**

> [!success] 高亮正确答案
> ==不是。物理 D-PHY 与逻辑 D-PHY 之间不使用 V4L2 Async：两个 DTS 节点分别由 Platform 总线框架与各自 Driver 匹配并触发 probe；逻辑 probe 再通过 `rockchip,hw` phandle，沿 `device_node → platform_device → platform_get_drvdata()` 取得物理 HW 对象。V4L2 Async 与 Sensor 直接相关：逻辑 D-PHY 从输入 endpoint 生成 IMX415 的 fwnode 匹配条件并注册 notifier；IMX415 Sensor subdev 出现后，Async 框架匹配双方并回调 D-PHY 的 `.bound()`，随后创建 `IMX415 Source → D-PHY Sink` 的 Media Link。==

```text
物理 D-PHY HW ↔ 逻辑 D-PHY
    机制：Platform 匹配 + rockchip,hw phandle + drvdata
    目的：逻辑对象取得共享物理资源

IMX415 Sensor ↔ 逻辑 D-PHY
    机制：Endpoint/fwnode + V4L2 Async notifier + .bound()
    目的：解决 probe 顺序不固定，并创建 Media Link

逻辑 D-PHY ↔ RKISP
    机制：D-PHY 注册为 V4L2 subdev，等待 RKISP 一侧的 Async notifier 匹配
    目的：继续建立下游 Camera 管线
```

一句话记忆：**`rockchip,hw` 负责“逻辑 D-PHY 找物理资源”；V4L2 Async 负责“Camera 管线中的相邻 subdev 找到彼此”。**

#### 追问：从 DTS 到 `/dev/video0`，V4L2 Async 只使用一次吗？

> [!question] 我的疑问
> V4L2 Async 在整个 DTS 到 video 节点的过程中只使用一次么？

> [!success] 高亮正确答案
> ==不是。在当前 RK3568 4.19 Camera 链路中，至少有两次关键异步绑定：第一次由逻辑 D-PHY 的子 notifier 等待并绑定 IMX415 Sensor subdev，建立 `IMX415 → D-PHY`；第二次由 RKISP 的根 notifier 等待并绑定 D-PHY subdev，随后在 `.complete()` 中建立 `D-PHY → rkisp-csi-subdev → rkisp-isp-subdev` 等链路。不是每一级都使用 Async，RKISP 内部的 CSI、ISP、mainpath 等对象由 RKISP 驱动直接注册和建链。`/dev/video0` 也不是 Async 创建的，而是 RKISP 通过 `video_register_device()` 注册 stream video device 时产生；因此 `/dev/video0` 存在不等于上游 Async 绑定完整，更不等于能够出帧。==

```text
RKISP 根 notifier
│  等待：D-PHY subdev
│
└─ rockchip-csi2-dphy0（它既是上游要匹配的 subdev，
   │                    也是下游 notifier 的拥有者）
   │  子 notifier 等待：IMX415 subdev
   │
   └─ m00_b_imx415 4-001a-1
```

两次关键 Async 的职责：

| 次数 | 谁注册 notifier | 等待谁 | 匹配后的主要结果 |
|---|---|---|---|
| 1 | 逻辑 D-PHY subdev | IMX415 Sensor subdev | `.bound()` 创建 `IMX415 Source → D-PHY Sink` Link |
| 2 | RKISP `v4l2_device` | D-PHY subdev | `.bound()` 保存上游 subdev；`.complete()` 创建 D-PHY→CSI→ISP 等链路并完成管线初始化 |

不是 Async 的部分：

```text
物理 D-PHY ↔ 逻辑 D-PHY
    使用 rockchip,hw + drvdata，不使用 V4L2 Async

RKISP 内部 CSI / ISP / mainpath
    由 RKISP 驱动直接创建、注册和建 Link

/dev/video0
    由 video_register_device() 注册 video_device 产生
```

一句话记忆：**Async 用来拼接独立 probe、顺序不固定的相邻 subdev；它不是从 DTS 一路创建到 `/dev/video0` 的单次总流程。**

### 2 分钟表达

必须覆盖：

1. `module_platform_driver()` 注册 HW Platform Driver，不直接调用 probe。
2. HW probe 准备 MMIO、时钟、GRF、stream ops 和 drvdata，再注册逻辑 driver。
3. Platform 总线框架第二次匹配后回调逻辑 probe。
4. 逻辑 probe 通过 `rockchip,hw` 完成 `node→pdev→drvdata`，取得共享 HW 对象。
5. `v4l2_subdev_init()` 挂 ops；`media_entity_pads_init()` 建 Sink/Source pads，但不建 link。
6. port@0 endpoint 被转换成等待 Sensor fwnode 的 async 条件；注册不阻塞。
7. 匹配后 Async 框架回调 `.bound()`，Rockchip 代码创建 Sensor Source→D-PHY Sink 的 link。
8. 最后用五层证据验证，主动说明软件 Link 不等于出帧。
