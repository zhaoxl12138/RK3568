# D-PHY 对象与数据链：Subdev、Pads、Endpoint、Async 与 Link

> 返回：[[02-源码陪读/04-DPHY/00-源码陪读索引|D-PHY 源码陪读索引]]　上一篇：[[02-源码陪读/04-DPHY/01-生命周期]]　下一篇：[[02-源码陪读/04-DPHY/03-调试与面试验收]]

## 这一章只解决三个问题

上一章结束时，逻辑 D-PHY 已经拿到了物理 HW 对象，但它还只是驱动内部的 `struct csi2_dphy`，Camera 框架并不认识它。本章继续追逻辑 probe 中紧接着执行的代码：

```text
struct csi2_dphy
  ↓ v4l2_subdev_init()
成为 V4L2 可以调度的 subdev
  ↓ media_entity_pads_init()
拥有 pad0 Sink 和 pad1 Source
  ↓
具备加入 Media Graph 的基本形状
```

本章只要求回答：

1. 为什么 D-PHY 要包装成 `v4l2_subdev`？
2. 为什么它需要一个 Sink pad 和一个 Source pad？
3. `v4l2_subdev_init()` 是执行所有驱动函数，还是只保存 ops 回调表？

先不进入 endpoint、异步 notifier 和 link 创建；那是下一章。

## 先认识三个对象的包含关系

```text
struct csi2_dphy                 Rockchip 驱动私有对象
└── struct v4l2_subdev sd        V4L2 认识的子设备对象
    └── struct media_entity      Media Controller 认识的图节点

struct csi2_dphy
└── struct media_pad pads[2]     图节点的输入/输出端口
```

大白话：同一个 D-PHY 被三套代码从不同角度观察。Rockchip 驱动关心硬件状态，V4L2 关心它能响应哪些 Camera 操作，Media Controller 关心它在数据链路中有哪些入口和出口。

## Source Insight 定位卡

本节仍然从 Rockchip 文件开始：

```text
drivers/phy/rockchip/phy-rockchip-csi2-dphy.c
```

精准搜索：

```text
csi2_dphy_subdev_ops

```

`v4l2_subdev_init` 会在 `v4l2-subdev.c` 找到通用实现，但你要先回到它的调用者 `rockchip_csi2_dphy_probe()`，确认是谁把 `sd` 和 `csi2_dphy_subdev_ops` 传进去。

## `v4l2_subdev_init()` 只初始化对象

```c
v4l2_subdev_init(sd, &csi2_dphy_subdev_ops);
```

```c
static const struct v4l2_subdev_ops csi2_dphy_subdev_ops = {
    .core = &csi2_dphy_core_ops,
    .video = &csi2_dphy_video_ops,
    .pad = &csi2_dphy_subdev_pad_ops,
};
```

`core/video/pad` 三组 ops 分别提供电源、帧率/总线/开流、格式与 selection 能力。此处只是保存函数指针；probe 不会顺序执行这些回调，未来由 V4L2 管线按需调用。

通用实现的关键部分：

```c
void v4l2_subdev_init(struct v4l2_subdev *sd,
                      const struct v4l2_subdev_ops *ops)
{
    INIT_LIST_HEAD(&sd->list);
    BUG_ON(!ops);
    sd->ops = ops;
    sd->v4l2_dev = NULL;
    sd->flags = 0;
    sd->name[0] = '\0';
    sd->entity.name = sd->name;
    sd->entity.obj_type = MEDIA_ENTITY_TYPE_V4L2_SUBDEV;
    sd->entity.function = MEDIA_ENT_F_V4L2_SUBDEV_UNKNOWN;
}
```

它还没有异步注册 D-PHY、没有把 entity 接入根 `media_device`，也没有创建 Sensor link。

## `rockchip_csi2dphy_media_init()` 准备图对象

```c
dphy->pads[CSI2_DPHY_RX_PAD_SOURCE].flags =
    MEDIA_PAD_FL_SOURCE | MEDIA_PAD_FL_MUST_CONNECT;
dphy->pads[CSI2_DPHY_RX_PAD_SINK].flags =
    MEDIA_PAD_FL_SINK | MEDIA_PAD_FL_MUST_CONNECT;
dphy->sd.entity.function = MEDIA_ENT_F_VID_IF_BRIDGE;

ret = media_entity_pads_init(&dphy->sd.entity,
                             CSI2_DPHY_RX_PADS_NUM, dphy->pads);
```

结果是 pad0 为 Sink、pad1 为 Source，entity 类型从 UNKNOWN 改成视频接口桥。

## `media_entity_pads_init()` 建所有权，不建 link

```c
entity->num_pads = num_pads;
entity->pads = pads;
for (i = 0; i < num_pads; i++) {
    pads[i].entity = entity;
    pads[i].index = i;
}
```

因此形成：

```text
entity.num_pads = 2
entity.pads = dphy->pads
pads[0].entity = &dphy->sd.entity, index = 0
pads[1].entity = &dphy->sd.entity, index = 1
```

在此时 `entity->graph_obj.mdev` 通常仍为 `NULL`。后续 D-PHY 被 RKISP 父 notifier 匹配，`v4l2_device_register_subdev()` / `media_device_register_entity()` 才把 entity/pad 接入根图。最后 `media_create_pad_link()` 才创建两个 pad 之间的边。

| 参数从哪里来 | `sd=&csi2dphy->sd`；ops 是驱动静态回调表 |
| 读取什么 | `csi2_dphy_subdev_ops` 中的 core/video/pad 入口 |

| 面试一句话 | “media_init 先准备 entity/pad，再把输入 endpoint 变成异步等待条件并注册 D-PHY subdev。” |

## 函数卡：`media_entity_pads_init()`

| 固定字段 | 内容 |
|---|---|
| 函数属于哪一层 | Media Controller 图对象层 |
| 谁调用：直接调用 / 框架回调 | `rockchip_csi2dphy_media_init()` 直接调用 |
| 参数从哪里来 | entity=`&dphy->sd.entity`，数量为 2，数组为 `dphy->pads` |
| 读取什么 | pad 数量与各 pad 预设的 Source/Sink flags |
| 修改哪个结构体 | `entity->num_pads/pads`、每个 `pad->entity/index` |
| DTS 对应 | port@0 对应 Sink 方向，port@1 对应 Source 方向；不在此函数解析 endpoint |
| 运行时证据 | `media-ctl -p` 显示 `rockchip-csi2-dphy0 (2 pads...)`、pad0 Sink、pad1 Source |
| 失败时下一检查点 | `-E2BIG` 查 pad 数；无 entity 时查后续 subdev/entity 注册链 |
| 面试一句话 | “pads_init 建立 entity 对 pad 的所有权和编号，link 必须由另一个 API 创建。” |

# Endpoint 与 Async Notifier

> 本篇继续：Endpoint 解析与 Async Notifier

## Source Insight 定位卡

先回到：

```text
drivers/phy/rockchip/phy-rockchip-csi2-dphy.c
```

先搜平台私有解析函数：

```text
rockchip_csi2_dphy_fwnode_parse
v4l2_async_notifier_parse_fwnode_endpoints_by_port
v4l2_async_subdev_notifier_register
```

如果跳到了 `v4l2-fwnode.c` 或 `v4l2-async.c`，这是正常的：前者是通用 endpoint 解析实现，后者是异步匹配框架；先记住调用者仍然是 `phy-rockchip-csi2-dphy.c`。

## 从静态 endpoint 得到等待条件

板级关系：

```dts
port@0 {
    reg = <0>;
    mipi_in_ucam1: endpoint@2 {
        reg = <2>;
        remote-endpoint = <&imx415_out>;
        data-lanes = <1 2 3 4>;
    };
};
```

**`remote-endpoint` 是静态连接声明，不代表 DTS 解析时已经创建 Media link。驱动先把它转换成“等待哪个 Sensor fwnode”的条件：**

```c
v4l2_async_notifier_parse_fwnode_endpoints_by_port(
    dphy->dev,
    &dphy->notifier,
    sizeof(struct sensor_async_subdev),
    0,
    rockchip_csi2_dphy_fwnode_parse);
```

五个参数分别表示起始设备、结果 notifier、每个等待项的大小、只扫描 port@0、Rockchip 的补充解析回调。

框架主线：

```text
遍历 D-PHY endpoint，只保留 port == 0
→ 分配 sensor_async_subdev
→ remote-endpoint 找到远端设备 fwnode
→ asd->match_type = V4L2_ASYNC_MATCH_FWNODE
→ asd->match.fwnode = IMX415 设备 fwnode
→ Rockchip parse 回调保存 Lane 信息
→ 加入 notifier->subdevs[]
```

通用代码的关键动作：

```c
asd->match_type = V4L2_ASYNC_MATCH_FWNODE;
asd->match.fwnode = fwnode_graph_get_remote_port_parent(endpoint);
vep = v4l2_fwnode_endpoint_alloc_parse(endpoint);
ret = parse_endpoint ? parse_endpoint(dev, vep, asd) : 0;
notifier->subdevs[notifier->num_subdevs++] = asd;
```

## Lane 参数怎样流动

```text
DTS data-lanes = <1 2 3 4>
→ vep->bus.mipi_csi2.num_data_lanes = 4
→ rockchip_csi2_dphy_fwnode_parse()
→ s_asd->lanes = 4
→ .bound() 后 dphy->sensors[n].lanes = 4
```

```c
if (vep->base.port != 0)
    return -EINVAL;
if (vep->bus_type == V4L2_MBUS_CSI2) {
    config->type = V4L2_MBUS_CSI2;
    config->flags = vep->bus.mipi_csi2.flags;
    s_asd->lanes = vep->bus.mipi_csi2.num_data_lanes;
} else {
    return -EINVAL;
}
```

Lane 数先成为软件链路描述，不会在 endpoint 解析阶段直接写硬件寄存器；开流时才结合数据率配置 D-PHY。

## notifier register 只登记等待关系

```c
static const struct v4l2_async_notifier_operations
rockchip_csi2_dphy_async_ops = {
    .bound = rockchip_csi2_dphy_notifier_bound,
    .unbind = rockchip_csi2_dphy_notifier_unbind,
};

dphy->sd.subdev_notifier = &dphy->notifier;
dphy->notifier.ops = &rockchip_csi2_dphy_async_ops;
ret = v4l2_async_subdev_notifier_register(&dphy->sd, &dphy->notifier);
return v4l2_async_register_subdev(&dphy->sd);
```

准确职责：

```text
v4l2_async_subdev_notifier_register()
= D-PHY 拿着 notifier 等上游 Sensor

v4l2_async_register_subdev()
= D-PHY 自己作为 subdev 等下游 RKISP 的根 notifier
```

实际是嵌套 notifier 树：

```text
RKISP 根 notifier（拥有 v4l2_device）
        ↓ 匹配 D-PHY subdev
D-PHY 子 notifier（等待 Sensor）
        ↓ 匹配 IMX415 subdev
IMX415
```

匹配核心条件可概括为 `sensor_sd->fwnode == asd->match.fwnode`。三者 probe 顺序不必固定；对象和等待条件都出现后，框架再完成匹配。

| DTS 对应          | `ports/port@0/endpoint/remote-endpoint/data-lanes`                             |

| 固定字段            | 内容                                                          |

| 谁调用：直接调用 / 框架回调 | `rockchip_csi2dphy_media_init()` 直接调用                       |
| 参数从哪里来          | `sd=&dphy->sd`；notifier 已由 endpoint parser 填入等待项和 ops       |

## 一个日志边界

板级 port@0 若还列出未实际注册的 IMX335、OV13850，可能看到：

```text
rkisp rkisp-vir0: clear unready subdev num: 2
```

前缀是 `rkisp`，表示 RKISP 根 notifier 清理整棵异步树中未就绪的等待项；不要归因成 D-PHY 文件内某个“clear 两个 Sensor”的直接调用。

# Bound 与 Media Link

> 本篇继续：Async Bound 与 Media Link

## Source Insight 定位卡

先打开：

```text
drivers/phy/rockchip/phy-rockchip-csi2-dphy.c
```

搜索：

```text
rockchip_csi2_dphy_notifier_bound
media_create_pad_link
v4l2_async_notifier_call_bound
```

第一个是 Rockchip 私有 `.bound()`；后两个分别是通用 Media link 创建函数和 Async 框架回调分发点。看到 `v4l2-async.c` 不要迷路：调用链会从通用框架回到当前文件的 `rockchip_csi2_dphy_notifier_bound()`。

## `.bound()` 是框架回调

Sensor subdev 的 fwnode 与 D-PHY 等待项匹配后，V4L2 Async 走：

```text
v4l2_async_find_match()
→ v4l2_async_match_notify()
→ v4l2_device_register_subdev(sensor_sd)
→ v4l2_async_notifier_call_bound()
→ notifier->ops->bound()
→ rockchip_csi2_dphy_notifier_bound()
```

先把 Sensor subdev/entity/pad 注册到根 `media_device`，再回调 D-PHY 的 `.bound()`。所以创建 link 时，Sensor 与 D-PHY 两端已经属于同一 Media Graph。

## 合并静态 endpoint 与运行时 Sensor

```c
dphy = container_of(notifier, struct csi2_dphy, notifier);
s_asd = container_of(asd, struct sensor_async_subdev, asd);

sensor = &dphy->sensors[dphy->num_sensors++];
sensor->lanes = s_asd->lanes;
sensor->mbus = s_asd->mbus;
sensor->sd = sd;
```

`container_of` 由内嵌成员地址找回外层对象。随后把等待阶段解析的 Lane/mbus 与真正匹配到的 `sensor sd` 合并进 `dphy->sensors[]`。

运行时日志：

```text
rockchip-csi2-dphy csi2-dphy0:
dphy0 matches m00_b_imx415 4-001a-1:bus type 4
```

## 找 Source pad 并显式创建边

```c
for (pad = 0; pad < sensor->sd->entity.num_pads; pad++)
    if (sensor->sd->entity.pads[pad].flags & MEDIA_PAD_FL_SOURCE)
        break;

ret = media_create_pad_link(
    &sensor->sd->entity, pad,
    &dphy->sd.entity, CSI2_DPHY_RX_PAD_SINK,
    dphy->num_sensors != 1 ? 0 : MEDIA_LNK_FL_ENABLED);
```

参数翻译：

```text
Source entity = IMX415 entity
Source pad    = IMX415 pad0
Sink entity   = rockchip-csi2-dphy0 entity
Sink pad      = D-PHY pad0
flags         = 第一个绑定的 Sensor 默认 ENABLED
```

最终 `media-ctl -p` 显示：

```text
"m00_b_imx415 4-001a-1":0
    → "rockchip-csi2-dphy0":0 [ENABLED]
```

**要区分三个动作：`media_entity_pads_init()` 只准备 pad；`v4l2_device_register_subdev()` 把 entity/pad 接入根图；`media_create_pad_link()` 才创建两个 pad 之间的边**。

## 函数卡：`.bound()` / `rockchip_csi2_dphy_notifier_bound()`

| 固定字段            | 内容                                                                          |
| --------------- | --------------------------------------------------------------------------- |
| 函数属于哪一层         | V4L2 Async 匹配结果处理层，与 Media Controller 建图层相接                                 |
| 谁调用：直接调用 / 框架回调 | V4L2 Async 经 `notifier->ops->bound` 框架回调；不是 media_init 直接调用                 |
| 参数从哪里来          | notifier 属于 D-PHY；sd 是匹配到的 IMX415 subdev；asd 是对应 endpoint 等待项               |
| 读取什么            | `s_asd->lanes/mbus`、Sensor entity 的 Source pad、D-PHY 当前 Sensor 数            |
| 修改哪个结构体         | `dphy->sensors[]/num_sensors`，并向 media_device 增加一条 link                     |
| DTS 对应          | `remote-endpoint` 决定匹配对象，`data-lanes` 提供保存到 Sensor 记录的 Lane 数               |
| 运行时证据           | `dphy0 matches ...` 日志与 `media-ctl -p` 的 IMX415→D-PHY `[ENABLED]`           |
| 失败时下一检查点        | 槽满查 Sensor 数；无 Source pad 查 Sensor entity；建 link 失败查双方是否同属根 media_device    |
| 面试一句话           | “bound 把 endpoint 参数与匹配到的 Sensor 合并，并创建 Sensor Source 到 D-PHY Sink 的 link。” |

## 函数卡：`media_create_pad_link()`

| 固定字段 | 内容 |
|---|---|
| 函数属于哪一层 | Media Controller 拓扑边创建层 |
| 谁调用：直接调用 / 框架回调 | D-PHY `.bound()` 回调内部直接调用 |
| 参数从哪里来 | Sensor entity/Source pad 来自匹配到的 sd；D-PHY entity/Sink pad 来自逻辑对象 |
| 读取什么 | 两端 entity/pad 的归属、索引与 link flags |
| 修改哪个结构体 | 在 media graph 中创建正反向 link 对象并设置 enabled flag |
| DTS 对应 | 实现 `imx415_out ↔ mipi_in_ucam1` 的运行时软件连接 |
| 运行时证据 | `media-ctl -p` 出现两端互相指向且第一路为 `[ENABLED]` |
| 失败时下一检查点 | 查 pad 索引/方向、entity 是否已注册、是否跨 media_device、重复 link |
| 面试一句话 | “DTS 只声明拓扑，真正的 Sensor→D-PHY 运行时边由 bound 中的 media_create_pad_link 建立。” |

## 证据能证明到哪一步

`dphy0 matches` 证明 fwnode 匹配并进入 bound；`[ENABLED]` 证明软件 link 存在。二者都不能单独证明 Sensor 已 streaming、MIPI 包到达、无 CRC/ECC 错误或能稳定抓帧。

## 调用类型与 C 基础

- `sd->ops = ops` 是字段赋值，`v4l2_subdev_call(...)` 才会按类别选择 ops 并调用函数指针。
- `container_of(asd, struct sensor_async_subdev, asd)` 用内嵌成员地址反推外层对象；这是对象所有权关系，不是创建新对象。
- `media_entity_pads_init()`、endpoint parser、notifier register 是直接调用；`.bound()` 是 Async 框架回调。

## 白话解释

Pad 是插座，Link 是连接线，Entity 是设备方框；Async 不坐着阻塞等人，而是留下“我要等哪个 fwnode”的登记单，IMX415 到场后再回调 `.bound()` 接线。

## 板端证据：能证明与不能证明

`media-ctl -p` 中出现 D-PHY 两个 pad 和 Sensor→D-PHY `[ENABLED]`，能证明 entity/pad/link 软件对象已经建立；不能证明 Sensor 已开流、MIPI 包到达、无 CRC/ECC 或 DMA 已完成。
