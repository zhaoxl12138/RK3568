# HW Driver 注册与 Probe

本篇还合并原“逻辑 D-PHY Probe 与 Attach HW”全文，保持 HW→逻辑层的生命周期连续。

> 返回：[[02-源码陪读/04-DPHY/00-源码陪读索引|D-PHY 源码陪读索引]]　下一篇：[[02-源码陪读/04-DPHY/02-对象与数据链]]

## Source Insight 定位卡

先打开：

```text
drivers/phy/rockchip/phy-rockchip-csi2-dphy-hw.c
```

然后按顺序搜索：

```text
rockchip_csi2_dphy_hw_driver
rockchip_csi2_dphy_hw_probe
rockchip_csi2_dphy_hw_match_id
rockchip_csi2_dphy_driver
```

不要直接搜索 `module_platform_driver`。它是全 Linux 通用宏，会把其他 Camera、显示、音频驱动全部列出来。当前文件中真正有意义的是：这个宏的参数是 `rockchip_csi2_dphy_hw_driver`。

## 为什么找不到 `rockchip_csi2_dphy_hw_probe()` 的直接调用者

这是正常现象。源码中没有普通的：

```c
rockchip_csi2_dphy_hw_probe(pdev);
```

驱动先把函数地址保存到结构体：

```c
static struct platform_driver rockchip_csi2_dphy_hw_driver = {
    .probe = rockchip_csi2_dphy_hw_probe,
};
```

之后由 Driver Core 通过函数指针间接调用。Source Insight 的普通 Caller 查询通常只能稳定看到 `.probe = rockchip_csi2_dphy_hw_probe` 这个引用，无法自动还原完整运行时回调链。

本 SDK 的真实路径是：

```text
module_platform_driver(rockchip_csi2_dphy_hw_driver)
        ↓ 注册具体 platform_driver
__platform_driver_register()
        ↓ 把通用包装函数装进 device_driver
drv->driver.probe = platform_drv_probe
        ↓ 设备和驱动匹配后，Driver Core 进入
really_probe(dev, drv)
        ↓ 间接调用通用 device_driver.probe
drv->probe(dev)
        ↓ 实际进入
platform_drv_probe(struct device *_dev)
        ↓ 转回具体 platform_driver，再次函数指针调用
drv->probe(struct platform_device *pdev)
        ↓ 这里最终进入
rockchip_csi2_dphy_hw_probe(pdev)
```

对应源码定位：

| 搜索符号 | 文件 | 关键代码 |
|---|---|---|
| `__platform_driver_register` | `drivers/base/platform.c` | `drv->driver.probe = platform_drv_probe` |
| `really_probe` | `drivers/base/dd.c` | `drv->probe(dev)` |
| `platform_drv_probe` | `drivers/base/platform.c` | `drv = to_platform_driver(...)`，然后 `drv->probe(dev)` |
| `rockchip_csi2_dphy_hw_driver` | `drivers/phy/rockchip/phy-rockchip-csi2-dphy-hw.c` | `.probe = rockchip_csi2_dphy_hw_probe` |

在 Source Insight 中按下面顺序搜，比“查找调用者”更可靠：

```text
rockchip_csi2_dphy_hw_driver
→ __platform_driver_register
→ platform_drv_probe
→ really_probe
```

这里有两个同名形式的 `drv->probe`，类型并不相同：

```text
device_driver.probe    → platform_drv_probe(struct device *)
platform_driver.probe  → rockchip_csi2_dphy_hw_probe(struct platform_device *)
```

一句话：`rockchip_csi2_dphy_hw_probe()` 没有固定的直接调用者，它是 Platform Core 在设备匹配成功后，通过保存在结构体里的函数指针回调的。

## 本阶段发生了什么

RK3568 BSP 把 CSI2 D-PHY 拆成物理 HW driver 和逻辑 D-PHY driver。前者先取得 MMIO、时钟、GRF 等硬件资源并保存开停流函数，随后才注册后者。

```text
module_platform_driver(rockchip_csi2_dphy_hw_driver)
→ Platform Core 匹配 rockchip,rk3568-csi2-dphy-hw
→ rockchip_csi2_dphy_hw_probe(pdev)
→ platform_driver_register(&rockchip_csi2_dphy_driver)
```

注意：第一和第二步之间是框架匹配与回调，不是宏直接调用 probe；最后一行也只是注册逻辑 driver，不是直接执行逻辑 probe。

## 关键代码

```c
static struct platform_driver rockchip_csi2_dphy_hw_driver = {
    .probe = rockchip_csi2_dphy_hw_probe,
    .remove = rockchip_csi2_dphy_hw_remove,
    .driver = {
        .name = "rockchip-csi2-dphy-hw",
        .of_match_table = rockchip_csi2_dphy_hw_match_id,
    },
};
module_platform_driver(rockchip_csi2_dphy_hw_driver);
```

`.probe = 函数名` 是保存函数地址；有括号的 `rockchip_csi2_dphy_hw_probe(pdev)` 才是直接调用表达式。宏可概念化为在 init 时调用 `platform_driver_register(&rockchip_csi2_dphy_hw_driver)`，Platform Core 之后根据 compatible 决定何时回调 `.probe`。

HW probe 尾部最容易漏：

```c
dphy_hw->stream_on = csi2_dphy_hw_stream_on;
dphy_hw->stream_off = csi2_dphy_hw_stream_off;
platform_set_drvdata(pdev, dphy_hw);
pm_runtime_enable(&pdev->dev);
platform_driver_register(&rockchip_csi2_dphy_driver);
```

`platform_set_drvdata()` 把 `struct csi2_dphy_hw *` 藏进 HW `platform_device`；下一阶段的 `attach_hw()` 会通过同一个设备取回它。逻辑 driver 的注册发生在 HW probe 的成功路径内，因此不会依靠不确定的 probe 顺序去碰运气。

## DTS 对照

```dts
csi2_dphy_hw: csi2-dphy-hw@fe870000 {
    compatible = "rockchip,rk3568-csi2-dphy-hw";
    reg = <0x0 0xfe870000 0x0 0x1000>;
    clocks = <&cru PCLK_MIPICSIPHY>;
    clock-names = "pclk";
    rockchip,grf = <&grf>;
    status = "disabled";
};
```

板级 DTSI 必须用 `&csi2_dphy_hw { status = "okay"; };` 启用。`compatible` 负责匹配，`reg`、clock 与 GRF 由 HW probe 消费。

## 函数卡：`module_platform_driver()` / HW 注册入口

| 固定字段 | 内容 |
|---|---|
| 函数属于哪一层 | Linux 模块初始化与 Platform 驱动模型 |
| 谁调用：直接调用 / 框架回调 | 内核模块初始化机制触发宏生成的 init；宏负责注册 driver，不直接调用 HW probe |
| 参数从哪里来 | 参数是静态定义的 `rockchip_csi2_dphy_hw_driver` |
| 读取什么 | driver 中的 `.probe/.remove/.of_match_table` |
| 修改哪个结构体 | 把 `struct platform_driver` 登记到 Platform Core |
| DTS 对应 | `compatible = "rockchip,rk3568-csi2-dphy-hw"` |
| 运行时证据 | 后续出现 HW probe 日志；仅注册动作通常无独立日志 |
| 失败时下一检查点 | 检查驱动是否编入、init 是否执行、match table 与运行时 compatible |
| 面试一句话 | “模块宏注册 HW platform_driver，compatible 匹配成功后才由 Platform Core 回调 probe。” |

## 函数卡：`rockchip_csi2_dphy_hw_probe()`

| 固定字段 | 内容 |
|---|---|
| 函数属于哪一层 | Platform 驱动模型 + D-PHY 物理硬件层 |
| 谁调用：直接调用 / 框架回调 | Platform Core 的 `.probe` 框架回调 |
| 参数从哪里来 | `pdev` 是 HW DTS 节点生成的 `platform_device` |
| 读取什么 | compatible 匹配数据、MMIO resource、clock、GRF 等 HW 资源 |
| 修改哪个结构体 | 分配并填写 `struct csi2_dphy_hw`，设置 ops，写入 `pdev->driver_data` |
| DTS 对应 | HW 节点的 `reg/clocks/rockchip,grf/status` |
| 运行时证据 | `csi2 dphy hw probe successfully!`；逻辑 probe 日志可能因同步匹配而先打印 |
| 失败时下一检查点 | 先查运行时节点是否启用，再查 MMIO/clock/GRF 获取和逻辑 driver 注册返回值 |
| 面试一句话 | “HW probe 准备物理资源和硬件 ops，把私有对象存进 drvdata，再注册逻辑 D-PHY driver。” |

## 容易误判的日志顺序

`platform_driver_register(&rockchip_csi2_dphy_driver)` 可能同步匹配已有 `csi2_dphy0` 并完成逻辑 probe，之后 HW probe 才打印自己的成功日志。因此：

```text
csi2 dphy0 probe successfully!
csi2 dphy hw probe successfully!
```

不表示逻辑对象比物理硬件更早准备好；只能说明 HW 成功日志位于逻辑 driver 注册之后。

## 本节关注问题总结：从注册宏到 HW Probe

### 1. 为什么搜索 `module_platform_driver` 会出现大量结果？

因为它是所有 Platform Driver 都可以使用的通用宏，不是 Rockchip D-PHY 专属函数。Source Insight 全局搜索会同时列出 Camera、显示、音频等大量驱动。

当前章节应先搜索唯一符号：

```text
rockchip_csi2_dphy_hw_driver
rockchip_csi2_dphy_hw_probe
rockchip_csi2_dphy_hw_match_id
```

### 2. `module_platform_driver` 是谁调用的？

它不是函数，没有运行时调用者。预处理阶段会把它展开成模块初始化和退出代码，核心效果可以理解为：

```c
static int __init rockchip_csi2_dphy_hw_driver_init(void)
{
    return platform_driver_register(
        &rockchip_csi2_dphy_hw_driver);
}

module_init(rockchip_csi2_dphy_hw_driver_init);
```

驱动编进内核时，由启动阶段的 initcall 机制调用生成的 init 函数；驱动编成 `.ko` 时，由模块加载器在加载模块时调用。

### 3. `register` 是“寄存器”还是“注册”？

这里是动词“注册、登记”：

```c
platform_driver_register(&rockchip_csi2_dphy_hw_driver);
```

表示把驱动对象交给 Linux Platform 驱动模型管理，不是在操作硬件寄存器。真正读写硬件寄存器通常会看到：

```c
readl();
writel();
regmap_read();
regmap_write();
```

### 4. `of_match_table` 如何连接 DTS？

驱动的匹配表：

```c
static const struct of_device_id rockchip_csi2_dphy_hw_match_id[] = {
    { .compatible = "rockchip,rk3568-csi2-dphy-hw" },
    { }
};
```

通过：

```c
.of_match_table = rockchip_csi2_dphy_hw_match_id
```

交给 Platform Core。Platform Core 将运行时 DTS 节点的：

```dts
compatible = "rockchip,rk3568-csi2-dphy-hw";
```

与匹配表逐项比较。字符串相等才认为设备和驱动匹配；DTS 标签、节点地址和 `.driver.name` 都不是这次 OF 匹配的核心依据。

### 5. 为什么找不到 `rockchip_csi2_dphy_hw_probe()` 的直接调用者？

因为源码没有直接写：

```c
rockchip_csi2_dphy_hw_probe(pdev);
```

它的函数地址先保存在：

```c
.probe = rockchip_csi2_dphy_hw_probe
```

设备匹配成功后，Driver Core 经过两层函数指针回调：

```text
really_probe()
→ device_driver.probe = platform_drv_probe()
→ platform_driver.probe
→ rockchip_csi2_dphy_hw_probe(pdev)
```

所以 Source Insight 的 Caller 查询不一定能还原完整链路，追框架回调时应从“结构体成员赋值”继续追注册函数和通用包装函数。

### 6. 本节最终应该能说清什么？

```text
内核启动或加载模块
→ module_platform_driver 宏生成的 init 函数执行
→ 注册 rockchip_csi2_dphy_hw_driver
→ Platform Core 比较 DTS compatible 与 of_match_table
→ 匹配成功
→ 通过函数指针回调 rockchip_csi2_dphy_hw_probe(pdev)
→ HW probe 获取物理资源、保存 drvdata 和 stream ops
→ 注册下一层逻辑 D-PHY driver
```

面试表达：

> D-PHY HW 驱动通过模块宏注册为 Platform Driver。Platform Core 使用 `of_match_table` 与 DTS 的 `compatible` 匹配，成功后通过 `.probe` 函数指针回调 HW probe；HW probe 准备寄存器、时钟和 GRF 等物理资源，再注册逻辑 D-PHY Driver。

## 学习诊断：我为什么会连续追问这些问题

### 这次疑问是怎样产生的

我最开始按照普通 C 程序的阅读方式追代码，默认函数之间应该存在清晰的直接调用：

```text
A()
→ B()
→ C()
```

但 Linux 驱动大量使用的是：

```text
宏生成初始化入口
→ 注册结构体
→ 框架保存函数指针
→ 设备匹配
→ 框架在另一个时刻回调 probe
```

所以我搜索 `module_platform_driver` 时看到了大量无关驱动；搜索 `rockchip_csi2_dphy_hw_probe()` 时又找不到普通 Caller。这不是代码不存在，而是我暂时还没有建立“注册 + 匹配 + 回调”的阅读方式。

随后我又把几个不同阶段混成了一件事：

```text
Kconfig / Makefile：决定是否参与编译
module_init：决定初始化入口何时被执行
register：把驱动对象登记给框架
match：比较 compatible
probe：匹配成功后初始化设备
```

这些阶段一旦混在一起，就容易产生“编译系统找到驱动并直接执行 probe”的错误印象。

### 当前暴露出的薄弱点

#### 1. C 语言框架代码阅读

需要补强：

```text
宏展开
结构体成员赋值
函数指针
回调函数
container_of / 类型转换
```

典型误区是把：

```c
.probe = rockchip_csi2_dphy_hw_probe
```

看成普通调用。它实际上只是保存函数地址。

#### 2. Linux 驱动生命周期

目前对下面几步的边界还不够稳定：

```text
编译
→ 初始化
→ 注册
→ 设备/驱动匹配
→ probe
→ 保存私有对象
→ 后续运行时调用
```

真正需要补的是 Linux Driver Model，不是继续记更多 Camera 名词。

#### 3. DTS 与运行时对象的转换

我容易把 DTS 节点理解成会主动调用代码的对象。更准确的理解是：

```text
DTS 只描述硬件、资源和引用关系
        ↓
内核把节点变成 device / platform_device
        ↓
驱动在 probe 中解析资源和 phandle
```

`rockchip,hw = <&csi2_dphy_hw>` 只是静态引用；真正找到 HW 设备并取得对象的是逻辑 Probe 中的代码。

#### 4. 对象所有权与分层

我最难理解的是：为什么 HW Probe 做完以后，逻辑 Probe 还要回来取得 HW 对象。

原因是两个对象职责不同：

```text
struct csi2_dphy_hw
负责寄存器、时钟、GRF、Lane 模式和硬件开停

struct csi2_dphy
负责 V4L2 Subdev、Pads、Endpoint、Sensor 和 Media Graph
```

逻辑 Probe 没有再次调用 HW Probe，只是通过：

```text
rockchip,hw phandle
→ HW device_node
→ HW platform_device
→ platform_get_drvdata()
→ 已初始化的 struct csi2_dphy_hw
```

取得底层硬件句柄。这样一个物理 HW 可以统一管理资源，并服务一个或多个逻辑 D-PHY 实例。

#### 5. 英文在代码语境中的含义

例如 `register` 同时可以表示“寄存器”和“注册”。在：

```c
platform_driver_register()
```

中是“向框架注册”；看到 `readl/writel/regmap_read/regmap_write` 才通常是在操作硬件寄存器。

### 以后追框架源码时的固定检查表

每遇到一个陌生符号，依次回答：

1. 它是宏、普通函数、结构体，还是结构体中的函数指针？
2. 当前发生在编译期、启动初始化期、匹配期，还是设备运行期？
3. 这一行是直接调用、保存函数地址，还是框架回调？
4. 当前对象由谁创建、由谁保存、由谁负责释放？
5. DTS 在这里提供的是匹配标识、资源，还是 phandle 引用？
6. 如果取得的是 `drvdata`，里面保存的具体私有结构体是什么？
7. 当前结论可以用哪条 dmesg、sysfs 或 Media Graph 证据验证？

### 当前应该形成的稳定模型

```text
Kconfig / Makefile 决定是否编译
        ↓
内核启动或模块加载执行 init
        ↓
注册 HW Platform Driver
        ↓
compatible 匹配 HW DTS 节点
        ↓
HW Probe 初始化物理资源并保存 dphy_hw
        ↓
注册逻辑 D-PHY Driver
        ↓
compatible 匹配逻辑 DTS 节点
        ↓
逻辑 Probe 通过 rockchip,hw 取得 dphy_hw
        ↓
继续建立 V4L2 Subdev、Pads 和 Media Graph
```

当前阶段不要求把 `really_probe()` 的所有内部实现背下来。验收标准是：能够解释为什么 Source Insight 找不到直接 Caller，能够区分注册与寄存器，能够说明两个 DTS 节点、两个 Platform Driver、两个 Probe 和两个私有对象之间的关系。

# 逻辑 D-PHY Probe 与 Attach HW

> 本篇前半：HW Driver 注册与 Probe　下一篇：[[02-源码陪读/04-DPHY/02-对象与数据链]]

## Source Insight 定位卡

先打开：

```text
drivers/phy/rockchip/phy-rockchip-csi2-dphy.c
```

按这个顺序搜索：

```text
rockchip_csi2_dphy_driver
rockchip_csi2_dphy_probe
rockchip_csi2_dphy_attach_hw
rockchip_csi2dphy_media_init
```

这里要区分两个文件：`phy-rockchip-csi2-dphy-hw.c` 负责物理 HW；本文件负责逻辑 D-PHY、V4L2 Subdev 和 Media Graph。不要因为两个文件都有 `probe` 就把它们当成同一个驱动。

## 从第二次匹配进入逻辑对象

HW probe 调用 `platform_driver_register(&rockchip_csi2_dphy_driver)` 后，Platform Core 用逻辑节点的 compatible 匹配第二个 driver，再回调：

```text
Platform Core
→ rockchip_csi2_dphy_probe(pdev)
→ rockchip_csi2_dphy_attach_hw(csi2dphy)
```

这里不是“一个 D-PHY 重复 probe 两次”：HW probe 管真实寄存器，逻辑 probe 管 V4L2/Media 对象。

## DTS 中的两层关系

```dts
csi2_dphy0: csi2-dphy0 {
    compatible = "rockchip,rk3568-csi2-dphy";
    rockchip,hw = <&csi2_dphy_hw>;
    status = "disabled";
};
```

板级 DTSI 启用它并提供 `ports`。`rockchip,hw` 是两层对象之间的桥，不是寄存器地址。

## 逻辑 probe 主线

```c
csi2dphy = devm_kzalloc(dev, sizeof(*csi2dphy), GFP_KERNEL);
csi2dphy->dev = dev;
csi2dphy->phy_index = of_alias_get_id(dev->of_node, "csi2dphy");

ret = rockchip_csi2_dphy_attach_hw(csi2dphy);
if (ret)
    return -ENODEV;

sd = &csi2dphy->sd;
mutex_init(&csi2dphy->mutex);
v4l2_subdev_init(sd, &csi2_dphy_subdev_ops);
sd->flags |= V4L2_SUBDEV_FL_HAS_DEVNODE;
snprintf(sd->name, sizeof(sd->name),
         "rockchip-csi2-dphy%d", csi2dphy->phy_index);
sd->dev = dev;
platform_set_drvdata(pdev, &sd->entity);

ret = rockchip_csi2dphy_media_init(csi2dphy);
```

结构体按生命周期逐步被填充：probe 写 `dev/phy_index`；attach 写 `dphy_hw`；subdev 初始化写 `sd`；media 初始化写 `pads/entity/notifier`；bound 再写 `sensors/num_sensors`。

vendor 代码有一个值得警惕的错误路径：`rockchip_csi2dphy_media_init()` 失败后清理资源却 `return 0`。所以“Platform 已绑定”不能替代成功日志和 Media Graph 验证。

## `attach_hw()` 的 phandle 链

```c
np = of_parse_phandle(dev->of_node, "rockchip,hw", 0);
if (!np || !of_device_is_available(np))
    return -ENODEV;

plat_dev = of_find_device_by_node(np);
of_node_put(np);
if (!plat_dev)
    return -ENODEV;

dphy_hw = platform_get_drvdata(plat_dev);
if (!dphy_hw)
    return -EINVAL;

dphy_hw->dphy_dev[dphy_hw->dphy_dev_num++] = dphy;
dphy->dphy_hw = dphy_hw;
```

大白话：phandle 先得到 HW `device_node`，再找到对应 `platform_device`，最后取回 HW probe 早先保存的 `drvdata`。

`phy_index == 0` 选择四 Lane FULL；dphy1/2 选择 SPLIT。第一个逻辑实例会确定共享 HW 的 lane mode，后续实例若请求不同模式则返回 `-ENODEV`。

## 为什么 HW 必须先准备好

若 HW `platform_device` 存在但 probe 尚未保存 drvdata，`platform_get_drvdata()` 会得到 `NULL`。本 BSP 把逻辑 driver 注册放到 HW probe 尾部，正是为了在注册前完成 MMIO、ops 与 drvdata 的准备。

## 本章学习总结：我为什么一开始觉得“看懂了又没懂”

我最开始把下面几件事混成了一条普通的 C 函数调用链：

```text
编译驱动 → 注册驱动 → DTS 匹配 → HW probe → 逻辑 probe
```

真正的困难不是某一行 C 代码，而是还没有稳定区分三种关系：

1. **直接函数调用**：源码中能看到 `函数名(...)`，例如逻辑 probe 直接调用 `rockchip_csi2_dphy_attach_hw()`。
2. **框架回调**：驱动只把 `.probe` 和 `.of_match_table` 交给 Platform 总线框架，匹配成功后由框架回调 probe，源码中不会出现一个普通函数直接调用它。
3. **对象引用**：DTS 的 `rockchip,hw = <&csi2_dphy_hw>` 只是在描述两个节点的关系，不是在调用 HW 驱动。

### 现在应当稳定记住的模型

```text
物理 HW 节点
  ↓ compatible 匹配
HW platform_driver
  ↓ HW probe：准备寄存器、时钟、GRF、stream ops
struct csi2_dphy_hw
  ↓ platform_set_drvdata() 保存

逻辑 csi2_dphy0 节点
  ↓ compatible 匹配
逻辑 platform_driver
  ↓ 逻辑 probe
rockchip_csi2_dphy_attach_hw()
  ↓ rockchip,hw phandle
device_node → platform_device → drvdata
  ↓
取得已经准备好的 struct csi2_dphy_hw
  ↓
继续创建 V4L2 Subdev、Media Entity、Pads 和异步匹配关系
```

关键结论：**不是同一个设备 probe 两遍，也不是逻辑 probe 反过来重新执行 HW probe。** 两个 DTS 节点对应两个 Platform 设备、两个驱动和两个私有对象；逻辑对象只是取用物理对象已经准备好的硬件能力。

### 为什么要拆成物理 HW 和逻辑 D-PHY

物理层集中管理共享寄存器、时钟、GRF 和 Lane 模式；逻辑层负责把 `csi2_dphy0/1/2` 表示成 Camera 管线中的 V4L2/Media 对象。这样可以避免多个逻辑实例重复映射寄存器、重复控制时钟或产生 FULL/SPLIT Lane 冲突。

### 面试优先级：本章必须能回答的 5 个问题

1. **`rockchip_csi2_dphy_probe()` 是谁调用的？**
   Platform 总线框架根据逻辑节点的 `compatible` 匹配到 `rockchip_csi2_dphy_driver` 后，回调其 `.probe`。

2. **`rockchip,hw = <&csi2_dphy_hw>` 是函数调用吗？**
   不是。它是 DTS phandle，描述逻辑 D-PHY 引用哪个物理 HW 节点。

3. **逻辑 probe 怎样取得 HW probe 创建的对象？**
   `of_parse_phandle()` 找 node，`of_find_device_by_node()` 找 platform_device，`platform_get_drvdata()` 取回 HW probe 保存的私有对象。

4. **为什么不能在逻辑 probe 中把物理资源重新初始化一次？**
   物理资源可能由多个逻辑 D-PHY 共享，重复初始化会带来寄存器、时钟和 Lane 模式冲突。

5. **HW probe 成功是否等于 Camera 链路已经建立？**
   不等于。它只说明物理 D-PHY 资源已准备；还要完成逻辑 probe、Subdev/Pad 初始化、异步绑定和 Media Link 创建。

### 面试时的一段完整表达

> RK3568 的 CSI2 D-PHY 驱动把物理硬件资源和 Camera 逻辑实例拆成两层。HW Platform Driver 先根据物理节点完成寄存器、时钟和 GRF 等资源初始化，并通过 drvdata 保存 `csi2_dphy_hw`。之后逻辑 Platform Driver 匹配 `csi2_dphy0`，在 probe 中根据 `rockchip,hw` phandle，经过 device_node、platform_device、drvdata 取回该 HW 对象，再继续初始化 V4L2 Subdev、Media Pads 和异步绑定。这里是两个设备对象之间的关联，不是同一个 probe 被调用两次。

### 后续复习触发点

如果再次把 DTS 当成“主动调用驱动”，或者疑惑“为什么源码里搜不到谁调用 probe”，就回到本节重新区分：**DTS 描述对象，driver 注册能力，Platform 总线框架负责匹配和回调。**

## 调用类型与 C 基础

- `.probe = rockchip_csi2_dphy_probe` 是**函数指针赋值**，不是调用；出现 `rockchip_csi2_dphy_probe(pdev)` 才是直接调用语法。
- `platform_driver_register()` 是直接调用；匹配成功后的 `.probe` 是框架回调；`rockchip,hw` 是对象关系。
- C 语言的 `struct platform_driver` 是结构体类型，`&rockchip_csi2_dphy_driver` 是取该对象地址，`->` 用于通过指针访问成员。

## 白话解释与板端证据边界

大白话解释：HW probe 先把“机房”准备好，逻辑 probe 再拿到机房钥匙并建立 Camera 框架窗口。两者不是互相调用。

板端执行 `dmesg | grep -E 'csi2-dphy|dphy'`：HW probe 成功日志能证明物理资源初始化函数返回成功；逻辑 probe 成功日志能证明 attach 和 Media 初始化主路径返回。它们不能证明 Sensor 已匹配或图像正在传输。
