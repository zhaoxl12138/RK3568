# D-PHY 从 DTS 到 Media Graph：源码陪读索引

> 配套概念章：[[01-课程主线/04-MIPI-CSI2-DPHY|MIPI CSI-2 / D-PHY]]

这组笔记按真实生命周期阅读 RK3568 内部 MIPI CSI-2 D-PHY 驱动。索引只保留总图、对象、源码事实基线、Source Insight 跳转顺序和六个模块入口；逐函数解释与代码摘录放在子文档。

## 完整调用总图

```text
module_platform_driver(rockchip_csi2_dphy_hw_driver)
        ↓ 注册 HW driver；Platform Core 匹配后回调
rockchip_csi2_dphy_hw_probe(pdev)
        ↓ HW probe 内直接调用
platform_driver_register(&rockchip_csi2_dphy_driver)
        ↓ 注册逻辑 driver；Platform Core 匹配后回调
rockchip_csi2_dphy_probe(pdev)
        ↓ 直接调用
rockchip_csi2_dphy_attach_hw(csi2dphy)
        ↓ 返回后继续初始化
v4l2_subdev_init(sd, &csi2_dphy_subdev_ops)
        ↓ probe 直接调用 Media 初始化
rockchip_csi2dphy_media_init(csi2dphy)
        ↓ 直接调用
media_entity_pads_init(...)
        ↓ 继续解析 port@0
v4l2_async_notifier_parse_fwnode_endpoints_by_port(...)
        ↓ 保存等待条件并执行 notifier register
v4l2_async_subdev_notifier_register(...)
        ↓ fwnode 匹配成功后由 V4L2 Async 回调
.bound() / rockchip_csi2_dphy_notifier_bound(...)
        ↓ 直接调用
media_create_pad_link(...)
```

这里混合了三种箭头，必须分清：源码中的直接调用、Platform Core 的驱动模型回调、V4L2 Async 的异步回调。注册只把对象交给框架，不等于在当前代码行直接调用回调。

最终希望看到的运行时关系：

```text
IMX415 pad0: Source
        → rockchip-csi2-dphy0 pad0: Sink
        → rockchip-csi2-dphy0 pad1: Source
        → rkisp-csi-subdev
```

## 三个对象不要混淆

| 对象 | 驱动模型 | DTS 节点 | C 结构体 | 职责 |
|---|---|---|---|---|
| D-PHY 物理硬件 | Platform device/driver | `csi2-dphy-hw@fe870000` | `struct csi2_dphy_hw` | 寄存器、时钟、Lane 模式、真正的 stream_on/off |
| D-PHY 逻辑接口 | Platform driver + V4L2 subdev | `csi2-dphy0` | `struct csi2_dphy` | subdev、pad、endpoint、Sensor 绑定 |
| IMX415 | I2C driver + V4L2 subdev | `imx415@1a` | `struct imx415` | 产生 RAW10，作为 D-PHY 上游 Sensor |

一句话：`csi2_dphy_hw` 是操作 RK3568 D-PHY 寄存器的硬件对象，`csi2_dphy0` 是放进 V4L2/Media Graph 的逻辑对象。

## Source Insight 防迷路：先文件，再定义，再调用

Source Insight 的 `Project Symbols` 是**全工程搜索**。搜索通用宏时会把所有子系统的使用点都列出来，例如搜索 `module_platform_driver` 会看到几十甚至几百个无关驱动。不要从这些结果逐个打开。

记住这条规则：

```text
通用名字：先不要搜
唯一结构体/函数名：优先搜
```



### 第一眼不要点开的结果

```text
module_platform_driver
platform_driver_register
v4l2_subdev_init
media_entity_pads_init
```

这些是通用框架 API 或宏，会有大量结果。要理解实现时再根据上表进入对应文件；追当前 D-PHY 时先用 `rockchip_csi2_dphy_*` 唯一前缀把范围缩小。

### 推荐实际操作

```text
1. Project Files 中打开 phy-rockchip-csi2-dphy-hw.c
2. 搜索 rockchip_csi2_dphy_hw_driver
3. 从 .probe 跳到 rockchip_csi2_dphy_hw_probe
4. 记录它注册的下一个 driver：rockchip_csi2_dphy_driver
5. 打开 phy-rockchip-csi2-dphy.c
6. 搜索 rockchip_csi2_dphy_probe
7. 依次追 attach_hw → media_init → notifier_bound
```

搜索结果里看到 `platform_device.h` 的 `module_platform_driver`，只把它当作“通用宏定义”；看到 `drivers/media/...` 的其他厂商驱动，先跳过。

## 调用类型、白话与证据边界

- **直接调用**：源码中能看到 `foo()`；**框架回调**：只看到 `.probe/.bound` 函数指针赋值；**对象关系**：`rockchip,hw` 和 `remote-endpoint` 只表达引用；**注册**：把对象交给框架，不等于立即执行全部回调。
- 大白话解释：HW 对象是“共享硬件仓库”，逻辑 D-PHY 是“Camera 管线里的接口对象”，Async 是“登记条件后立即返回、对象到齐再通知”的非阻塞机制。
- 板端证据：`probe successfully` 能证明对象初始化返回成功；`dphy0 matches` 能证明 Async 已匹配；`[ENABLED]` 能证明软件 link 已启用。它们都不能单独证明 MIPI 电气、包传输和稳定出帧正常。

## 面试问题

为什么 D-PHY 要拆 HW 和逻辑两层？`remote-endpoint` 如何变成运行时 link？

**我的回答：**

>

<mark>高亮正确答案：HW 层统一管理共享寄存器、时钟和 Lane 模式；逻辑层创建 V4L2/Media 对象。Endpoint 先被解析成 Async fwnode 等待条件，匹配到 IMX415 后由 `.bound()` 调用 `media_create_pad_link()` 建立运行时边。</mark>
