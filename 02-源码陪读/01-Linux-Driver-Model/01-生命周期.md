# 01-01 生命周期：device/driver 怎样进入总线

## Source Insight 定位顺序

1. `drivers/base/core.c` 搜 `device_register`，再看 `device_add`。
2. `drivers/base/driver.c` 搜 `driver_register`。
3. `drivers/base/bus.c` 搜 `bus_probe_device`、`bus_add_driver`。
4. `drivers/base/dd.c` 搜 `__device_attach_driver`、`__driver_attach`。

不要先搜全工程的 `module_platform_driver`；同名使用点很多。先进入具体驱动文件，再从它的唯一 driver 结构体往框架走。

## 两个起点，谁先来都可以

```text
设备先来：device_add() → bus_probe_device() → 遍历已有 driver
驱动先来：bus_add_driver() → driver_attach() → 遍历已有 device
                                    ↓
                         driver_match_device(drv, dev)
```

## 原始代码陪读

```c
int device_register(struct device *dev)
{
    device_initialize(dev); // 初始化引用计数、kobject 等；直接调用
    return device_add(dev); // 加到系统；直接调用
}

int driver_register(struct device_driver *drv)
{
    /* 先检查 drv->bus 已初始化，再把 driver 加到总线 */
    return bus_add_driver(drv); // 直接调用，不是硬件寄存器操作
}
```

## 调用类型

| 表达式 | 类型 | 说明 |
|---|---|---|
| `device_initialize(dev)` | 直接调用 | 当前函数立即进入其函数体 |
| `drv->bus = &i2c_bus_type` | 字段赋值/对象关系 | 指定驱动属于 I2C bus |
| `.match = i2c_device_match` | 函数指针赋值 | 给总线保存匹配规则 |
| `bus->match(dev, drv)` | 框架回调 | Driver Core 在需要匹配时执行规则 |

### C 基础：初始化和注册不是一回事

初始化主要让一个内存对象处于可用状态；注册会把它放入框架可发现的集合，并可能触发副作用，例如匹配。`device_register()` 把这两步包装在一起，底层也可分别调用 `device_initialize()` 和 `device_add()`。

## 大白话解释

设备和驱动就像求职者与岗位。谁先在系统里登记都可以；另一方到达时，人事系统遍历已有对象做配对。登记不等于上岗，match 成功并完成 probe 才算绑定。

## 板端证据能/不能证明

```bash
find /sys/bus/i2c/devices/4-001a-1 -maxdepth 1 -type l -ls
ls -l /sys/bus/i2c/drivers/imx415
```

- devices 下的 client：能证明 device 已注册。
- drivers 下的 driver 目录：能证明 driver 已注册。
- 互相的符号链接：能证明已经绑定。
- 上述都不能替代 Sensor ID 日志和成功抓帧。

## 面试问题

如果 IMX415 driver 比 `i2c_client` 先注册，会不会因为当时没有设备而永久错过 probe？

**我的回答：**


<mark>高亮正确答案：不会。driver 注册时会匹配已有 device；后续新 device 加入 bus 时也会匹配已有 driver。只要双方最终都存在且规则匹配，就有机会进入 probe；依赖未就绪还可返回 -EPROBE_DEFER。</mark>
