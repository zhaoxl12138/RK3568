## 代码片段：注册时补齐通用字段

```c
int __platform_driver_register(struct platform_driver *drv, struct module *owner)
{
    drv->driver.bus = &platform_bus_type;      // 字段赋值：归属 Platform bus
    drv->driver.probe = platform_drv_probe;    // 字段赋值：通用包装入口
    return driver_register(&drv->driver);      // 直接调用：进入 Driver Core
}

int i2c_register_driver(struct module *owner, struct i2c_driver *driver)
{
    driver->driver.bus = &i2c_bus_type;         // 字段赋值：归属 I2C bus
    return driver_register(&driver->driver);    // 直接调用：进入同一 Driver Core
}
```

厂商 `.probe` 没丢：它仍保存在外层 `platform_driver.probe` 或 `i2c_driver.probe`，包装函数转换参数后再回调。

### C 基础：同名层级

外层结构体和内嵌结构体都可能有 `probe` 相关字段。看代码时先确认当前变量类型：`drv->probe` 是 Platform 专用回调，`drv->driver.probe` 是通用 `device_driver` 包装入口。

## 大白话调试树

```text
没有 device 对象
→ 查运行时 DTS、status、I2C adapter/OF populate

有 device、没有 driver
→ 查 CONFIG、内建/ko、模块加载、driver 注册日志

两者都有、没有绑定
→ 查 bus 归属、compatible、of_match_table

已经绑定、probe 报错
→ 查资源获取、-EPROBE_DEFER、硬件访问和失败清理
```

## 板端证据能/不能证明

```bash
ls -l /sys/bus/i2c/devices/4-001a-1
ls -l /sys/bus/i2c/drivers/imx415
dmesg | grep -Ei 'defer|probe|imx415|csi2-dphy|rkisp'
```

能证明对象是否存在、是否绑定、probe 是否打印过日志；不能凭“driver 已注册”推断该 driver 一定找到了设备，也不能凭 compatible 匹配断言真实芯片型号正确。

## 面试问题

请用一分钟解释为什么 I2C 控制器通常是 Platform Driver，而挂在它下面的 IMX415 是 I2C Driver。

**我的回答：**


<mark>高亮正确答案：I2C 控制器是 SoC 内部固定 MMIO、IRQ、clock 资源的硬件，通常由 Platform Driver 初始化并注册 i2c_adapter；IMX415 是该 adapter 下地址 0x1a 的外部从设备，由 OF/I2C Core 创建 i2c_client，再与 i2c_driver 匹配。两者最终共享 Driver Core，但专用总线对象和 probe 参数不同。</mark>
