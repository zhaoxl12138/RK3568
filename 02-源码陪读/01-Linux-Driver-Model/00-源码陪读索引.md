## 一张主图

```text
device_register/device_add ──→ bus 中的 device 集合 ─┐
                                                    ├→ match → really_probe
driver_register/bus_add_driver → bus 中的 driver 集合 ┘
                                                    ↓
                              I2C 或 Platform 的 probe 包装
                                                    ↓
                                          厂商 driver.probe
```

## 带中文注释的核心代码

```c
int driver_register(struct device_driver *drv)
{
    return bus_add_driver(drv); // 直接调用：把 driver 加入 drv->bus
}

int device_register(struct device *dev)
{
    device_initialize(dev);     // 直接调用：初始化通用 device
    return device_add(dev);     // 直接调用：加入 bus，并触发匹配机会
}
```

> 调用类型：上面都是直接调用；`bus->match(dev, drv)` 和 `bus->probe(dev)` 是框架通过函数指针回调；`drv->bus = &i2c_bus_type` 是字段赋值与对象关系。

### C 基础

Linux 用“大结构体包含小结构体”和 `container_of()` 在通用 `struct device_driver`、`struct device` 与 I2C/Platform 专用对象之间转换。这样 Driver Core 只认识通用接口，各总线仍能保留自己的参数。

## 大白话解释

`driver_register()` 不是寄存器访问。这里 register 的意思是“登记”：把一份驱动对象交给 Linux 管理。register 只有在寄存器语境如 `readl()`/`writel()` 时才可能译成“寄存器”。

## 板端证据边界

```bash
ls /sys/bus/platform/devices | grep -E 'csi|isp'
ls /sys/bus/i2c/devices | grep 4-001a
readlink -f /sys/bus/i2c/devices/4-001a-1/driver
```

- 能证明：总线中的对象和绑定结果。
- 不能证明：单看 driver 目录就证明具体硬件已经响应，也不能证明 Camera 已出图。

## 面试问题

DTS 会不会先读取 `compatible`，然后只选择匹配的驱动进行编译和注册？

**我的回答：**


<mark>高亮正确答案：不会。Kconfig/Makefile 决定驱动是否编译；built-in 在内核初始化时注册，模块在加载时注册。DTS 负责描述并创建 device；device 与已注册 driver 同时存在后，bus 才按 compatible 等规则匹配。</mark>
