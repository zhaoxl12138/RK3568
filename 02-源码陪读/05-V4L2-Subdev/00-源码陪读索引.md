# IMX415 V4L2 Subdev：源码陪读索引

## 本阶段解决什么

前一阶段已经说明了 D-PHY 怎样成为 Camera 管线中的 subdev。本阶段回到 Sensor 驱动，回答：

```text
imx415.c 中已经写好的能力
怎样被整理成 V4L2 Sensor Subdev，
又怎样在格式、控制和开流请求到来时被框架调用？
```

## 先记住三个入口，不要把它们混成“一次全部注册”

```text
入口 A：I2C Driver 生命周期
imx415_i2c_driver
├─ .probe  = imx415_probe
├─ .remove = imx415_remove
└─ .driver.pm = imx415_pm_ops

入口 B：V4L2 Subdev 操作能力
imx415_subdev_ops
├─ .core  = imx415_core_ops
├─ .video = imx415_video_ops
└─ .pad   = imx415_pad_ops

入口 C：V4L2 Controls
imx415_ctrl_ops
└─ .s_ctrl = imx415_set_ctrl
```

大白话：同一个 `imx415.c` 同时参加了 I2C 总线框架和 V4L2 Camera 框架，但它不是在一次注册中把所有函数执行掉。每张 ops 表只是先保存“以后遇到哪种请求要找谁”。

不要直接搜索 `probe`、`ops`、`s_stream` 这类全局通用名字。先打开上面的精确文件，再按下表搜索唯一符号：

| 顺序 | 文件 | 搜索符号 | 这一站要看懂什么 |
|---|---|---|---|
| 1 | `imx415.c` | `sensor_mod_init` | `device_initcall_sync` 何时进入注册入口，`i2c_add_driver` 为什么不等于直接调用 probe |
| 2 | 同上 | `imx415_i2c_driver` | `.probe/.remove/.pm/of_match_table` 都是函数指针或表地址赋值 |
| 3 | 同上 | `imx415_probe` | client、DTS、私有对象、资源、subdev、controls、pad、Async 如何依次组装 |

| 5 | `v4l2-subdev.c` | `v4l2_subdev_init` | 真正执行 `sd->ops = ops` 的通用函数；它只存表地址，不执行 ops |

## 总调用图：先看静态准备，再看运行时回调

```text
【启动/模块加载阶段】
device_initcall_sync(sensor_mod_init)
        ↓ 让内核在初始化阶段执行入口
sensor_mod_init()
        ↓ 直接调用
i2c_add_driver(&imx415_i2c_driver)
        ↓ 注册 I2C Driver；这里不直接调用 probe
I2C 总线框架匹配 compatible
        ↓ 框架回调
imx415_probe(client, id)
        ├─ 准备 IMX415 私有对象和硬件资源
        ├─ v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops)
        │      └─ 建立 sd/client 关系，并挂接 subdev_ops
        ├─ imx415_initialize_controls(imx415)
        │      └─ 建立 controls，并挂接 imx415_ctrl_ops
        ├─ media_entity_pads_init(...)
        │      └─ 建立一个 Source Pad
        └─ v4l2_async_register_subdev_sensor_common(sd)
               └─ 把 Sensor subdev 放入 V4L2 Async 匹配体系

【未来格式/控制/开流请求到来】
V4L2 框架
        ├─ pad.set_fmt  → imx415_set_fmt()
        ├─ ctrl.s_ctrl  → imx415_set_ctrl()
        └─ video.s_stream → imx415_s_stream()
                               └─ __imx415_start_stream()
```

## 适合当前薄弱点的看码规则

每遇到一行，先贴标签：

| 标签     | 判断方式               | 示例                                |
| ------ | ------------------ | --------------------------------- |
| 对象定义   | 只是在内存中描述一个对象       | `static struct i2c_driver ...`    |
| 函数指针赋值 | `成员 = 函数名`，没有执行函数体 | `.probe = &imx415_probe`          |
| 直接调用   | 有 `函数名(...)`       | `i2c_add_driver(...)`             |
| 框架回调   | 源码中找不到普通上层直接调用     | I2C 框架调用 `imx415_probe()`         |
| 对象关联   | 两个结构体以后能互相找到       | `i2c_set_clientdata(client, sd)`  |
| 框架注册   | 把准备好的对象放入框架可见集合    | `v4l2_async_register_subdev...()` |

## 本阶段不追什么

- 不逐字节追 `imx415_write_reg()`。
- 不背全部寄存器表。
- 不深入每个 V4L2 ioctl 的通用实现。
- 不把 Media Controller 的完整拓扑抢到本阶段；它属于阶段 06。

先把“谁把什么对象交给谁、谁在什么时候回调谁”讲清楚，再进入细节。

## 板端证据与面试问题

`/dev/v4l-subdev3` 和 `media-ctl -p` 中的 Sensor entity 能证明 Sensor subdev 已注册并进入图；不能证明 `s_stream(1)` 已执行或 RAW 数据稳定到达。

**面试问题：** 同一个 `imx415.c` 中的 I2C Driver、subdev_ops 和 ctrl_ops 是一次全部执行的吗？

**我的回答：**



<mark>高亮正确答案：不是。I2C Driver 负责生命周期；probe 中把 subdev_ops 和 ctrl_ops 的函数地址挂到对象上；格式、控制和开流请求到来时，V4L2 再通过对应函数指针回调。</mark>
