# 第 01 章：驱动注册与 Subdev 组装

## 大白话解释

**这一章是在给 IMX415 办两张证件：I2C 身份让 Linux 找到并控制芯片，V4L2 Subdev 身份让 Camera 框架以后按 ops 调格式、控制和开流回调。**

> 返回：[[02-源码陪读/05-V4L2-Subdev/00-源码陪读索引|IMX415 V4L2 Subdev 源码陪读索引]]

## 本节目标

只追一条线：

```text
IMX415 I2C Driver 被注册
→ I2C 框架匹配后进入 probe
→ probe 取出内嵌的 v4l2_subdev
→ 把 client、sd 和 imx415_subdev_ops 组装起来
→ 建 Source Pad
→ 注册 Sensor subdev
```

本节不追 `imx415_s_stream()` 的寄存器细节。

## 一、Source Insight 从哪里开始

直接打开：

```text
drivers/media/i2c/imx415.c
```

搜索唯一符号：

```text
device_initcall_sync(sensor_mod_init)
```

不要先全工程搜索 `probe`、`register` 或 `ops`，这些公共词会命中大量无关驱动。

## 二、第一段：声明 I2C Driver 的能力

源码位置：`imx415.c:2597–2632`（当前 E 盘学习副本）。

```c
static const struct of_device_id imx415_of_match[] = {
    { .compatible = "sony,imx415" }, // DTS compatible 的匹配表项
    {},                               // 空表项，表示数组结束
};

static struct i2c_driver imx415_i2c_driver = {
    .driver = {
        .name = IMX415_NAME,                         // 驱动模型中的名字
        .pm = &imx415_pm_ops,                        // 保存运行时电源管理回调表地址
        .of_match_table = of_match_ptr(imx415_of_match), // 保存 DTS 匹配表地址
    },
    .probe    = &imx415_probe,  // 函数指针赋值：匹配成功后由 I2C 框架回调
    .remove   = &imx415_remove, // 函数指针赋值：解绑时由 I2C 框架回调
    .id_table = imx415_match_id,
};

static int __init sensor_mod_init(void)
{
    return i2c_add_driver(&imx415_i2c_driver); // 直接调用：注册整个 I2C Driver 对象
}

device_initcall_sync(sensor_mod_init); // 把 sensor_mod_init 声明为内核初始化入口
```

### 逐行边界

```text
i2c_add_driver(&imx415_i2c_driver)
```

这是直接函数调用。它把整个 driver 对象交给 I2C 总线框架。注册后，框架会检查总线上已有的 I2C device/client；当 `sony,imx415` 匹配成功时，框架才从 `.probe` 成员取出函数地址并回调 `imx415_probe(client, id)`。

> [!important] 本节第一条结论
> **注册 I2C Driver 不等于直接调用 probe。** 注册是“把对象交给框架”；probe 是匹配成功后的框架回调。

### `init`、`register`、`probe` 不要再混

| 词        | 本段含义                          | 当前函数                       |
| -------- | ----------------------------- | -------------------------- |
| init     | 内核/模块初始化入口                    | `sensor_mod_init()`        |
| register | 把 Driver 对象交给 I2C 框架管理        | `i2c_add_driver()` 内部的注册流程 |
| probe    | device 与 driver 匹配成功后的设备初始化回调 | `imx415_probe()`           |

因此：**init 不等于 register，register 也不等于 probe。** `sensor_mod_init()` 只是入口；它内部调用注册 API；匹配成功后框架才回调 probe。

## 三、第二段：为什么 `imx415` 里面要内嵌 `subdev`

进入 `imx415_probe()` 后：

```c
imx415 = devm_kzalloc(dev, sizeof(*imx415), GFP_KERNEL);
if (!imx415)
    return -ENOMEM;

imx415->client = client;

sd = &imx415->subdev;
v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops);
```

### 对象关系

`struct imx415` 是 IMX415 驱动的完整对象，里面保存两类信息：

```
IMX415 自己需要的信息
├─ I2C client
├─ 时钟、GPIO、电源
├─ 当前分辨率和工作模式
└─ 是否正在开流

V4L2 框架需要认识的对象
├─ v4l2_subdev
├─ controls
└─ Source Pad
```

可以把它理解为：

> `imx415` 是完整的 Camera 驱动对象，`subdev` 是它交给 V4L2 框架使用的标准接口。

```
sd = &imx415->subdev;
```

这行只是让 `sd` 指向 `imx415` 内部的 `subdev`，没有复制或创建新对象。

接着：

```
v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops);
```

建立三组关系：

```
sd → imx415_subdev_ops
sd → I2C client
I2C client → sd
```

以后 V4L2 要设置格式或开流时，只会把通用的 `sd` 传给驱动：

```
imx415_s_stream(struct v4l2_subdev *sd, int on)
```

驱动再通过：

```
struct imx415 *imx415 = to_imx415(sd);
```

从 `sd` 找回完整的 `imx415` 对象，从而使用其中的 I2C、时钟、GPIO和当前模式。

一句话总结：

> V4L2 通过 `subdev` 找到并调用 Camera；IMX415 驱动通过 `subdev` 找回自己的完整硬件资源和运行状态。

## 四、第三段：`v4l2_i2c_subdev_init()` 究竟组装什么

IMX415 probe 直接调用：

```c
v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops);
```

三个参数：

| 参数                   | 是什么                    | 从哪里来               |
| -------------------- | ---------------------- | ------------------ |
| `sd`                 | 待初始化的 V4L2 subdev      | `&imx415->subdev`  |
| `client`             | 当前 IMX415 的 I2C client | I2C 框架调用 probe 时传入 |
| `&imx415_subdev_ops` | IMX415 的 V4L2 能力表      | `imx415.c` 中静态定义   |

进入 `drivers/media/v4l2-core/v4l2-common.c`：

```c
void v4l2_i2c_subdev_init(struct v4l2_subdev *sd,
                          struct i2c_client *client,
                          const struct v4l2_subdev_ops *ops)
{
    v4l2_subdev_init(sd, ops);          // 初始化 sd，并在内部执行 sd->ops = ops
    sd->flags |= V4L2_SUBDEV_FL_IS_I2C; // 标记它是 I2C 类型 subdev
    sd->owner = client->dev.driver->owner;
    sd->dev = &client->dev;             // subdev 记住底层 Linux device
    v4l2_set_subdevdata(sd, client);     // sd → client
    i2c_set_clientdata(client, sd);      // client → sd
    snprintf(sd->name, sizeof(sd->name), "%s %d-%04x", ...);
}
```

最重要的不是只盯 `sd->ops = ops`，而是看见它完成三组关系：

```text
1. 能力关系：sd → imx415_subdev_ops
2. 设备关系：sd ↔ i2c_client
3. 身份关系：sd 被标成 I2C subdev，并得到运行时名称
```

### 它没有做什么

- 没有执行 `imx415_set_fmt()`。
- 没有执行 `imx415_s_stream()`。
- 没有把 Sensor 注册进 Async 全局列表。
- 没有创建 Sensor 到 D-PHY 的 Media Link。

它的职责是**初始化并组装对象**，不是完成全部 Camera 注册。

## 五、第四段：把能力表挂到 `sd`

```c
/* video ops：与“视频运行状态”有关的操作集合。
 * 注意：这里只是在表中保存函数地址，没有执行这些函数。 */
static const struct v4l2_subdev_video_ops imx415_video_ops = {
    // V4L2 请求开流或停流时，框架回调 imx415_s_stream(sd, on)
    .s_stream = imx415_s_stream,

    // V4L2 查询当前帧间隔/帧率时，框架回调该函数
    .g_frame_interval = imx415_g_frame_interval,

    // V4L2 查询 Sensor 的 MIPI CSI-2 总线配置时，框架回调该函数
    .g_mbus_config = imx415_g_mbus_config,
};

/* pad ops：与 Sensor 图像输出端口有关的操作集合。
 * IMX415 的 pad 是 Source Pad，负责向 D-PHY 输出 RAW 数据。 */
static const struct v4l2_subdev_pad_ops imx415_pad_ops = {
    // 枚举 Source Pad 支持的 Media Bus Code，例如 SGBRG10_1X10
    .enum_mbus_code = imx415_enum_mbus_code,

    // 查询 TRY 格式或当前已经保存的 ACTIVE 格式
    .get_fmt = imx415_get_fmt,

    // 根据请求选择 supported_modes，并保存格式；此时还没有真正开流
    .set_fmt = imx415_set_fmt,
};

/* subdev 总操作表：把 core、video、pad 三类能力汇总到一个入口。
 * & 表示取子表地址；这些语句是对象关联，不是函数调用。 */
static const struct v4l2_subdev_ops imx415_subdev_ops = {
    // 通用控制能力，例如电源管理和私有 ioctl
    .core  = &imx415_core_ops,

    // 开停流、帧间隔和总线配置能力
    .video = &imx415_video_ops,

    // 图像格式、分辨率和输出端口能力
    .pad   = &imx415_pad_ops,
};
```

`ops` 是 **operations（操作/操作集合）** 的缩写。

这里所有 `=` 都是在建立函数指针或子表关系，不是在执行右侧函数。最终：

```text
sd->ops
  → imx415_subdev_ops
       ├─ video->s_stream → imx415_s_stream
       └─ pad->set_fmt    → imx415_set_fmt
```

未来 V4L2 框架收到开流请求，才会沿 `sd->ops->video->s_stream` 找到并调用 `imx415_s_stream()`。

## 六、第五段：从一个 `sd` 变成 Media Graph 中可匹配的 Sensor

这里不能简单记成“注册 V4L2”。`imx415_probe()` 实际连续完成了三个不同层次的动作：

```text
第一层：subdev 对象已经有操作能力
v4l2_i2c_subdev_init()
        ↓
第二层：subdev 对应的 Media Entity 有一个图像输出口
media_entity_pads_init()
        ↓
第三层：Sensor subdev 进入 V4L2 Async 全局可匹配集合
v4l2_async_register_subdev_sensor_common()
```

### 6.1 先声明：IMX415 是什么 Entity，数据从哪个端口出去

```c
// pad 的方向是 Source：图像数据从 IMX415 向外输出
imx415->pad.flags = MEDIA_PAD_FL_SOURCE;

// entity 的功能类型是 Camera Sensor
sd->entity.function = MEDIA_ENT_F_CAM_SENSOR;

// 给 sd->entity 安装一个 pad，pad 数量为 1
ret = media_entity_pads_init(&sd->entity, 1, &imx415->pad);
```

这三行建立的是：

```text
IMX415 Media Entity
└─ pad0: Source
```

`media_entity_pads_init()` 内部最关键的关系是：

```c
entity->num_pads = num_pads;   // 这个 Entity 有几个 pad
entity->pads = pads;           // Entity 保存 pad 数组地址

pads[i].entity = entity;       // 每个 pad 反向指回所属 Entity
pads[i].index = i;             // 当前 pad 在 Entity 中的编号
```

因此它建立的是 **Entity 与 Pad 的归属关系**，不是上下游连接关系。

此时只有：

```text
IMX415 entity
└─ pad0 Source
```

还没有：

```text
IMX415 pad0 Source → D-PHY pad0 Sink
```

也就是说，Pad 相当于先把“插口”安装好；Link 才是以后把两端插口连接起来的“线”。

### 6.2 再把 Sensor subdev 注册进 V4L2 Async

```c
ret = v4l2_async_register_subdev_sensor_common(sd);
```

这个 helper 不是阻塞等待函数。它做完登记就返回，后面哪一方先注册都可以。

内部流程可以拆成：

```text
v4l2_async_register_subdev_sensor_common(sd)
    │
    ├─ kzalloc(notifier)
    │     给 Sensor 自己申请一个 notifier
    │
    ├─ v4l2_async_notifier_parse_fwnode_sensor_common(...)
    │     解析 flash-leds、lens-focus、ir-cut 等 Sensor 附属设备引用
    │
    ├─ v4l2_async_subdev_notifier_register(sd, notifier)
    │     把这个附属设备 notifier 挂到 Sensor subdev
    │
    ├─ v4l2_async_register_subdev(sd)
    │     把 IMX415 sd 放进 Async 全局 subdev 集合，并立即尝试匹配已有 notifier
    │
    └─ sd->subdev_notifier = notifier
          保存 Sensor 自己的附属设备 notifier
```

这里必须纠正一个容易混淆的理解：

> `v4l2_async_notifier_parse_fwnode_sensor_common()` 主要解析闪光灯、镜头马达、IR-CUT 等 Sensor 附属设备，不负责解析 IMX415 到 D-PHY 的 `remote-endpoint`。

IMX415 到 D-PHY 的 endpoint，是 **D-PHY 驱动**解析的。

### 6.3 真正“等待 IMX415”的是 D-PHY notifier

D-PHY probe 的 Media 初始化会执行：

```c
ret = v4l2_async_notifier_parse_fwnode_endpoints_by_port(
        dphy->dev,
        &dphy->notifier,
        sizeof(struct sensor_async_subdev),
        0,
        rockchip_csi2_dphy_fwnode_parse);

dphy->notifier.ops = &rockchip_csi2_dphy_async_ops;

ret = v4l2_async_subdev_notifier_register(
        &dphy->sd,
        &dphy->notifier);
```

它解析 D-PHY 的 `port@0`，沿 `remote-endpoint` 找到 IMX415 endpoint，并生成一个 Async 等待条件，可以白话理解为：

```text
D-PHY notifier：
“我要找 fwnode 等于 imx415_out 的 Sensor subdev。”
```

与此同时，IMX415 执行：

```c
v4l2_async_register_subdev(sd);
```

可以理解为：

```text
IMX415：
“我的 fwnode 是运行时 imx415@1a 对应的固件节点，我已经可以被匹配了。”
```

**Async 框架会比较 D-PHY notifier 的等待条件和已经注册的 Sensor subdev。无论 D-PHY 先注册还是 IMX415 先注册，后到的一方都会触发一次匹配尝试，所以这里不需要阻塞等待。**

### 6.4 匹配成功后才进入 `.bound()` 并创建 Link

D-PHY 注册了下面这张回调表：

```c
static const struct v4l2_async_notifier_operations
rockchip_csi2_dphy_async_ops = {
    // 函数指针赋值：匹配成功后由 Async 框架回调
    .bound = rockchip_csi2_dphy_notifier_bound,
    .unbind = rockchip_csi2_dphy_notifier_unbind,
};
```

匹配成功后，Async 框架回调：

```text
rockchip_csi2_dphy_notifier_bound(notifier, imx415_sd, asd)
        │
        ├─ 保存 Sensor subdev 指针
        ├─ 保存 data-lanes 和总线类型
        ├─ 找到 IMX415 的 Source Pad
        └─ media_create_pad_link(...)
```

最后才得到：

```text
IMX415 entity pad0 Source
        ───────────────→
rockchip-csi2-dphy0 pad0 Sink
```

所以这几步的边界必须分清：

| 函数                                           | 建立了什么                                      | 还没有建立什么                         |
| -------------------------------------------- | ------------------------------------------ | ------------------------------- |
| `v4l2_i2c_subdev_init()`                     | `sd->ops`、`sd ↔ client`                    | 没有 Pad、Link，也没有开流               |
| `media_entity_pads_init()`                   | Sensor Entity 和 Source Pad                 | 没有连接到 D-PHY                     |
| `v4l2_async_register_subdev_sensor_common()` | Sensor 对 Async 可见；并处理 Sensor 附属设备 notifier | 不直接解析 D-PHY endpoint，不直接创建 Link |
| D-PHY endpoint 解析与 notifier 注册               | 建立“等待哪个 Sensor”的条件                         | Sensor 未出现时不会阻塞，也还没有 Link       |
| D-PHY `.bound()`                             | 保存 Sensor，并创建 Sensor→D-PHY Media Link      | Link 成功仍不能证明 MIPI 已稳定出帧         |

### 6.5 用一句白话记住

> `v4l2_i2c_subdev_init()` 是给 IMX415 装上 V4L2 操作说明书；`media_entity_pads_init()` 是给它安装一个 RAW 输出插口；Async 注册是让系统知道这个 Sensor 已经出现；D-PHY notifier 根据 DTS endpoint 找到它；最后由 D-PHY 的 `.bound()` 把两个 Pad 真正连成 Media Link。

## 七、把本节压成一张对象图

```text
I2C 总线框架
    │ 匹配成功后回调
    ▼
imx415_probe(client, id)
    │
    ├─ 创建 struct imx415
    │      ├─ 保存 client
    │      ├─ 内嵌 subdev
    │      ├─ 内嵌 pad
    │      └─ 保存 controls / mode / 电源资源
    │
    ├─ v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops)
    │      ├─ sd->ops = &imx415_subdev_ops
    │      └─ sd ↔ client
    │
    ├─ media_entity_pads_init(...)
    │      └─ Sensor entity 有一个 Source Pad
    │
    └─ v4l2_async_register_subdev_sensor_common(sd)
           └─ Sensor subdev 对 Async 框架可见
```

## 八、第一轮问题

### 面试问题

下面三题都按面试口述标准回答：先说谁保存函数地址，再说框架何时真正回调。

请先自己回答，我会按你的规则把高亮正确答案补在原回答下面。

### 问题 1

```c
.probe = &imx415_probe,
```

这行是在调用 `imx415_probe()`，还是保存函数地址？真正是谁、在什么时候调用它？

> [!question] 我的回答
> 保存函数地址 。dts跟i2cclient 匹配成功后再调用

> [!success] 高亮正确答案
> 第一半正确：`.probe = &imx415_probe` 只是把函数地址保存到 `imx415_i2c_driver.probe`，此刻不会执行函数体。第二半需要修正为：DTS 先使 I2C Core 创建带 `of_node/compatible` 的 `i2c_client`；IMX415 `i2c_driver` 注册后，Linux Driver Core/I2C Core 比较设备与驱动的匹配表，匹配成功才通过 I2C 总线的 probe 包装层回调 `imx415_probe(client, id)`。不是“i2c_client probe 成功后”再调用，因为 `imx415_probe()` 本身就是该 client 与驱动绑定阶段的 probe 回调。

### 问题 2

```c
sd = &imx415->subdev;
```

`sd`、`imx415`、`imx415->subdev` 三者是什么关系？这里有没有复制结构体？

> [!question] 我的回答
> 只取了地址。没有复制结构体
>

> [!success] 高亮正确答案
> 回答正确。`imx415` 指向整个 Sensor 私有对象；`imx415->subdev` 是内嵌在该对象中的 `struct v4l2_subdev` 成员；`&imx415->subdev` 取得这个成员在原对象中的地址并赋给局部指针 `sd`。没有分配新 subdev，也没有复制结构体，所以通过 `sd` 修改字段，就是在修改同一个 `imx415->subdev`。

### 问题 3

```c
v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops);
```

这行建立了哪三组关系？它是否已经执行了 `imx415_set_fmt()` 和 `imx415_s_stream()`？

> [!question] 我的回答
> 只是ops操作表地址赋值，并没有执行

> [!success] 高亮正确答案
> “没有执行 `set_fmt/s_stream`”判断正确，但“三组关系”回答不完整。该 helper 先用 `v4l2_subdev_init(sd, ops)` 建立 `sd → imx415_subdev_ops` 能力表关系；再用 `v4l2_set_subdevdata(sd, client)` 建立 `sd → client`；最后用 `i2c_set_clientdata(client, sd)` 建立 `client → sd`，形成双向查找。它还设置 I2C 标志、owner、dev 和名字。这里只组装对象；以后格式或开流请求到来时，V4L2 才通过 ops 函数指针分别回调 `imx415_set_fmt()`、`imx415_s_stream()`。

## 九、面试优先级

### 必须会说

> IMX415 先以 `i2c_driver` 注册，I2C 总线框架匹配 `compatible` 后回调 `imx415_probe()`。probe 创建私有对象，并通过 `v4l2_i2c_subdev_init()` 把内嵌的 `v4l2_subdev`、I2C client 和 `imx415_subdev_ops` 关联起来；随后建立 Sensor Source Pad，并把 subdev 注册进 V4L2 Async 框架。ops 中的格式和开流函数只是保存为回调，只有对应请求到来时才执行。

## 板端证据边界

`Detected imx415 id` 能证明 I2C 控制通道和基本上电条件；`/dev/v4l-subdev3` 能证明 subdev 节点已注册。它们不能证明 `imx415_s_stream()` 已执行、MIPI 数据到达或 `/dev/video0` 已完成帧。
