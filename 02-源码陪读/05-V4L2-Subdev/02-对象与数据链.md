## 三张 ops 表不是“一次注册全部函数”

```c
static const struct v4l2_subdev_video_ops imx415_video_ops = {
    .s_stream = imx415_s_stream, // 函数指针赋值：将来开/停流时回调
};

static const struct v4l2_subdev_pad_ops imx415_pad_ops = {
    .get_fmt = imx415_get_fmt,   // 查询当前总线格式
    .set_fmt = imx415_set_fmt,   // 协商并保存 Sensor mode
};

static const struct v4l2_subdev_ops imx415_subdev_ops = {
    .video = &imx415_video_ops,  // 对象关系：主表指向 video 子表
    .pad = &imx415_pad_ops,      // 对象关系：主表指向 pad 子表
};

static const struct v4l2_ctrl_ops imx415_ctrl_ops = {
    .s_ctrl = imx415_set_ctrl,   // control 框架回调
};
```

**调用类型：** 上面的 `=` 全是函数指针赋值或对象关联，没有执行右侧函数。未来框架执行类似 `v4l2_subdev_call(sd, pad, set_fmt, ...)` 时，才沿 `sd->ops->pad->set_fmt` 找到 `imx415_set_fmt()`。

## 格式链：请求分辨率到选择 mode

### 为什么这样设计

V4L2 不能要求每一种 Sensor 都用同一套寄存器。框架只传递通用的 `fmt` 请求，IMX415 驱动再把它翻译成自己支持的 `struct imx415_mode`。因此格式协商和真正写硬件被拆开：`set_fmt()` 先选模式并保存软件状态，开流时再一次性写模式寄存器。

```c
static int imx415_set_fmt(struct v4l2_subdev *sd,
                         struct v4l2_subdev_pad_config *cfg,
                         struct v4l2_subdev_format *fmt)
{
    struct imx415 *imx415 = to_imx415(sd); // container_of：sd 反推私有对象
    const struct imx415_mode *mode;

    // 直接调用：按请求的宽、高和 bus code，从 supported_modes 选最佳项
    mode = imx415_find_best_fit(imx415, fmt);
    fmt->format.code = mode->bus_fmt;
    fmt->format.width = mode->width;
    fmt->format.height = mode->height;

    if (fmt->which == V4L2_SUBDEV_FORMAT_TRY) {
        // TRY：只把试算结果放在 cfg 中，不改变 Sensor 当前工作模式
        *v4l2_subdev_get_try_format(sd, cfg, fmt->pad) = fmt->format;
    } else {
        // ACTIVE：直接调用，修改 cur_mode/cur_vts，并同步 control 范围
        imx415_change_mode(imx415, mode);
    }
    return 0;
}
```

### 这一步改变了什么

- `TRY`：只改变当前 file handle 的试算格式，适合上层探测“如果这样设置是否可行”。
- `ACTIVE`：改变 `imx415->cur_mode`、`cur_vts` 和相关 control 范围。
- 两条分支都没有写完整模式表，也没有退出 Standby。

大白话：`set_fmt()` 是“选套餐并记下来”，不是“让厨房立刻开火”。真正把套餐对应寄存器写入 Sensor，要等 `__imx415_start_stream()`。

## Control 链：曝光、增益、VBLANK

### 为什么 control 既能缓存又能写硬件

应用可能在 Sensor 尚未上电时先设置曝光。驱动不能为了每次调参数都强制上电，因此 control 对象先保存目标值；Sensor 已经在用时立即写寄存器，尚未上电时暂不访问 I2C，开流阶段再统一应用。

```c
static int imx415_set_ctrl(struct v4l2_ctrl *ctrl)
{
    struct imx415 *imx415 =
        container_of(ctrl->handler, struct imx415, ctrl_handler);

    if (!pm_runtime_get_if_in_use(&imx415->client->dev))
        return 0; // 未上电时只保存 control 值，不立即访问 I2C

    switch (ctrl->id) {
    case V4L2_CID_EXPOSURE:
        // IMX415 曝光由 SHR0 = VTS - exposure 换算，再拆成三个真实寄存器
        shr0 = imx415->cur_vts - ctrl->val;
        ret = imx415_write_reg(imx415->client, IMX415_LF_EXPO_REG_L,
                               IMX415_REG_VALUE_08BIT,
                               IMX415_FETCH_EXP_L(shr0));
        break;
    case V4L2_CID_ANALOGUE_GAIN:
        ret = imx415_write_reg(imx415->client, IMX415_LF_GAIN_REG_L,
                               IMX415_REG_VALUE_08BIT,
                               IMX415_FETCH_GAIN_L(ctrl->val));
        break;
    }
    pm_runtime_put(&imx415->client->dev);
    return ret;
}
```

### 这一步改变了什么

`imx415_initialize_controls()` 创建 control 对象并把 `&imx415_ctrl_ops` 交给 V4L2 Controls；`imx415_set_ctrl()` 是以后控件变化时的框架回调。control 值改变一定会改变软件对象，但只有 runtime PM 表明 Sensor 正在使用时才立即改变硬件寄存器。

### Control 第一轮回答与批改

#### 问题 1：`ctrl->val` 是 Sensor 寄存器值吗？

**我的回答：**

> 不是。

<mark>高亮正确答案：回答正确。`ctrl->val` 是 V4L2 Control 层保存的通用控制值，不一定能原样写进 Sensor。驱动还要根据具体 Sensor 的寄存器定义进行换算。例如曝光的 `ctrl->val` 表示曝光行数，IMX415 需要先计算 `SHR0 = cur_vts - ctrl->val`，再把 SHR0 拆成低、中、高三个字节写入寄存器。</mark>

#### 问题 2：Sensor 未上电时调用 `imx415_set_ctrl()`，曝光设置丢失了吗？

**我的回答：**

> 不会。

<mark>高亮正确答案：回答正确。V4L2 Control Core 已经先把新值保存到 `ctrl->val`；`pm_runtime_get_if_in_use()` 发现 Sensor 未在使用时，驱动只是不立即访问 I2C，软件值不会丢失。开流上电后，`__v4l2_ctrl_handler_setup()` 会再次通过 `imx415_ctrl_ops.s_ctrl` 回调 `imx415_set_ctrl()`，把缓存值写入 IMX415。</mark>

#### 问题 3：为什么曝光请求是 `203`，最终写入的 `SHR0` 却是 `2047`？

**我的回答：**

>

<mark>高亮正确答案：因为 V4L2 的 `203` 表示期望曝光的行数，而 IMX415 曝光寄存器保存的是帧末到曝光起点之间的 SHR0。当前 `cur_vts = 2250`，所以驱动计算 `SHR0 = 2250 - 203 = 2047`，再将 2047 拆分后写入 `IMX415_LF_EXPO_REG_L/M/H`。这体现了驱动把通用 V4L2 参数翻译成 Sensor 专用寄存器值。</mark>

## 开流链：从能力表到寄存器

```text
V4L2/RKISP pipeline 发出 s_stream(1)
  → v4l2_subdev_call(sd, video, s_stream, 1)  [通用分发]
  → imx415_s_stream(sd, 1)                    [框架回调]
  → pm_runtime_get_sync(dev)                  [直接调用，上电]
  → __imx415_start_stream(imx415)             [直接调用]
      → imx415_write_array(cur_mode->reg_list) [写模式寄存器]
      → __v4l2_ctrl_handler_setup(...)         [回调 set_ctrl，应用缓存 controls]
      → imx415_write_reg(IMX415_REG_CTRL_MODE,
                         IMX415_REG_VALUE_08BIT, 0) [退出 Standby]
```

停流则由 `imx415_s_stream(sd, 0)` 进入 `__imx415_stop_stream()`，再释放 runtime PM 引用。

### 为什么开流顺序不能反过来

必须先保证供电和时钟，再写模式表；必须在退出 Standby 前应用曝光、增益等 controls。否则 Sensor 可能用旧模式或旧参数开始送帧。最后写 `IMX415_REG_CTRL_MODE = 0` 才是数据开始离开 Sensor 的边界。

### 这一步改变了什么

```text
软件状态：imx415->streaming = true
硬件状态：Sensor 从 Standby 进入 Streaming
数据状态：RAW Bayer 才开始送向 D-PHY
```

### 开流链第一轮回答与批改

#### 问题 1：`pm_runtime_get_sync()` 成功是否表示 IMX415 已经开始输出 RAW？

**我的回答：**

> 不能。

<mark>高亮正确答案：回答正确。`pm_runtime_get_sync()` 只保证 Runtime PM 使用计数增加，并在需要时通过 `imx415_runtime_resume()` 让 Sensor 完成供电、时钟和复位等上电过程。此时 IMX415 已经可以通过 I2C 配置，但仍可能处于 Standby；只有后面写 `IMX415_REG_CTRL_MODE = 0` 退出 Standby，Sensor 才开始输出 RAW。</mark>

#### 问题 2：为什么必须先写模式表，再调用 `__v4l2_ctrl_handler_setup()`？

**我的回答：**

> 不懂。

<mark>高亮正确答案：模式表负责配置当前分辨率、帧时序和一组默认寄存器，其中可能包含曝光、增益、VTS 等默认值。如果先应用 controls、再写模式表，刚写入的用户曝光和增益可能被模式表覆盖。因此驱动先写 `cur_mode->reg_list` 建立模式基础，再调用 `__v4l2_ctrl_handler_setup()`，通过 `imx415_set_ctrl()` 把缓存的最新 controls 覆盖到硬件，最后才退出 Standby。</mark>

#### 问题 3：`imx415->streaming = true` 能证明什么，不能证明什么？

**我的回答：**

>

<mark>高亮正确答案：它能证明驱动的 `imx415_s_stream(1)` 主路径已成功返回，包括 Runtime PM 获取成功、模式表和 controls 的 I2C 写入没有返回错误、退出 Standby 的寄存器写入也没有报错，因此驱动把软件状态记录为正在开流。它不能证明 RAW 数据真的到达 D-PHY，更不能证明 CSI、RKISP、DMA 和用户态 DQBUF 正常；这些必须结合 D-PHY/CSI 状态、帧中断及持续抓帧验证。</mark>

## C 基础

- `const struct ... *` 表示通过这个指针不修改静态 ops 表。
- `to_imx415(sd)` 通常是对 `container_of` 的封装，用内嵌 `subdev` 地址找回外层 `struct imx415`。
- `switch (ctrl->id)` 是按 control ID 分发，不是注册。
- `mutex_lock` 保护 mode、streaming 与 controls 的一致性，防止并发请求交叉修改。

## 板端证据：能证明与不能证明

```bash
v4l2-ctl -d /dev/v4l-subdev3 --list-ctrls
media-ctl -p
dmesg | grep -E 'imx415|set fmt|stream'
```

- controls 可枚举：证明 control handler 已注册；不能证明每次 I2C 写都成功。
- `set fmt` 日志：证明格式回调被执行并选出 mode；不能证明已经开流。
- 抓到连续帧：组合证明上游开流和 DMA 工作；单凭 Sensor ID 不能证明这一点。

## 函数卡

| 字段       | `imx415_s_stream()`                       |
| -------- | ----------------------------------------- |
| 函数属于哪一层  | V4L2 Sensor Subdev video ops              |
| 谁调用      | V4L2/RKISP pipeline 通过函数指针框架回调            |
| 参数从哪里来   | `sd` 是 IMX415 subdev；`on` 来自开/停流请求        |
| 读取什么     | 当前 mode、streaming 状态、runtime PM           |
| 修改哪个结构体  | `imx415->streaming`，并通过 I2C 修改 Sensor 寄存器 |
| DTS 对应   | 无直接解析；硬件资源已在 probe 取得                     |
| 运行时证据    | 开流日志、寄存器写错误、连续帧                           |
| 失败时下一检查点 | PM/时钟/复位、模式表、I2C 写、D-PHY/CSI 错误           |
| 面试一句话    | “s_stream 是 Sensor 真正响应 pipeline 开停流的回调。” |

## 面试问题

`v4l2_i2c_subdev_init()` 是否把 `set_fmt/set_ctrl/s_stream` 全部执行了一遍？

**我的回答：**

>
<mark>高亮正确答案：没有。它只初始化 subdev 并挂上 ops；controls 由 control handler 单独创建。对应请求到来后，V4L2 才通过函数指针分别回调 set_fmt、set_ctrl 和 s_stream。</mark>
