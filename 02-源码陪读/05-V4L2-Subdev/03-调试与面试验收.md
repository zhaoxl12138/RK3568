# V4L2 Subdev 调试与面试验收

## 大白话解释

把 Sensor subdev 当成“可被 Camera 框架遥控的芯片对象”：节点存在只是遥控器已登记，真正有图还要看开流回调、MIPI 数据链和 capture buffer 是否都工作。

## 五道门诊断法

排查时不要从几十条日志中猜原因。按下面五道门顺序检查，找到**第一处失败**就停在这一层追源码；后面的现象通常只是前面失败的结果。

| 门                           | Source Insight 搜索                                                                      | 关键对象或语句                                                      | 日志/断点                                                       | 能证明                                  | 不能继续推断                                |
| --------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------------ | ------------------------------------- |
| Gate 1：I2C probe            | `drivers/media/i2c/imx415.c` → `imx415_probe`、`imx415_check_sensor_id`                 | `client->dev.of_node`、上电资源、I2C read                          | `driver version`、`Detected imx415 id 0000e0`                | DTS client 已匹配到驱动，基本控制面足以读取 ID       | D-PHY、CSI、ISP、DMA 已正常                 |
| Gate 2：Subdev 对象组装          | `v4l2_i2c_subdev_init` → `v4l2_subdev_init`                                            | `sd->ops = ops`、`i2c_set_clientdata`、`v4l2_set_subdevdata`   | 在三条赋值后检查 `sd/client/ops`                                    | 同一个 IMX415 私有对象已能以 V4L2 subdev 接口被访问 | 回调已执行、Media Link 已建立                  |
| Gate 3：Entity 与 Source Pad  | `media_entity_pads_init`                                                               | `pad.flags = MEDIA_PAD_FL_SOURCE`、`sd->entity.function`      | `media-ctl -p` 中 Sensor entity 与 `pad0: Source`             | 图节点和输出端口的软件对象存在                      | 对端已经绑定、RAW 正在经过                       |
| Gate 4：Async 匹配与 Media Link | `v4l2_async_register_subdev_sensor_common`、D-PHY 的 `rockchip_csi2_dphy_notifier_bound` | Sensor 进入 Async；D-PHY `.bound()` 调 `media_create_pad_link()` | `media-ctl -p` 中 Sensor→D-PHY `[ENABLED]`                   | 两端真实对象已匹配，运行时软件 link 已创建并启用          | MIPI lane 电气、包接收和帧中断正常                |
| Gate 5：开流与真实帧               | `imx415_s_stream` → `__imx415_start_stream`                                            | runtime PM、模式寄存器、controls、`IMX415_REG_CTRL_MODE`             | 在 `s_stream`、`__imx415_start_stream`、stop 路径加日志/断点；连续 DQBUF | 回调确实执行；连续 DQBUF 还能证明 buffer 到达用户态    | 仅 STREAMON 返回 0 不能证明第一帧，单帧也不能证明稳定性和画质 |

这五道门对应五类不同动作：

```text
probe 成功             = 设备与驱动完成初始化入口
sd/client/ops 关联      = 通用框架取得私有驱动能力
entity/pad 初始化       = 图中有方框和端口
Async bound + link      = 独立 probe 的上下游对象相遇
s_stream + DQBUF        = 启动请求真正走到 Sensor，并最终看到帧
```

它们不能压缩成一句“V4L2 注册成功”。

## 原始代码检查点

```c
sd = &imx415->subdev; // 取内嵌成员地址：对象关系，不复制结构体
v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops); // 直接调用：组装对象

imx415->pad.flags = MEDIA_PAD_FL_SOURCE; // 字段赋值：声明输出方向
media_entity_pads_init(&sd->entity, 1, &imx415->pad); // 直接调用：建立 pad 所有权

v4l2_async_register_subdev_sensor_common(sd); // 直接调用：进入 Async 可匹配集合
```

不要把上面三行都叫“注册”。第一行组装对象，第二行初始化图端口，第三行才把 Sensor subdev 交给 Async 框架。

## 误区诊断

1. **“有 `/dev/v4l-subdev3` 就能 cat 图片。”** 错。subdev 节点主要用于控制和配置，不是 capture buffer 队列。
2. **“Source 是输入源，所以不是输出。”** 错。Media Pad 站在当前 entity 看数据方向；Sensor Source pad 即数据从 Sensor 输出。
3. **“Sensor ID 成功说明 MIPI 正常。”** 错。ID 走 I2C 控制面，MIPI 是独立数据面。
4. **“`s_stream` 注册后自动执行。”** 错。它只是回调地址，pipeline STREAMON 时才被调用。
5. **“格式是 NV12，所以 Sensor 输出 NV12。”** 错。IMX415 输出 RAW10；NV12 是 RKISP capture node 的处理结果。

## 板端诊断顺序：每条命令只跨一道门

```bash
cat /sys/class/video4linux/v4l-subdev3/name
media-ctl -p
v4l2-ctl -d /dev/v4l-subdev3 --list-ctrls
v4l2-ctl -d /dev/video0 --all
v4l2-ctl -d /dev/video0 --stream-mmap=4 --stream-count=30 --stream-to=/tmp/30.nv12
dmesg | tail -n 120
```

**能证明：** 名称证明 Sensor subdev 节点存在；Media Graph 证明 entity/pad/link；controls 列表证明控制对象已建立；成功连续取回 30 个 buffer，且文件大小、sequence、timestamp 合理，才能证明 capture 队列持续收到帧。

**不能证明：** 节点存在不能证明开流；link enabled 不能证明无 CRC/ECC；仅仅看到输出文件大小增长也不能单独证明内容有效；单帧成功不能证明长时间稳定性或画质正确。

## 30 秒面试表达

> IMX415 先通过 I2C Driver 完成匹配和 probe。probe 用 `v4l2_i2c_subdev_init` 把 Sensor 私有对象中的 subdev、I2C client 和 subdev_ops 关联起来，再初始化一个 Source Pad，并把 Sensor 注册进 V4L2 Async。格式、controls 和 stream 都是后续框架回调：set_fmt 选择 mode，set_ctrl 更新曝光增益，s_stream 才真正上电、写模式表并退出 Standby。

## 面试问题

读取 Sensor ID 成功能证明什么、不能证明什么？怎样证明 `s_stream` 真正走到了？

**我的回答：**

>

<mark>高亮正确答案：ID 成功证明 I2C 控制通道、基本供电/时钟/复位足以读芯片；不能证明 MIPI、D-PHY、CSI、ISP 或 DMA。要结合 s_stream/寄存器写日志、D-PHY/CSI 错误计数以及持续抓帧结果证明数据链。</mark>
