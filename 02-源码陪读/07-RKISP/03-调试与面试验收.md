# RKISP Async、STREAMON 与分层验收

## Source Insight 精确入口与大白话

在 `drivers/media/platform/rockchip/isp/dev.c` 追 `subdev_notifier_complete()` 和 `rkisp_pipeline_set_stream()`；在 `drivers/media/platform/rockchip/isp/capture_v21.c` 追 `rkisp_start_streaming()`；需要看 video node 注册时回到 `drivers/media/platform/rockchip/isp/capture.c`。大白话：先确认图建完，再确认启动命令确实逐级传到上游，最后确认中断把 DMA buffer 交还 VB2；三层证据不能互相替代。

## 先明确本阶段的最终目标

第 07 阶段不是看到 RKISP probe 成功就结束，而是要把四层证据分开：

```text
1. 驱动对象存在：HW/逻辑 probe 成功
2. 管线关系存在：Async complete、Media link 和 pad 格式正确
3. 硬件启动：STREAMON 让 RKISP、CSI、Sensor 按顺序进入工作状态
4. 帧真正完成：IRQ/DMA 调用 vb2_buffer_done，用户态才能 DQBUF
```

其中第 1、2 层主要是“软件对象和拓扑”，第 3 层才开始让硬件工作，第 4 层才证明图像已经走到内存。后面排查“没有图”时，必须先说清楚自己卡在哪一层。

## 为什么调试必须拆成四道门

```text
门 1：HW/逻辑 probe 与对象桥
→ 门 2：内部注册 + Async complete + Media Links
→ 门 3：STREAMON 启动 capture 和上游
→ 门 4：IRQ / DMA / VB2 done / DQBUF / 画质
```

上一道门成功只是下一道门的必要条件，不是充分条件。最常见误判是看到 `/dev/videoX` 就宣布链路成功，或看到 STREAMON 返回 0 就宣布已经有帧。

白话：窗口开张、道路画好、全线开机、货物真正到手是四件不同的事。

## Async：外部对象为什么晚于 RKISP probe 汇合

`rkisp_register_platform_subdevs()` 最后调用 `isp_subdev_notifier()`，把 `subdev_notifier_ops` 注册给 V4L2 Async：

```c
static const struct v4l2_async_notifier_operations subdev_notifier_ops = {
    .bound = subdev_notifier_bound,
    .complete = subdev_notifier_complete,
};
```

### bound 做什么

```c
isp_dev = container_of(notifier, struct rkisp_device, notifier);
s_asd = container_of(asd, struct rkisp_async_subdev, asd);
isp_dev->sensors[isp_dev->num_sensors].mbus = s_asd->mbus;
isp_dev->sensors[isp_dev->num_sensors].sd = subdev;
++isp_dev->num_sensors;
```

- 对象从哪里来：`notifier` 内嵌于 `rkisp_device`；`subdev` 是外部 Sensor/D-PHY 等 driver 独立注册并被 Async 匹配到的真实对象；`asd` 是解析 fwnode endpoint 得到的等待描述。
- 谁调用：V4L2 Async 框架回调，不是 `rkisp_plat_probe()` 直接调用。
- 为什么只收集不立即全图建链：外部对象可能一个个到达，尚未 complete 时建完整图会得到半套拓扑。
- 能证明 / 不能证明：一次 bound 能证明一个等待对象已经匹配；不能证明其他对象到齐，也不能证明数据流。

### complete 在哪汇合

```c
static int subdev_notifier_complete(struct v4l2_async_notifier *notifier)
{
    struct rkisp_device *dev = container_of(notifier, ...);

    mutex_lock(&dev->media_dev.graph_mutex);
    ret = rkisp_create_links(dev);
    ret = v4l2_device_register_subdev_nodes(&dev->v4l2_dev);
    ret = rkisp_update_sensor_info(dev);
    ret = _set_pipeline_default_fmt(dev);
    mutex_unlock(&dev->media_dev.graph_mutex);
}
```

这里是 Async 外部对象、RKISP 内部 CSI/ISP entity 和默认格式的汇合点。`rkisp_create_links()` 根据 `entity.function` 与 `mbus.type` 决定 DVP/CIF/LVDS/CSI 路径；MIPI 主路径创建“上游 source → CSI sink → CSI source → ISP sink”。

为什么加 `graph_mutex`：Media Link、subdev node 和 active format 都属于共享图状态，必须避免用户或其他线程观察到半更新结果。

`Async subdev notifier completed` 能证明 complete 主线已经走到日志点，即建链、subdev node 注册、Sensor 信息与默认格式调用均未提前失败；不能证明 Sensor 发包、D-PHY 收包、ISP 中断或 DMA done。

## STREAMON 的对象入口从哪里来

注册阶段已经把五类关系装好：

```text
video_device.fops       = rkisp_fops
video_device.ioctl_ops  = rkisp_v4l2_ioctl_ops
video_device.queue      = &vnode.buf_queue
vb2_queue.ops           = rkisp_vb2_ops
vb2_queue.drv_priv      = stream
```

`rkisp_v4l2_ioctl_ops` 中：

```c
.vidioc_streamon = vb2_ioctl_streamon,
```

`rkisp_vb2_ops` 中：

```c
.start_streaming = rkisp_start_streaming,
```

因此应用没有直接调用 `rkisp_start_streaming()`；对象和函数表逐级分发：

```text
应用 ioctl(fd, VIDIOC_STREAMON, ...)
→ V4L2 Core 找到 fd 对应 struct video_device
→ rkisp_v4l2_ioctl_ops.vidioc_streamon
→ vb2_ioctl_streamon()
→ video_device.queue 指向的 struct vb2_queue
→ queue.ops = rkisp_vb2_ops
→ VB2 在队列条件满足后框架回调 rkisp_start_streaming(queue, count)
→ queue->drv_priv 取回原 struct rkisp_stream
→ stream->ispdev 取回 struct rkisp_device
```

为什么这样设计：V4L2 负责 ioctl ABI，VB2 负责通用 buffer 状态机，RKISP 只实现硬件相关 queue ops。每层通过字段/函数表关联，减少重复实现 REQBUFS/QBUF/DQBUF 规则。

## `rkisp_start_streaming()` 做了什么

按源码顺序，不要只背概览：

```text
1. queue->drv_priv → stream → ispdev                    [取回对象]
2. 锁 hw_dev->dev_lock                                  [共享 HW 串行化]
3. 检查 !dev->isp_inp 或 !stream->linked                [图/输入门槛]
4. 首条 capture stream 时 rkisp_update_sensor_info()    [刷新上游信息]
5. rkisp_create_dummy_buf(stream)                        [无用户 buffer 时兜底]
6. dev->pipe.open(..., true)                             [函数指针间接调用]
   └─ rkisp_pipeline_open()
      └─ __isp_pipeline_prepare()                        [沿 enabled sink link 逆向收集 subdev]
7. rkisp_stream_start(stream)                            [直接调用：v2.1 resize/MI/DMA 配置]
8. MP/SP 才调用 dev->pipe.set_stream(..., true)          [函数指针间接调用]
   └─ rkisp_pipeline_set_stream()
9. media_pipeline_start()                                [标记 Media pipeline 正在使用]
```

为什么先配置 ISP/capture 再让 Sensor 发货：接收端必须先准备好，否则上游先吐数据可能在下游尚未接管时丢帧或触发错误。具体循环顺序由 enabled Media Graph 决定；典型 MIPI 主路径是先显式启动 ISP subdev，再依次分发 RKISP CSI、D-PHY、Sensor。

为什么只对 MP/SP 调 `pipe.set_stream`：源码条件明确限制 `stream->id == RKISP_STREAM_MP || RKISP_STREAM_SP`；DMATX/HDR 路径有不同数据源与控制，不应把主路径结论无条件推广到所有 stream。

调用返回 0 能证明上述软件调用链没有返回致命错误；不能证明第一帧中断已经发生，因为函数返回与异步帧到达不是同一时刻。

## `pipe.set_stream` 怎样启动上游

函数指针在逻辑 probe 中装配：

```c
isp_dev->pipe.set_stream = rkisp_pipeline_set_stream;
```

运行时在 `rkisp_start_streaming()` 间接调用：

```c
ret = dev->pipe.set_stream(&dev->pipe, true);
```

真实实现先从内嵌 pipe 反查外层：

```c
struct rkisp_device *dev = container_of(p, struct rkisp_device, pipe);
```

再启动：

```c
v4l2_subdev_call(&dev->isp_sdev.sd, video, s_stream, true);
for (i = 0; i < p->num_subdevs; ++i)
    v4l2_subdev_call(p->subdevs[i], video, s_stream, true);
```

`p->subdevs[]` 不是手写固定名单。`pipe.open()` 内的 `__isp_pipeline_prepare()` 从当前 capture entity 沿 enabled sink link 向上游遍历，把 ISP 之外的远端 subdev 依次收集。典型 MP MIPI 链会收集 RKISP CSI subdev、D-PHY、Sensor，但实际数组内容与顺序仍应以板端 Media Graph 为准。

函数表最终关联：

```text
ISP sd->ops = rkisp_isp_sd_ops
└─ video->s_stream = rkisp_isp_sd_s_stream

CSI sd->ops = rkisp_csi_ops
└─ video->s_stream = rkisp_csi_s_stream

外部 D-PHY / IMX415
└─ 各自 v4l2_subdev_ops.video.s_stream
```

注意证据边界：仅凭 `rkisp_pipeline_set_stream()` 源码能证明它会按收集到的 subdev 数组分发；不能不看实际 graph 就断言某块板上 `p->subdevs[0]` 永远是哪一个对象。

## 出错时在哪回滚

如果某个上游 `s_stream(true)` 返回致命错误，`rkisp_pipeline_set_stream()` 会对已启动对象反向 `s_stream(false)`，并关闭 ISP subdev。`rkisp_start_streaming()` 还按标签依次：

```text
pipe_stream_off → pipe.set_stream(false)
stop_stream     → rkisp_stream_stop(stream)
close_pipe      → pipe.close(&dev->pipe)
destroy_dummy   → rkisp_destroy_dummy_buf(stream)
buffer_done     → destroy_buf_queue(...)
```

为什么用 goto：内核初始化具有“前面成功多少，就反向清理多少”的层级；集中标签可避免每个失败分支复制清理代码。goto 本身不能证明清理完整，仍要核对跳转落点是否覆盖已经成功的步骤。

## 分层故障表

| 现象 | 最早可疑层 | 先查对象/函数 | 能证明 | 不能证明 |
|---|---|---|---|---|
| 无 `rkisp_hw` probe | HW DTS/compatible/resource | `rkisp_hw_probe` | 日志缺失能定位未到该证据点 | 单靠缺日志不能区分日志级别与 probe 未执行 |
| 有 HW、无逻辑版本日志 | rkisp-vir 节点/driver match | `rkisp_plat_probe` | HW 层与逻辑层已分开 | HW 成功不保证逻辑匹配 |
| attach 报错 | `rockchip,hw`、HW pdev drvdata | `rkisp_attach_hw`、`platform_get_drvdata` | 错误点说明对象桥失败 | 不必先怀疑 Sensor 格式 |
| 有 `/dev/videoX`、无完整 link | Async bound/complete | `subdev_notifier_complete`、`rkisp_create_links` | video node 与外部建链不是同一步 | 节点存在不证明 Sensor/D-PHY 到齐 |
| `media-ctl -p` link 缺失 | endpoint / notifier / entity type | `dev->sensors[]`、pad flags | 软件图可直接检查 | 图正确不证明物理 RAW |
| STREAMON 报 `check video link or isp input` | `stream->linked` / `dev->isp_inp` | `rkisp_start_streaming` | 失败发生在硬件启动前 | 不应先追 DMA done |
| STREAMON 返回 0、DQBUF 超时 | Sensor standby、D-PHY/CSI、ISP/MI IRQ、DMA | 各 `s_stream`、IRQ counters、buffer done | 启动 API 成功与帧到达已被区分 | STREAMON 0 不保证帧 |
| DQBUF 正常但颜色错 | Bayer code/order、ISP IQ、NV12 解码 | pad fmt、node fmt、参数节点 | buffer 链基本工作 | 有帧不保证 IQ 正确 |

## 板端验收命令与证据边界

```bash
dmesg | grep -E 'rkisp_hw|rkisp driver version|Async|csi|mipi|isp'
media-ctl -p
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoX --all
v4l2-ctl -d /dev/videoX --stream-mmap=4 --stream-count=100 --stream-to=/tmp/rkisp.raw
```

| 证据 | 能证明 | 不能证明 |
|---|---|---|
| `v4l2-ctl --list-devices` | `/dev/videoX` 与设备名称的当前映射 | 编号重启后永远固定 |
| `media-ctl -p` | entity/pad/link 和当前 pad format | 电气信号与 buffer done |
| `--all` 显示 NV12 | capture queue 当前 FourCC/尺寸 | ISP source pad 一定也是 NV12 |
| STREAMON 返回 0 | 启动调用成功返回 | 后续第一帧必到 |
| 100 次 DQBUF、sequence 递增 | DMA/VB2 持续交帧 | 颜色、曝光、Bayer order 与 IQ 正确 |
| 保存文件尺寸符合预期 | 收到相应数量/布局的字节 | 每个像素内容正确 |

## 面试问题：STREAMON 成功但 DQBUF 超时怎么查

先确认 `media-ctl -p` 的 enabled link 和 RAW/YUYV pad 格式，再确认 `/dev/videoX` 对应正确 stream 且 queue 格式/尺寸匹配。然后沿 `rkisp_start_streaming → pipe.set_stream → rkisp_pipeline_set_stream → v4l2_subdev_call` 检查 ISP、D-PHY、Sensor 的 `s_stream` 是否真正执行；数据面依次查 Sensor 是否退出 standby、D-PHY/CSI 是否有包或错误、ISP/MI 是否有帧中断、buffer 是否入队并 done。STREAMON 返回 0 只能证明启动主链成功返回，不能证明异步到来的第一帧已经完成。

**我的回答：**

>

<mark>高亮正确答案：先按“软件图→启动回调→数据中断→buffer 完成”分层。图层核对 enabled link 和 pad 格式；控制层确认 `rkisp_start_streaming()`、`pipe.set_stream(true)` 及各 subdev `s_stream`；数据层查 D-PHY/CSI 错误和 ISP/MI frame-end；队列层查 ACTIVE buffer 是否进入 `vb2_buffer_done()`。STREAMON 返回 0 只说明启动链未报错，DQBUF 仍依赖真实帧和 DMA 完成。</mark>
