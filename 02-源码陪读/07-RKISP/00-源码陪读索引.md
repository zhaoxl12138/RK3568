# RKISP v2.1 源码陪读索引

> 本阶段只以 RK3568 BSP 的 `drivers/media/platform/rockchip/isp/` 为事实源，不把上游 `isp1/`、旧 `rk-isp10/` 或其他内核版本的实现套进来。

Source Insight 本阶段固定打开：

## 先把 RKISP 讲成大白话

`RKISP` 是 Rockchip 芯片内部的 Image Signal Processor 及其 Linux 驱动栈。这里要区分三层：

```text
硬件层：RK3568 内部 ISP、CSI、DMA、寄存器、中断
驱动层：Rockchip BSP 的 platform driver、V4L2 subdev、capture 驱动
框架层：V4L2、Media Controller、Videobuf2
```

所以 RKISP 不是一个需要单独安装的第三方库，也不只是一个名称。它既指芯片里的图像处理硬件，也指 Linux 中控制这套硬件的驱动模块。驱动启动后会把硬件能力包装成 V4L2/Media 对象，用户态最终看到的 `/dev/video0` 就是其中的一个视频输出入口。

本阶段承接关系是：

```text
第 06 阶段：Media Graph 说明“模块怎样连接”
第 07 阶段：RKISP 说明“RAW 怎样进入 ISP 并被处理/输出”
第 08 阶段：V4L2 用户态取流说明“应用怎样把输出帧取回来”
```

不要把 `rkisp-isp-subdev` 和 `/dev/video0` 当成同一个东西：前者是管线中的处理子模块，后者是应用可以打开的 Video Node。

## 这一阶段到底要回答什么

不是背十个函数名，而是把下面五个问题连成一条可验证的链：

1. 为什么同一个 ISP 驱动要拆成 `struct rkisp_hw_dev` 和 `struct rkisp_device`？
2. 这两个对象分别从哪里来，`dev_set_drvdata` 与 `platform_get_drvdata` 怎样构成对象桥？
3. `struct rkisp_csi_device`、`struct rkisp_isp_subdev`、`struct rkisp_stream`、`struct video_device`、`struct vb2_queue` 为什么不能合成一个对象？
4. RAW 在哪进入 ISP，processed 路径在哪以 `MEDIA_BUS_FMT_YUYV8_2X8` 离开 ISP，又在哪变成内存格式 `V4L2_PIX_FMT_NV12`？
5. `/dev/videoX`、Async complete、Media Link、`VIDIOC_STREAMON` 和第一帧 DQBUF 分别能证明什么、不能证明什么？

## 一张总对象图

```text
物理 HW platform_device
└─ dev_set_drvdata(hw pdev, struct rkisp_hw_dev *)
   ├─ base_addr / IRQ / clocks / reset / mem_ops
   └─ isp[] ───────────────────────────────┐
                                           │ rkisp_attach_hw()
逻辑 rkisp-vir platform_device              │ rockchip,hw phandle
└─ dev_set_drvdata(vir pdev, struct rkisp_device *)
   ├─ hw_dev ──────────────────────────────┘
   ├─ v4l2_dev / media_dev / notifier / pipe
   ├─ csi_dev: struct rkisp_csi_device
   │  └─ sd + pads + rkisp_csi_ops
   ├─ isp_sdev: struct rkisp_isp_subdev
   │  └─ sd + pads + rkisp_isp_sd_ops
   └─ cap_dev.stream[]: struct rkisp_stream
      └─ vnode
         ├─ struct video_device ── video_register_device() ── /dev/videoX
         ├─ struct vb2_queue ───── rkisp_vb2_ops
         └─ media sink pad
```

为什么这样设计：物理寄存器、IRQ、时钟和 DMA 内存策略跟 SoC ISP 硬件一起存活；Media Graph、Sensor 绑定、格式和 stream 状态跟某个逻辑 `rkisp-vir` 实例一起存活。两者生命周期和职责不同，拆分后还允许一个 HW 对象通过 `hw->isp[]` 关联多个逻辑实例。对象桥只传递指针，不会复制硬件对象。

白话：`rkisp_hw_dev` 是厂房和总电闸，`rkisp_device` 是一条生产线；CSI/ISP subdev 是流水线工位，video node 是出货窗口，VB2 queue 是周转箱管理系统。

## 总时序：在哪汇合

```text
rkisp_hw_drv_init()                                      [内核 init 直接调用]
├─ platform_driver_register(&rkisp_hw_drv)               [直接调用：发布 driver]
│  └─ rkisp_hw_probe()                                   [Platform 框架回调]
│     └─ dev_set_drvdata(hw pdev, hw_dev)                [HW 对象桥写端]
└─ platform_driver_register(&rkisp_plat_drv)              [直接调用：发布 driver]
   └─ rkisp_plat_probe()                                 [Platform 框架回调]
      ├─ dev_set_drvdata(vir pdev, isp_dev)              [逻辑对象桥写端]
      ├─ rkisp_attach_hw(isp_dev)                        [直接调用]
      │  └─ platform_get_drvdata(hw pdev)                [HW 对象桥读端]
      └─ rkisp_register_platform_subdevs()               [内部对象注册汇合]
         ├─ rkisp_register_isp_subdev()
         ├─ rkisp_register_csi_subdev()
         ├─ rkisp_register_stream_vdevs()
         │  └─ rkisp_register_stream_v21()
         │     └─ rkisp_register_stream_vdev()
         │        └─ video_register_device()             [/dev/videoX 生成点]
         └─ isp_subdev_notifier()
            ├─ subdev_notifier_bound()                   [Async 框架回调]
            └─ subdev_notifier_complete()                [异步对象汇合]
               └─ rkisp_create_links()                   [外部建链汇合]

VIDIOC_STREAMON                                          [用户 API]
└─ rkisp_v4l2_ioctl_ops.vidioc_streamon
   └─ vb2_ioctl_streamon()                               [函数表分发]
      └─ rkisp_vb2_ops.start_streaming
         └─ rkisp_start_streaming()                      [VB2 框架回调]
            ├─ pipe.open()                               [函数指针间接调用]
            ├─ rkisp_stream_start()                      [直接调用：capture/DMA]
            └─ pipe.set_stream(true)                     [函数指针间接调用]
               └─ rkisp_pipeline_set_stream()
                  └─ v4l2_subdev_call(... s_stream ...) [ops 间接分发 CSI/D-PHY/Sensor]
```

两个汇合点不能混淆：`rkisp_register_platform_subdevs()` 汇合驱动内部对象；`subdev_notifier_complete()` 汇合异步到齐的外部 subdev 并建 link。前者可能已经生成 `/dev/videoX`，后者才让完整上游图成立。

| 步 | 文件与搜索符号 | 对象从哪里来 / 关键字段 | 谁调用与调用类型 | 在哪汇合、为什么这样设计 | 证据边界 |
|---|---|---|---|---|---|
| 1 | `hw.c` → `rkisp_hw_drv_init` | `rkisp_hw_drv`、`rkisp_plat_drv` 是静态 driver 表 | 内核 init 调用；函数内直接调用 `platform_driver_register` | 先发布资源生产者，再发布逻辑消费者 | register 返回成功能证明 driver 已发布；不能证明任一 probe 成功 |
| 2 | `hw.c` → `rkisp_hw_probe` | `devm_kzalloc` 产生 `struct rkisp_hw_dev`，填 `base_addr/clks/reset/mem_ops` | Platform 总线框架回调 | 物理资源集中到一个 HW 对象 | probe 成功能证明资源初始化路径完成；不能证明有 video node 或帧 |
| 3 | `dev.c` → `rkisp_plat_probe` | `devm_kzalloc` 产生 `struct rkisp_device`，内嵌 media/V4L2/CSI/ISP/capture | Platform 总线框架回调 | 逻辑对象在 `rkisp_register_platform_subdevs` 汇合 | 版本日志能证明逻辑 probe 进入；不能证明 Async complete |
| 4 | `common.c` → `rkisp_attach_hw` | `rockchip,hw` → HW node → HW pdev → `platform_get_drvdata` → `hw_dev` | `rkisp_plat_probe` 直接调用 | 把两个独立 probe 的对象桥接 | `isp_dev->hw_dev` 非空能证明软件指针关联；不能证明 MMIO 数据正确 |
| 5 | `rkisp.c` / `csi.c` → 两个 `register_*_subdev` | 对象内嵌于 `rkisp_device`，函数表为 `rkisp_isp_sd_ops` / `rkisp_csi_ops` | `rkisp_register_platform_subdevs` 直接调用 | 生成内部 entity/pad/ops | subdev 注册能证明软件对象存在；不能证明外部 link 到齐 |
| 6 | `capture.c` / `capture_v21.c` → `rkisp_register_stream_vdevs` | `cap_dev.stream[]` → `stream.vnode.vdev/buf_queue` | 版本分派后直接调用 | 共用 video 层与 v2.1 实现汇合 | `/dev/videoX` 能证明 vdev 注册；不能证明它是哪个固定编号或能出帧 |
| 7 | `dev.c` → `subdev_notifier_complete` / `rkisp_create_links` | `bound` 已把外部 `sd` 放进 `dev->sensors[]` | V4L2 Async 框架回调；函数内直接建链 | 外部对象、内部 CSI/ISP entity 汇合 | complete 日志与 `media-ctl -p` 能证明软件图；不能证明物理 RAW 到达 |
| 8 | `capture_v21.c` → `rkisp_start_streaming` | `queue->drv_priv` 取回 `stream`，再到 `stream->ispdev` | VB2 经 `rkisp_vb2_ops` 框架回调 | buffer、capture DMA、上游 subdev 启动汇合 | STREAMON 返回 0 能证明启动调用链成功返回；不能证明随后必有 DQBUF |

## 本阶段证据边界总表

| 观察 | 能证明 | 不能证明 |
|---|---|---|
| `rkisp_hw_probe` 成功日志 | HW driver 已匹配并完成该软件路径 | 逻辑 ISP、Media Graph、像素流 |
| `/dev/videoX` 存在 | 某个 `video_device` 已由 V4L2 Core 注册 | 节点编号固定、外部 link 完整、能 DQBUF |
| `Async subdev notifier completed` | 等待对象已 bound，建链/默认格式主线返回成功 | Sensor 真正在发 MIPI 包、DMA 已写内存 |
| `media-ctl -p` 显示 RAW/YUYV | 软件拓扑与 pad 格式状态 | 电气 lane、帧中断、实际像素内容 |
| `VIDIOC_STREAMON` 返回 0 | VB2/capture/上游启动调用未报告致命错误 | 后续帧一定到达 |
| 连续 DQBUF 且 sequence 增长 | buffer 确实完成并交回用户 | Bayer 顺序、曝光、颜色和 ISP IQ 一定正确 |

## 大白话与面试问题

为什么 RKISP 拆 HW 和逻辑对象？因为寄存器、IRQ、时钟等是共享物理资源，而 V4L2/Media 图、Sensor、stream 和 buffer 是逻辑实例状态。HW probe 用 `dev_set_drvdata` 把 `rkisp_hw_dev` 存到 HW device；逻辑 probe 经 `rockchip,hw` 找到那个 platform device，再由 `platform_get_drvdata` 取回同一指针。之后内部 CSI/ISP subdev 和 capture video node 在注册函数汇合，外部 Sensor/D-PHY 在 Async complete 汇合，STREAMON 最后从 VB2 capture node 反向启动整条上游。

为什么 `/dev/videoX` 已经出现，仍不能说 Camera 管线完整？

**我的回答：**

>

<mark>高亮正确答案：`video_register_device()` 可以在 RKISP 逻辑 probe 注册内部 stream 时先创建 video node；外部 Sensor、D-PHY 仍可能没有通过 Async complete 汇合并建完 link。节点存在只能证明 `video_device` 已发布，完整管线还要看 Async complete、Media Graph、STREAMON 和持续 DQBUF。</mark>
