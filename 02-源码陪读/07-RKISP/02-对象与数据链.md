# RKISP 对象与 RAW→processed 数据链

## Source Insight 精确文件与大白话

先打开 `drivers/media/platform/rockchip/isp/csi.c`、`drivers/media/platform/rockchip/isp/rkisp.c`、`drivers/media/platform/rockchip/isp/capture.c`、`drivers/media/platform/rockchip/isp/capture_v21.c` 和 `drivers/media/platform/rockchip/isp/dev.c`。本篇的大白话主线是：CSI/ISP subdev 负责描述管线工位，video_device 负责用户入口，vb2_queue 负责帧容器；它们被 `rkisp_device` 关联，但不是同一个对象。

## 先区分四种“东西”

你在 Media Graph 和 RKISP 源码里会同时看到硬件、subdev、video node 和 buffer。它们不是同一层：

```text
RKISP 硬件       = 真正做 RAW 接收、图像处理和 DMA 的芯片模块
CSI/ISP subdev   = 驱动在 Media Graph 中对内部处理模块的软件描述
video_device     = 对用户暴露 /dev/videoX 的 V4L2 字符设备对象
vb2_queue        = 管理应用 buffer、DMA 地址和完成状态的通用队列
```

可以把它们想成：

```text
硬件机器       → 真的加工图像
subdev 工位图   → 描述机器在管线中的位置和格式
video node 窗口 → 应用打开和发 ioctl 的入口
VB2 周转箱      → 应用与 DMA 之间交接帧的队列
```

本篇的关键不是背“RAW→YUV”四个字，而是找出每一步由哪个对象负责、数据在哪个 pad/stream 进入、最后由哪个 `video_device` 和 `vb2_queue` 接住。

## 先把“包含关系”看清

```text
struct rkisp_device
├─ struct rkisp_csi_device csi_dev
│  ├─ struct v4l2_subdev sd
│  ├─ struct media_pad pads[]
│  └─ sink[] / err_cnt / irq_cnt
├─ struct rkisp_isp_subdev isp_sdev
│  ├─ struct v4l2_subdev sd
│  ├─ struct media_pad pads[]
│  └─ in_frm / in_fmt / in_crop / out_fmt / out_crop
└─ cap_dev.stream[]: struct rkisp_stream
   ├─ ispdev ───────────────> 外层 struct rkisp_device
   ├─ id / linked / streaming / ops / config / pixm
   └─ vnode: struct rkisp_vdev_node
      ├─ struct video_device vdev
      ├─ struct vb2_queue buf_queue
      └─ struct media_pad pad
```

这些不是五次独立分配。CSI、ISP、capture stream 都内嵌在 `rkisp_device` 中，生命周期天然跟逻辑实例一致；stream 又内嵌 vnode，vnode 再内嵌 `struct video_device` 和 `struct vb2_queue`。

为什么不做成一个大对象：subdev 管内部模块的 pad/format/stream 操作；video_device 管字符设备、file operations 和 ioctl；VB2 queue 管 buffer 状态机与内存方法；`rkisp_stream` 管 Rockchip 某条 MP/SP/DMATX 路径。职责和框架接口不同，但通过内嵌与反向指针关联。

白话：CSI/ISP 是地图上的加工节点，video_device 是用户能打开的窗口，VB2 queue 是窗口背后的周转箱队列，stream 是这条出货路径自己的生产状态。

## CSI subdev：RAW 接收/分流的软件模型

`rkisp_register_csi_subdev()` 的对象来源是 `&dev->csi_dev`：

```c
struct rkisp_csi_device *csi_dev = &dev->csi_dev;
struct v4l2_subdev *sd = &csi_dev->sd;

csi_dev->ispdev = dev;
v4l2_subdev_init(sd, &rkisp_csi_ops);
csi_dev->pads[CSI_SINK].flags = MEDIA_PAD_FL_SINK;
csi_dev->pads[CSI_SRC_CH0].flags = MEDIA_PAD_FL_SOURCE;
v4l2_set_subdevdata(sd, csi_dev);
v4l2_device_register_subdev(v4l2_dev, sd);
```

字段/函数表关系：

```text
sd->ops = rkisp_csi_ops                         [由 v4l2_subdev_init 保存]
rkisp_csi_ops.core  -> rkisp_csi_core_ops
rkisp_csi_ops.video -> rkisp_csi_video_ops
                        └─ .s_stream = rkisp_csi_s_stream
rkisp_csi_ops.pad   -> rkisp_csi_pad_ops
                        ├─ .set_fmt = rkisp_csi_get_set_fmt
                        └─ .get_fmt = rkisp_csi_get_set_fmt
sd->entity.ops      -> rkisp_csi_media_ops
                        ├─ .link_setup
                        └─ .link_validate
```

谁调用：`rkisp_register_platform_subdevs()` 直接调用注册函数；以后 V4L2/Media 框架经 `sd->ops` 间接调用 pad/video 操作。注册完成只证明 CSI 软件 entity/pads/ops 已存在；不能证明 D-PHY lane、VC/DT 或 RAW 包正确。

## ISP subdev：RAW sink 与 processed source

`rkisp_register_isp_subdev()` 的对象来源是 `&isp_dev->isp_sdev`：

```c
struct rkisp_isp_subdev *isp_sdev = &isp_dev->isp_sdev;
struct v4l2_subdev *sd = &isp_sdev->sd;

v4l2_subdev_init(sd, &rkisp_isp_sd_ops);
isp_sdev->pads[RKISP_ISP_PAD_SINK].flags = MEDIA_PAD_FL_SINK;
isp_sdev->pads[RKISP_ISP_PAD_SINK_PARAMS].flags = MEDIA_PAD_FL_SINK;
isp_sdev->pads[RKISP_ISP_PAD_SOURCE_PATH].flags = MEDIA_PAD_FL_SOURCE;
isp_sdev->pads[RKISP_ISP_PAD_SOURCE_STATS].flags = MEDIA_PAD_FL_SOURCE;
v4l2_set_subdevdata(sd, isp_dev);
```

为什么 `v4l2_set_subdevdata(sd, isp_dev)` 存外层对象而 CSI 存 `csi_dev`：ISP 的实现大量需要整机 `rkisp_device` 的 HW、stream、HDR、参数等状态；CSI 的回调先取 `rkisp_csi_device`，再由 `csi->ispdev` 到外层。这是源码里的真实对象桥，不能凭命名假设二者一致。

函数表关系：

```text
rkisp_isp_sd_ops.core  -> rkisp_isp_core_ops
rkisp_isp_sd_ops.video -> rkisp_isp_sd_video_ops
                           └─ .s_stream = rkisp_isp_sd_s_stream
rkisp_isp_sd_ops.pad   -> rkisp_isp_sd_pad_ops
                           ├─ .enum_mbus_code
                           ├─ .get_fmt / .set_fmt
                           └─ .get_selection / .set_selection
sd->entity.ops         -> rkisp_isp_sd_media_ops
```

subdev 表达的是内部总线和处理块，不等于 capture buffer。ISP subdev 注册能证明 pad 和 ops 已发布；不能证明 ISP 算法参数正确或 processed 像素已写内存。

## stream、video_device、vb2_queue 怎样串起来

RK3568 走 `rkisp_register_stream_vdevs()` 的 `ISP_V21` 分支，直接调用 `rkisp_register_stream_v21()`；后者对 MP/SP/DMATX 调用 `rkisp_stream_init()`：

```c
stream = &dev->cap_dev.stream[id];
stream->ispdev = dev;
vdev = &stream->vnode.vdev;

rkisp_init_vb2_queue(&stream->vnode.buf_queue, stream, ...);
rkisp_register_stream_vdev(stream);
```

VB2 初始化建立反向桥：

```c
q->drv_priv = stream;
q->ops = &rkisp_vb2_ops;
q->mem_ops = stream->ispdev->hw_dev->mem_ops;
vb2_queue_init(q);
```

video node 注册再建立正向桥：

```c
vdev->ioctl_ops = &rkisp_v4l2_ioctl_ops;
vdev->fops = &rkisp_fops;
video_set_drvdata(vdev, stream);
vdev->queue = &stream->vnode.buf_queue;
video_register_device(vdev, VFL_TYPE_GRABBER, -1);
```

于是对象路径是：

```text
/dev/videoX
→ struct video_device
  ├─ fops = rkisp_fops
  ├─ ioctl_ops = rkisp_v4l2_ioctl_ops
  ├─ drvdata = struct rkisp_stream
  └─ queue = struct vb2_queue
             ├─ ops = rkisp_vb2_ops
             ├─ drv_priv = 同一个 rkisp_stream
             └─ mem_ops = rkisp_hw_dev 选择的 DMA 策略
```

为什么 `video_device` 与 `vb2_queue` 分开：前者解决“用户打开哪个字符设备、哪个 ioctl 函数接收”；后者解决“REQBUFS/QBUF/STREAMON/DQBUF 中 buffer 怎样流转”。`rkisp_stream` 则把这两套框架状态落到具体 MP/SP 硬件路径。

## `/dev/videoX` 到底在哪生成

`rkisp_register_stream_vdev()` 调用：

```c
ret = video_register_device(vdev, VFL_TYPE_GRABBER, -1);
```

`-1` 表示让 V4L2 Core 动态选择可用 minor。因此源码能证明“会注册一个 video device”，不能从这句单独证明它永远是 `/dev/video0`；实际 `/dev/videoX` 编号受系统中其他 video_device 的注册顺序影响。

节点在哪汇合：`vdev->fops/ioctl_ops/queue/drvdata/caps` 都先赋好，`video_register_device()` 再把完整对象交给 V4L2 Core。随后 `media_create_pad_link()` 把 ISP source 或 CSI source 接到这个 vdev 的 sink pad。

`ls /dev/video*` 能证明节点注册；不能证明 link 已启用、当前节点就是 mainpath、格式正确或能够 DQBUF。要结合 `v4l2-ctl --list-devices` 和 `media-ctl -p` 映射名字。

## RAW 在哪进入 ISP，processed 在哪输出

典型非 HDR MIPI 主路径的软件拓扑是：

```text
IMX415 RAW Bayer
→ MIPI D-PHY source pad
→ rkisp-csi-subdev CSI_SINK
→ rkisp-csi-subdev CSI_SRC_CH0
→ rkisp-isp-subdev RKISP_ISP_PAD_SINK        [RAW 进入 ISP 的 pad 边界]
→ ISP 硬件处理（demosaic / color / NR 等，由软件配置寄存器）
→ rkisp-isp-subdev RKISP_ISP_PAD_SOURCE_PATH [processed 离开 ISP 的 pad 边界]
→ rkisp_mainpath video entity sink
→ resize / MI / DMA
→ VB2 buffer
→ /dev/videoX DQBUF                         [processed 内存输出]
```

`rkisp_create_links()` 对 MIPI 路径真实创建两段内部 link：

```c
media_create_pad_link(&sensor->sd->entity, source_pad,
                      &dev->csi_dev.sd.entity, CSI_SINK, en);
media_create_pad_link(&dev->csi_dev.sd.entity, CSI_SRC_CH0,
                      &dev->isp_sdev.sd.entity, RKISP_ISP_PAD_SINK, en);
```

这里 `sensor->sd` 对典型 MIPI 链可能是 notifier 绑定到 RKISP 的上游 D-PHY subdev，并不应只按变量名断言一定是 IMX415；应看 `entity.function`、mbus type 和实际 `media-ctl -p`。

## 三种“格式”不要混为一个

`_set_pipeline_default_fmt()` 展示了三个层次：

```c
fmt = dev->active_sensor->fmt[0];
fmt.pad = RKISP_ISP_PAD_SINK;
v4l2_subdev_call(isp, pad, set_fmt, NULL, &fmt);  // Sensor RAW 到 ISP sink

if ((code & RKISP_MEDIA_BUS_FMT_MASK) == RKISP_MEDIA_BUS_FMT_BAYER)
    fmt.format.code = MEDIA_BUS_FMT_YUYV8_2X8;
fmt.pad = RKISP_ISP_PAD_SOURCE_PATH;
v4l2_subdev_call(isp, pad, set_fmt, NULL, &fmt);  // processed bus code

rkisp_set_stream_def_fmt(dev, RKISP_STREAM_MP,
                         width, height, V4L2_PIX_FMT_NV12); // 内存 FourCC
```

| 位置                      | 例子                                       | 描述什么                                | 能证明 / 不能证明                                      |
| ----------------------- | ---------------------------------------- | ----------------------------------- | ----------------------------------------------- |
| Sensor/CSI/ISP sink pad | `MEDIA_BUS_FMT_SGBRG10_1X10` 一类 RAW code | entity 之间的 Bayer media-bus 格式       | 能证明软件协商状态；不能证明电气 RAW 到达                         |
| ISP source pad          | `MEDIA_BUS_FMT_YUYV8_2X8`                | ISP processed path 的 media-bus code | 能证明内部 source pad 设定；不能证明最终 buffer 是 packed YUYV |
| MP capture queue        | `V4L2_PIX_FMT_NV12`                      | DMA 写入用户 buffer 的 FourCC/plane 布局   | 能证明当前内存格式；不能证明像素值和 IQ 正确                        |

为什么 ISP source 是 YUYV 而节点是 NV12：一个描述 subdev pad 间的总线语义，一个描述 capture DMA 的内存布局；mainpath/resize/MI 还会按 stream 格式配置输出。

不能从 `_set_pipeline_default_fmt()` 证明每个 IQ 算法已经运行。它只设置默认软件格式；真正开流时 `rkisp_isp_sd_s_stream()`、`rkisp_stream_start()` 等配置硬件，具体图像质量还依赖参数节点与用户态 IQ 策略。

## Async complete：为什么不能在 probe 里一次建完 link

RKISP 内部 CSI/ISP entity 在逻辑 probe 内同步创建；IMX415、D-PHY 等外部 subdev 由各自 driver 独立 probe，先后顺序不固定。因此 notifier 的 `bound` 回调先把到达的 `subdev` 放进 `dev->sensors[]`，全部到齐后才由 `subdev_notifier_complete()`：

```text
subdev_notifier_complete()
├─ rkisp_create_links()                    [外部与内部 entity 在此汇合]
├─ v4l2_device_register_subdev_nodes()
├─ rkisp_update_sensor_info()
└─ _set_pipeline_default_fmt()
```

为什么在 graph mutex 下执行：建 link、发布节点和更新格式会修改同一 Media Graph，需要避免并发看到半完成拓扑。

complete 日志能证明等待集合到齐且上述主线执行到日志点；不能证明 Sensor 已退出 standby、D-PHY 有包、ISP 有帧中断或 VB2 buffer 已 done。

## 大白话与面试问题

`v4l2_subdev` 不直接等于 `/dev/videoX`：CSI/ISP subdev 用 entity、pad 和 ops 表达内部处理模块；`struct video_device` 经 `video_register_device()` 才成为用户态节点；它的 `queue` 指向 `struct vb2_queue`，后者的 `drv_priv` 又指回 `struct rkisp_stream`。RAW 从 CSI source link 进入 ISP sink，processed 数据从 ISP source path 到 mainpath，最后按 NV12 等 FourCC 由 DMA 写入 VB2 buffer。软件图和格式能证明配置关系，不能代替真实 DQBUF 与画质验证。

为什么 `rkisp-isp-subdev` 的 Source 显示 YUYV，但 `/dev/video0` 可以输出 NV12？

**我的回答：**

>

<mark>高亮正确答案：YUYV8_2X8 是 ISP subdev pad 之间的 media-bus code，描述内部处理边界；NV12 是 mainpath capture node 写入内存时使用的 FourCC 和 plane 布局。mainpath/resize/MI 会按 stream 输出格式配置 DMA，所以这两个字段属于不同层，不能要求名字相同。</mark>
