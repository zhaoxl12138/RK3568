# RKISP HW 与逻辑实例生命周期

Source Insight 本篇只沿三份真实源码阅读：`drivers/media/platform/rockchip/isp/hw.c` 中的 HW 生产者，`drivers/media/platform/rockchip/isp/dev.c` 中的逻辑实例生产者，以及 `drivers/media/platform/rockchip/isp/common.c` 中的 `rkisp_attach_hw()` 对象桥。

## 本篇先回答：为什么 RKISP 有两个 probe

这里的两个 probe 不是同一个驱动重复初始化，也不是 HW probe 调用逻辑 probe 的普通函数链。它们对应两个不同的 `platform_device` 和两个不同的对象职责：

```text
HW platform_device
    ↓
rkisp_hw_probe()
    ↓
struct rkisp_hw_dev
    保存寄存器、IRQ、时钟、复位和底层硬件能力

逻辑 rkisp-vir platform_device
    ↓
rkisp_plat_probe()
    ↓
struct rkisp_device
    组织 V4L2、Media、CSI、ISP、capture 和 Sensor 管线
```

硬件对象像“同一台机器的总电控柜”，逻辑对象像“使用这台机器的一条生产线”。逻辑 probe 通过 `rockchip,hw` 的 phandle 找到前面保存的 HW 对象，再把它挂到自己的 `rkisp_device->hw_dev` 中。这个对象桥接关系，正是本篇要追的重点。

## 先给结论：为什么必须拆两个对象

`struct rkisp_hw_dev` 和 `struct rkisp_device` 不是同一对象的两个名字。

| 对象                    | 对象从哪里来                                                               | 主要字段                                                                             | 为什么归它管理                                             |
| --------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------- |
| `struct rkisp_hw_dev` | `rkisp_hw_probe()` 对 HW `platform_device` 执行 `devm_kzalloc`          | `base_addr`、IRQ、`clks[]`、`reset`、`mem_ops`、`isp[]`、`dev_lock`                    | 这些资源对应一块物理 ISP，必须按 HW device 生命周期统一管理，也可能被多个逻辑实例引用  |
| `struct rkisp_device` | `rkisp_plat_probe()` 对 rkisp-vir `platform_device` 执行 `devm_kzalloc` | `v4l2_dev`、`media_dev`、`notifier`、`pipe`、`csi_dev`、`isp_sdev`、`cap_dev`、`hw_dev` | 这些状态描述一套逻辑 Media/V4L2 管线，包含自己的 Sensor、格式、stream 与队列 |

白话：HW 对象是“厂房、机器和总电闸”，逻辑对象是“某条生产线的工位、订单和出货口”。把它们拆开，才能让资源所有权清楚，也能让 `hw->isp[]` 记录多个逻辑实例。

## 第 1 步：两个 platform driver 如何进入总线

```c
static int __init rkisp_hw_drv_init(void)
{
    int ret;

    ret = platform_driver_register(&rkisp_hw_drv);
    if (!ret)
        ret = platform_driver_register(&rkisp_plat_drv);
    return ret;
}
```

- 对象从哪里来：`rkisp_hw_drv` 与 `rkisp_plat_drv` 都是源码中的静态 `struct platform_driver`，各自的 `.probe` 字段分别指向 `rkisp_hw_probe` 和 `rkisp_plat_probe`。
- 谁调用：内核 init 机制通过 `module_init(rkisp_hw_drv_init)` 调用本函数；函数内是对 `platform_driver_register` 的直接调用。
- **为什么先 HW 后逻辑：逻辑 probe 要消费 HW probe 写入 drvdata 的对象。先注册 HW driver 让已有 HW device 先获得匹配机会，减少逻辑消费者先到而取不到对象的窗口。**
- 在哪汇合：这里仅把两个 driver 发布到 Platform 总线；真正的 driver/device 汇合发生在总线匹配后回调各自 `.probe`。
- 证据边界：返回 0 能证明 driver 注册调用成功；不能证明两个 probe 都成功，更不能证明 `/dev/videoX` 或图像帧存在。

## 第 2 步：`rkisp_hw_probe()` 生产 HW 对象

```c
static int rkisp_hw_probe(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;
    struct rkisp_hw_dev *hw_dev;

    hw_dev = devm_kzalloc(dev, sizeof(*hw_dev), GFP_KERNEL);
    dev_set_drvdata(dev, hw_dev);
    hw_dev->base_addr = devm_ioremap_resource(dev, res);
    rkisp_register_irq(hw_dev);
    hw_dev->clks[i] = devm_clk_get(dev, match_data->clks[i]);
    hw_dev->reset = devm_reset_control_array_get(dev, false, false);
}
```

- 参数从哪里来：`pdev` 是 HW DTS 节点被 OF/Platform 创建并与 `rkisp_hw_drv` 匹配后的 `platform_device`。
- 具体字段如何关联：`match->data` 给出 `isp_ver`、clock 表等 SoC 版本数据；resource 映射成 `base_addr`；IRQ、clock、reset 句柄都进入同一个 `hw_dev`；内存条件决定 `mem_ops` 是 RDMA SG、DMA SG 还是 DMA contiguous。
- 为什么用 `devm_*`：资源跟 `&pdev->dev` 绑定，probe 失败或 device 解绑时由 device-managed 机制回收，避免每条错误路径重复释放。
- `dev_set_drvdata(dev, hw_dev)` 做什么：把一个无类型私有指针存进这个 HW `struct device` 的 drvdata 槽。这是对象桥的写端，不是深拷贝。
- 证据边界：HW probe 成功能证明软件已取得并初始化其所需资源；不能证明逻辑 `rkisp_device` 已创建，也不能证明 MMIO 已收到有效 RAW。

## 第 3 步：`rkisp_plat_probe()` 生产逻辑对象

```c
static int rkisp_plat_probe(struct platform_device *pdev)
{
    struct rkisp_device *isp_dev;

    isp_dev = devm_kzalloc(&pdev->dev, sizeof(*isp_dev), GFP_KERNEL);
    dev_set_drvdata(&pdev->dev, isp_dev);
    ret = rkisp_attach_hw(isp_dev);

    isp_dev->pipe.open = rkisp_pipeline_open;
    isp_dev->pipe.close = rkisp_pipeline_close;
    isp_dev->pipe.set_stream = rkisp_pipeline_set_stream;
}
```

这里的 `pdev` 是 rkisp-vir 逻辑节点对应的另一个 `platform_device`。因此两次 `dev_set_drvdata` 虽然 API 相同，但 key 不同：

```text
HW pdev.dev  drvdata ──> struct rkisp_hw_dev
VIR pdev.dev drvdata ──> struct rkisp_device
```

为什么逻辑对象也存 drvdata：remove/shutdown 等回调只收到 `platform_device *`，可用 `platform_get_drvdata(pdev)` 找回这个 probe 创建的 `isp_dev`。它不能用来直接取得另一个 HW device 的 drvdata；跨设备桥接还需要 `rockchip,hw`。

`pipe.open/close/set_stream` 是函数指针赋值，不是此刻执行函数。这样设计让 capture 层只依赖统一 pipeline 接口；直到 VB2 STREAMON，`rkisp_start_streaming()` 才间接调用这些字段。

逻辑 probe 日志能证明代码进入并走到对应位置；不能证明 attach、内部对象注册或 Async complete 全部完成。

## 第 4 步：`rkisp_attach_hw()` 怎样跨两个 device 搭桥

真实定义在 `common.c`，调用点在授权注释范围 `dev.c:rkisp_plat_probe()`：

```c
np = of_parse_phandle(isp->dev->of_node, "rockchip,hw", 0);
pdev = of_find_device_by_node(np);
hw = platform_get_drvdata(pdev);

isp->dev_id = hw->dev_num;
hw->isp[hw->dev_num] = isp;
hw->dev_num++;
isp->hw_dev = hw;
isp->isp_ver = hw->isp_ver;
isp->base_addr = hw->base_addr;
```

对象从哪里来与怎样关联：

1. `isp->dev->of_node` 是逻辑节点。
2. `rockchip,hw` phandle 找到物理 HW 节点；为什么不用全局变量：DTS 明确表达哪条逻辑实例依赖哪块 HW，支持多实例且关系可追踪。
3. `of_find_device_by_node` 从节点取得 HW `platform_device`。
4. `platform_get_drvdata(pdev)` 读取 `rkisp_hw_probe()` 早先 `dev_set_drvdata` 保存的同一 `hw_dev` 指针。
5. 双向关联在这里汇合：`isp->hw_dev = hw` 让逻辑实例访问物理资源，`hw->isp[] = isp` 让共享 HW 反向枚举逻辑实例。

`platform_get_drvdata` 返回非空能证明对象桥已建立；不能证明 `base_addr` 上的硬件状态正确。如果 `hw` 为空，源码返回错误，而不是临时创建假 HW 对象。

## 第 5 步：内部对象在哪汇合

`rkisp_plat_probe()` 注册 `v4l2_device` 与 `media_device` 后，直接调用 `rkisp_register_platform_subdevs(isp_dev)`：

```text
rkisp_register_platform_subdevs()
├─ rkisp_register_isp_subdev()
├─ rkisp_register_csi_subdev()
├─ rkisp_register_bridge_subdev()
├─ rkisp_register_stream_vdevs()
├─ rkisp_register_dmarx_vdev()
├─ rkisp_register_stats_vdev()
├─ rkisp_register_params_vdev()
├─ rkisp_register_luma_vdev()
└─ isp_subdev_notifier()
```

为什么有严格顺序：后面的对象依赖前面的 `v4l2_device/media_device` 与 entity；任何一步失败，goto 标签按相反顺序注销已经成功的对象，避免残留半套图。

这里是驱动内部对象的注册汇合点，但外部 Sensor/D-PHY 可能还没异步到齐。`rkisp_register_stream_vdevs()` 可在此阶段调用 `video_register_device()`，所以 `/dev/videoX` 可能先于完整外部 Media Link 出现。

内部注册全部返回成功能证明软件对象已经交给框架；不能证明 notifier complete，更不能证明真实帧。

## 调用类型速查

- 直接调用：源码里明确写 `rkisp_attach_hw(isp_dev)`。
- 函数指针赋值：`isp_dev->pipe.set_stream = rkisp_pipeline_set_stream`，此时不执行目标函数。
- Platform 框架回调：`.probe = rkisp_plat_probe`，由总线匹配触发。
- Async 框架回调：`.complete = subdev_notifier_complete`，由等待对象到齐触发。
- `container_of`：从内嵌成员地址反查外层对象，不会新建对象。

## 大白话与面试问题

`rkisp_hw_probe()` 成功为什么还没有完整 Camera？

因为它只创建 `rkisp_hw_dev` 并准备寄存器、IRQ、时钟、reset 和 DMA 内存策略。另一个 rkisp-vir probe 才创建 `rkisp_device`，通过 `rockchip,hw` 与 drvdata 取回 HW 指针，再注册 CSI/ISP subdev、stream video nodes 和 notifier；最后还要等 Async complete 把外部 subdev 建进图。HW 日志能证明资源层，不能证明 `/dev/videoX` 可出帧。

`platform_get_drvdata()` 为什么不能省掉，直接把 HW probe 的局部变量交给逻辑 probe？

**我的回答：**

>

<mark>高亮正确答案：两个 probe 属于不同 `platform_device`，执行先后和调用栈彼此独立，HW probe 的局部变量离开函数后也不能作为跨设备接口。HW probe 把长期存在的 `rkisp_hw_dev` 指针写进 HW device 的 drvdata；逻辑 probe 经 DTS `rockchip,hw` 找到同一个 HW device，再用 `platform_get_drvdata()` 取回该指针。drvdata 是跨生命周期对象桥，不是多余绕路。</mark>
