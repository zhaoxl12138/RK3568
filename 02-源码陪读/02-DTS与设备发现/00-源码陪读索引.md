## 关键流程

```text
*.dts/*.dtsi → dtc → DTB
  → unflatten_device_tree() → device_node 树
  ├→ of_platform_populate() → I2C4 platform_device
  │    → I2C 控制器 probe → i2c_add_adapter()
  │         → of_i2c_register_devices()
  │              → i2c_new_device() → 4-001a-1 i2c_client
  └→ endpoint/phandle 暂存在 fwnode 图中，供 Camera 驱动稍后解析
```

## 带注释代码

```c
void of_i2c_register_devices(struct i2c_adapter *adap)
{
    for_each_available_child_of_node(adap->dev.of_node, node) {
        /* 遍历 I2C4 下 status 可用的子节点 */
        client = of_i2c_register_device(adap, node); // 直接调用
    }
}
```

调用类型：遍历宏由预处理器展开；`of_i2c_register_device()` 是直接调用；`client->dev.of_node = ...` 是字段赋值与对象关系；后面的 driver probe 由框架回调。

### C/DTS 基础

`&i2c4` 是对已有 label 的引用并修改该节点，不是 C 语言取地址。`<&cru CLK_CIF_OUT>` 是 phandle 加参数；`<&gpio3 RK_PB6 GPIO_ACTIVE_LOW>` 由对应 provider 框架解释。

## 大白话解释

DTS 不是一段按行执行的 C 程序，而是一份树形硬件档案。内核先把压平的 DTB 恢复成节点树；不同父总线再负责把自己的孩子翻译成合适对象。因此 I2C4 控制器是 Platform device，I2C4 下面的 IMX415 是 I2C client。

## 板端证据边界

```bash
NODE=/sys/firmware/devicetree/base/i2c@fe5d0000/imx415@1a
tr -d '\0' < "$NODE/compatible"
od -An -tx1 "$NODE/reg"
cat /sys/bus/i2c/devices/4-001a-1/uevent
```

- 能证明：运行 DTB 确实包含节点，地址被解析并创建 client。
- 不能证明：DTS 内容与原理图一定正确，也不能证明 Sensor 对 0x1a 有应答。

## 面试问题

为什么整个 IMX415 节点写在 `&i2c4` 下面，但图像数据不经过 I2C？

**我的回答：**


<mark>高亮正确答案：父子关系描述控制和设备发现：IMX415 通过 I2C4 配置寄存器；节点内部 port/endpoint 另行描述 RAW 图像通过 MIPI CSI-2 发向 D-PHY。I2C 是控制面，MIPI 是数据面。</mark>
