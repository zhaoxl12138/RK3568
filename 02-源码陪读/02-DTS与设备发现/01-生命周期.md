# 02-01 生命周期：DTB、OF 与 Platform 设备

## Source Insight 定位

按下列顺序打开：

1. `arch/arm64/boot/dts/rockchip/rk3568-atk-evb1-ddr4-v10.dtsi`，搜索 `imx415@1a`。
2. `drivers/of/fdt.c`，搜索 `unflatten_device_tree`。
3. `drivers/of/platform.c`，搜索 `of_platform_default_populate_init`、`of_platform_populate`、`of_platform_device_create_pdata`。
4. `drivers/base/platform.c`，搜索 `platform_device_add`。

E 盘用于陪读，WSL `/home/rk3568/work/rk3568_linux_sdk/kernel` 用于验证真实编译版本。

## 生命周期

```text
DTS/DTSI include 合并
→ dtc 编译成 DTB
→ bootloader 把 DTB 地址交给内核
→ unflatten_device_tree()
→ struct device_node 树
→ of_platform_default_populate_init()
→ of_platform_populate()
→ 适合 Platform bus 的节点变 platform_device
```

注意：`imx415@1a` 不是在这里直接生成 platform_device；它由 I2C adapter 的 OF 代码处理。

## 代码片段与调用关系

```c
void __init unflatten_device_tree(void)
{
    __unflatten_device_tree(initial_boot_params, NULL,
                            &of_root, early_init_dt_alloc_memory_arch);
    /* 直接调用：把 flat blob 恢复为 device_node 对象树 */
}

static int __init of_platform_default_populate_init(void)
{
    of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL);
    /* 直接调用：从 OF 树选择并创建 Platform 设备 */
    return 0;
}
```

调用类型：`arch_initcall_sync(of_platform_default_populate_init)` 是宏生成 initcall 登记；内核启动时通过函数指针框架回调该函数，不是源码中某个普通函数直接调用。

### C 基础：`__init` 和 initcall

`__init` 把初始化代码放入特定段，启动完成后相关内存可释放。`arch_initcall_sync(fn)` 把 `fn` 地址放进内核初始化表；后续启动框架遍历表并调用它。

## 大白话解释

DTB 是压缩档案，`unflatten` 像解包成内存中的文件夹树。`of_platform_populate()` 再按规则把 SoC 内部可枚举节点办成 Platform 身份证。挂在 I2C 总线下面的孩子由 I2C 部门接手，不是一律办 Platform 身份证。

## 板端证据边界

```bash
find /sys/firmware/devicetree/base -maxdepth 2 -name 'i2c@fe5d0000'
ls -ld /sys/bus/platform/devices/fe5d0000.i2c
```

- OF 路径能证明运行时 device_node 存在。
- platform devices 中 I2C 控制器能证明它已被 OF/Platform 创建。
- 不能据此证明控制器 probe 成功注册 adapter，也不能证明 IMX415 client 已创建。

## 面试问题

`status = "okay"` 会直接调用该节点对应的 `probe()` 吗？

**我的回答：**


<mark>高亮正确答案：不会。它使节点在设备发现时属于 available；随后框架创建相应 device。只有匹配的 driver 也注册并由 bus match 成功后，Driver Core 才进入 probe。</mark>
