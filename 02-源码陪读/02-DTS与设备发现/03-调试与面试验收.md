## 一次完成运行时审计

```bash
NODE=/sys/firmware/devicetree/base/i2c@fe5d0000/imx415@1a

ls -l "$NODE"
tr -d '\0' < "$NODE/compatible"; echo
tr -d '\0' < "$NODE/status"; echo
od -An -tx1 "$NODE/reg"

cat /sys/bus/i2c/devices/4-001a-1/uevent
readlink -f /sys/bus/i2c/devices/4-001a-1/driver
```

## 代码片段：OF 信息怎样进入 client

```c
client->addr = info->addr;                    // 字段赋值：来自 reg
client->dev.of_node = of_node_get(info->of_node); // 对象关系：保留 DTS 节点
client->dev.bus = &i2c_bus_type;               // 对象关系：归属 I2C bus
device_register(&client->dev);                 // 直接调用：加入驱动模型
```

之后 `i2c_device_match()` 通过 `client->dev.of_node` 与 driver 的 `of_match_table` 比较，这是框架回调匹配，不是 DTS 主动调用驱动。

### C 基础：为什么用 `tr -d '\0'`

DT 字符串属性以 NUL 字节结尾。sysfs 暴露的是二进制属性内容，`tr -d '\0'` 只是删除结尾的零字节；`reg` 是 32 位 big-endian cell，所以用 `od -tx1` 能看到 `00 00 00 1a`。

## 大白话排错顺序

1. 路径不存在：当前 DTB 不含节点，或节点路径/板型选错。
2. 节点存在但无 `4-001a-1`：查 I2C4 控制器、adapter 和子节点 available 状态。
3. client 存在但 driver 链接不存在：查驱动编译/加载和 compatible。
4. 已绑定但 ID 失败：进入 Sensor 资源、上电和 I2C 硬件排查。

## 板端证据能/不能证明

- `status=okay`：能证明运行 DT 认为节点可用；不能证明驱动已注册。
- `MODALIAS=of:...sony,imx415`：能证明匹配标识已经进入设备对象；不能证明有驱动接受它。
- driver 链接存在：能证明完成绑定；不能证明 MIPI endpoint 和抓帧正常。

## 面试问题

如果板端不存在 `/sys/firmware/devicetree/base/i2c@fe5d0000/imx415@1a`，第一反应应该改 `imx415_probe()` 吗？

**我的回答：**


<mark>高亮正确答案：不应该。probe 还没有设备入口。应先确认实际启动 DTB/BoardConfig、DTS include 链和节点 status，再确认 I2C4 路径。只有运行时节点和 client 已存在后，才进入驱动匹配与 probe 排查。</mark>
