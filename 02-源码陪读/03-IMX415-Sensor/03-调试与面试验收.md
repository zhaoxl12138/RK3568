## probe 后半段：把 Sensor 交给 Camera 框架

```c
sd = &imx415->subdev; // 字段取地址：私有对象包含一个 subdev

v4l2_i2c_subdev_init(sd, client, &imx415_subdev_ops);
/* 直接调用：关联 client、sd 和 ops；不执行所有 ops */

imx415->pad.flags = MEDIA_PAD_FL_SOURCE; // 字段赋值：Sensor 是数据源
sd->entity.function = MEDIA_ENT_F_CAM_SENSOR;
media_entity_pads_init(&sd->entity, 1, &imx415->pad); // 直接调用：创建端口

v4l2_async_register_subdev_sensor_common(sd);
/* 直接调用注册动作；未来与 D-PHY 的绑定由 Async 框架回调 */
```

## 交接边界

```text
I2C Driver 负责：匹配、probe/remove、资源与硬件通信
V4L2 Subdev 负责：格式、controls、s_stream 等 Camera 能力入口
Media Controller 负责：entity、Source Pad、与 D-PHY 的 Link
```

注册完成不等于执行 `imx415_s_stream()`；应用真正 STREAMON 后，V4L2/RKISP 才沿 pipeline 回调开流入口，最终由 `__imx415_start_stream()` 写模式表并退出 standby。

## 调用类型与 C 基础

- `sd = &imx415->subdev`：对象包含关系。
- `sd->ops = ops`：函数表指针赋值。
- `v4l2_async_register_subdev_sensor_common(sd)`：直接调用的注册动作。
- Async `.bound()`：未来匹配时的框架回调。
- `MEDIA_PAD_FL_SOURCE`：位标志常量；Source 表示数据从该 pad 流出。

## 大白话解释

读 ID 后，驱动只是证明“这颗芯片能对话”。接着它要办理 Camera 身份：告诉 V4L2 自己支持哪些操作，告诉 Media Controller 自己有一个 RAW 输出口，再登记到异步匹配名单。等 D-PHY 也准备好后，框架才把上下游连起来。

## Bring-up 证据树

```bash
# Sensor 控制面
dmesg | grep -E 'imx415|Detected|set fmt|exposure'
cat /sys/class/video4linux/v4l-subdev3/name

# 拓扑交接
media-ctl -p

# 真正出流
v4l2-ctl -d /dev/video0 --stream-mmap=4 --stream-count=30 --stream-to=/tmp/imx415.raw
```

- subdev 名称能证明 Sensor 已注册进 V4L2。
- Source Pad 与 `[ENABLED]` 能证明 Media 拓扑交接完成。
- 仍不能证明帧有效；要以 STREAMON、帧计数、文件大小和画面内容验证。

## 面试问题

一个新 Sensor 已能读 ID，但 `media-ctl -p` 看不到 Sensor entity，你会优先检查什么？

**我的回答：**


<mark>高亮正确答案：说明 I2C 控制面已通，但 V4L2/Media 交接未完成。我会检查 probe 在读 ID 后是否因 controls、media_entity_pads_init 或 v4l2_async_register_subdev_sensor_common 失败而退出，再核对 endpoint/fwnode 和 Async 绑定日志，而不是重新怀疑 I2C 地址。</mark>
