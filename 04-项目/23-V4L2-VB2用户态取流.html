当前 阶段 05 · V4L2 Subdev

应用怎样从 /dev/video0 领回一帧

/dev/video0 是已经注册好的 video_device，不是 Sensor。V4L2 Core 分发 ioctl，VB2 管 buffer 状态，RKISP/DMA 完成后才由 DQBUF 交回用户态。

本章只追一条线：fd → ioctl → VB2 → DMA → DQBUF

图 1 · 先看注册时挂表，运行时怎样找到 RKISP/VB2图 2 · 再看从 open、ioctl 到 IRQ、DQBUF 的完整闭环图 3 · 最后看一个 buffer 在应用、驱动和硬件之间怎样换手

V4L2 ioctl

把应用的 VIDIOC_* 命令按 ioctl_ops 分给格式函数或 VB2 通用入口。

VB2

管理 buffer 的申请、映射、状态、完成队列和唤醒；它不产生像素。

RKISP / DMA

从 VB2 接走 ACTIVE buffer 的 DMA 地址；帧结束中断确认完成后才调用 vb2_buffer_done()。

图 1：注册时挂表，运行时查表

虚线是赋值关系；实线是实际调用。

大白话：注册期只是把 fops、ioctl_ops 和 queue 这三张“联系电话表”挂进 video_device；应用真正发起 ioctl 时，V4L2 Core 才读取这些指针并回调 RKISP 或 VB2。

图 2：控制请求向右，完成帧再向左

绿色只表示 DMA 完成后的帧交接，不是普通函数调用。

图 3：同一个 buffer 在谁手里？

状态机直接解释为什么 DQBUF 会阻塞或返回。

实线：直接调用 / 控制流虚线：对象赋值 / 函数表关系绿色：DMA 完成后的帧交接

证据边界：open、S_FMT、REQBUFS、QBUF 和 STREAMON 都只证明各自步骤返回成功；只有持续成功 DQBUF，并看到合理的 bytesused / sequence / timestamp，才能证明完成 buffer 已回到用户态。

DQBUF 超时先看哪里

从右向左查：mi_frame_end 是否命中 → vb2_buffer_done(DONE) 是否执行 → ACTIVE buffer 是否有 DMA 地址 → 上游是否真开流。

NV12 提醒

Video Capture Multiplanar 表示 mplane API；实际 num_planes 以驱动回填为准，不能只靠 FourCC 猜。

30 秒面试表达

RKISP 注册 node 时挂 fops、ioctl_ops 与 VB2 queue。应用 ioctl 经 V4L2 两级分发进入 RKISP/VB2；QBUF 交空 buffer，STREAMON 回调驱动启动 DMA；帧结束中断调用 buffer done，DQBUF 才能领回完成帧。
