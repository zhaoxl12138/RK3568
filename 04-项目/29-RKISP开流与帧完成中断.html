阶段 07 · 专题 3/3

开流与帧完成中断

把两件事彻底分开：STREAMON 是控制流从应用向上游逐层启动；帧结束中断则是像素真正写入内存后，buffer 从硬件返回应用。

图 1 · 进入 RKISPV4L2/VB2 如何回调 rkisp_start_streaming()图 2 · 两段启动先配置本地 MI，再通过 pipeline 启动上游 subdev图 3 · 真实帧MI 中断怎样把 ACTIVE buffer 交回 VB2

直接调用

RKISP 驱动函数内部按源码顺序调用，用灰蓝实线。

框架回调

V4L2/VB2 或函数指针间接进入驱动，用紫色虚线。

数据流 / Buffer 所有权

RAW、DMA 与 buffer 状态返回，用绿色线。

图 2：先启动 RKISP 本地采集，再启动整条上游管线

rkisp_start_streaming()
rkisp_stream_start()：先准备本地 MI/DMA
pipe.set_stream(..., true)
rkisp_pipeline_set_stream()
ISP → CSI → D-PHY → Sensor：各模块 s_stream(1)
RAW 数据再从 Sensor 反向流回 MI

为什么本地先启动？

先准备 DMA 地址和接收状态，再让 Sensor 发帧，可以避免第一批像素到达时没有可写 buffer。这里是源码顺序，不是两条并行初始化线。

应用 VIDIOC_DQBUF 取回该帧

Source Insight 只追三组

capture_v21.c · 启动

rkisp_start_streaming() → rkisp_stream_start() → pipe.set_stream。

dev.c · 上游

rkisp_pipeline_set_stream()：看函数指针如何变成各 subdev 的 s_stream(1)。

capture_v21.c · 完帧

rkisp_mi_v21_isr() → mi_frame_end() → vb2_buffer_done(DONE)。

证据强度

STREAMON 返回 0

证明软件启动链没有立即失败；不能证明已经收到一帧。

MI frame-end IRQ

证明 RKISP MI 看到了帧完成事件；比开流成功更接近真实数据证据。

连续 DQBUF

证明 buffer 被反复填充并交回应用；下一阶段继续看 VB2 状态机和用户态循环。
