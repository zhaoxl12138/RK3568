当前 阶段 05 · V4L2 Subdev

RK3568 Camera：从 DTS 到 /dev/videoX 的真实启动时序

这页只追一条可落地的主线：DTS 如何让 RK3568 控制器和 IMX415 出现，驱动如何完成 probe，Media Graph 如何建立，以及应用开流后图像才怎样真正流动。

返回学习驾驶舱前置：总线分层详解：IMX415 / I2C继续：V4L2 subdev详解：D-PHY / Media
先记住 1

不是一条函数直线

驱动注册和设备创建是两个独立准备入口，谁先发生不固定；双方都出现后才进入匹配。

先记住 2

启动先建对象

开机阶段主要创建 device、driver、client、subdev、entity 和 video node，还没有持续图像帧。

先记住 3

Sensor 通过 I2C 控制

IMX415 的 ID、曝光、模式寄存器由 I2C 读写；图像数据走 MIPI CSI-2，不走 I2C。

先记住 4

STREAMON 才开始出图

probe 成功只能证明设备被识别和注册；应用开流后，Sensor、D-PHY、CSI、ISP 才连续工作。

一条真实主线：两个启动入口，四个连续阶段

按启动时间拆成四个阶段

1

DTS 被解析

静态配置 → 运行时对象
  • 父节点 i2c@fe5d0000 描述 I2C4 控制器。
  • 子节点 imx415@1a 描述 I2C 外设。
  • port/endpoint 描述图像数据连接。
2

I2C 控制器与 Sensor

控制器 Platform → 外设 I2C
  • rk3x_i2c_probe() 初始化控制器并注册 adapter。
  • of_i2c_register_devices() 创建 i2c_client。
  • 驱动注册和 client 创建先后可变化，匹配后进入 probe。
3

V4L2 / Media 建链

软件对象 → 图像拓扑
  • IMX415 注册 Sensor subdev。
  • D-PHY 解析 endpoint，创建 Sink/Source pad。
  • 异步 notifier 把各个 subdev 绑定进 Media Graph。
4

应用真正开流

video node → 硬件帧流
  • /dev/video0 是用户态入口，不是 Sensor 本身。
  • STREAMON 后才请求持续输出。
  • 最终要用抓帧结果和错误日志证明出图。

板端证据

dmesg | grep -Ei 'imx415|i2c|csi|rkisp'
ls -l /sys/bus/i2c/devices/4-001a-1
media-ctl -p
v4l2-ctl --list-devices
v4l2-ctl -d /dev/video0 --all

面试版回答：启动时，内核先根据 DTS 创建设备对象；RK3568 内部 I2C 控制器由 Platform Driver probe 并注册 I2C adapter，adapter 再根据 DTS 创建 IMX415 的 I2C client。IMX415 I2C Driver 匹配成功后进入 imx415_probe()，完成上电、读 ID 和 V4L2 Sensor subdev 注册。之后 D-PHY、CSI、ISP 通过异步 notifier 建立 Media Graph，应用对 /dev/video0 执行 STREAMON 后，图像才沿 MIPI CSI-2 → D-PHY → CSI → ISP 连续流动。

排障边界：Detected imx415 id 0000e0 只能证明 I2C 控制面识别成功；media-ctl -p 只能证明拓扑存在；真正证明出图，还需要 STREAMON、抓帧成功，并结合 MIPI/CSI/RKISP 日志。
