Linux 通用驱动模型

模块 2 · 中介 / 翻译员

I2C Core

I2C adapter 注册时，由 OF 辅助代码解析 DTS 子节点并创建 i2c_client；I2C Core 提供 match、probe、remove 规则。client 只是设备对象，不是驱动。

模块 3 · 真正干活的人

IMX415 驱动

获取时钟和 GPIO、执行上电时序、读取芯片 ID，并注册 V4L2 subdev。

本页名词定位：只讲 IMX415 与 I2C 驱动匹配

IMX415

外部硬件 Sensor。上电并经过 I2C 配置后，将光转换为 RAW10；本页的 imx415_probe() 负责让它先被识别并注册为 V4L2 subdev。

I2C Core

Linux 内核的 I2C 子系统，不是 Sensor 驱动。它解析 I2C4 下的 DTS、创建 i2c_client，并提供 match / probe / remove 规则。

i2c_client

内核中的 I2C 设备对象。本板的 4-001a-1 表示 I2C4、地址 0x1a；它是“设备档案”，不是驱动。

compatible

DTS 中的硬件型号标记，例如 sony,imx415。I2C Core 用它与驱动的 imx415_of_match[] 比较，决定是否绑定。

Linux 通用驱动模型

内核通用的 device / driver 管理框架。它不懂 IMX415，也不懂 I2C 细节；它只负责在设备和驱动就绪后发起匹配和 probe。

V4L2 subdev

内核中的媒体功能模块对象。Sensor 注册成 subdev 后，才能被后续 D-PHY、CSI、RKISP 的 Media Graph 发现和绑定；它还不是 /dev/video0。

匹配开始前：谁决定驱动是否注册

起点 A · 驱动路径

内核配置 / 模块加载

  • CONFIG_VIDEO_IMX415=y：编进内核，开机注册驱动。
  • =m：生成 imx415.ko，模块加载后注册。
  • 未启用：驱动不参与编译，不可能进入匹配。
起点 B · 设备路径

DTS / i2c_client

  • &i2c4 和 reg=<0x1a> 创建 I2C 设备档案。
  • client->dev.of_node 指向同一个 imx415@1a 节点。
  • 匹配时才拿 DTS 的 compatible 与驱动支持表比较。
先记住：DTS 不负责挑选并注册内建驱动；配置决定哪些驱动存在，compatible 决定当前 client 与哪个驱动绑定。

IMX415 驱动 · 第 1 阶段

sensor_mod_init()

它不直接操作 Sensor，只把 imx415_i2c_driver 交给 I2C Core。登记表中已经保存了 compatible、imx415_probe 和 imx415_remove。

交给：i2c_add_driver() → i2c_register_driver()

为什么有两个 probe

I2C Core 的 probe

i2c_device_probe(dev)

  • 接收通用的 struct device *
  • 转换成 struct i2c_client *
  • 找到具体 struct i2c_driver
  • 通过 driver->probe(client, id) 转交任务
IMX415 的 probe

imx415_probe(client, id)

  • 读取 IMX415 的 DTS 属性
  • 获取 MCLK、RESET、PDN 和电源
  • 执行上电并通过 I2C 读取芯片 ID
  • 注册 V4L2 subdev，等待 CSI/ISP 绑定

I2C Core 比较 compatible

设备和驱动都写着 sony,imx415，所以确认可以配对。

04 · 正式派工
两级 probe 完成交接

I2C Core 把通用 device 翻译成 client，再让 IMX415 驱动真正上电读 ID。
