RKISP：共享硬件、逻辑实例与 Video Node

RKISP 是 RK3568 内部的 ISP 硬件及其 Linux 驱动，不是第三方用户态库。HW probe 集中管理寄存器、IRQ、时钟；逻辑 probe 组装 CSI/ISP/stream 对象，最后把 mainpath 注册成 /dev/video0。

两条初始化分支汇合，再串行注册 ISP 与采集节点

实线：直接调用 / 控制流虚线：赋值 / 对象关联 / 数据依赖绿色实线：开流后的图像数据方向

分支 A：共享 HW 资源初始化

platform_driver_register(&rkisp_hw_drv) 发布回调表；匹配后 rkisp_hw_probe() 面向真正的 ISP 硬件，集中取得寄存器、IRQ、时钟、复位和内存操作，最后留下一个 struct rkisp_hw_dev。它解决的是“硬件资源由谁管理”。

分支 B：逻辑 Camera 管线初始化

platform_driver_register(&rkisp_plat_drv) 发布另一张回调表；匹配后 rkisp_plat_probe() 创建 struct rkisp_device，负责 V4L2、Media、CSI、ISP subdev 和采集流。它解决的是“一条 Camera 管线如何组织”。

汇合以后仍不能证明已经出图

两个对象在 rkisp_attach_hw() 汇合后，才能注册内部对象和 Video Node；但 /dev/videoX 可能先于 Async complete 出现， 还不能证明 D-PHY、Sensor 与帧数据已经全部到达。

图 2：两个 Platform Driver 不是父子调用，靠对象桥在逻辑层汇合

先分清“注册 driver”“Platform Core 回调 probe”“驱动里直接调用”三种箭头。

怎样按图追代码：先在 hw.c 搜 rkisp_hw_drv_init，确认它连续注册两个 platform_driver。接着分别读 rkisp_hw_probe 与 rkisp_plat_probe；只在后者里追 rkisp_attach_hw，再跳 common.c 看 rockchip,hw、platform_get_drvdata 如何拿到同一个 rkisp_hw_dev。 两个 probe 都是 Platform Core 的独立回调，不是 HW probe 直接调用逻辑 probe。

大白话

HW 层像统一机房，管理寄存器、时钟、IRQ；逻辑层像 Camera 项目组，拿着 HW 对象组装 CSI、ISP 和输出节点。这样多个逻辑实例不用各自重复占用同一套物理资源。

证据边界

rkisp driver version 证明逻辑 probe 执行；出现 /dev/video0 证明 video_device 注册。两者都不能保证 RAW 已进入 ISP 或 DQBUF 能得到有效帧。

面试表达

RKISP 驱动分 HW 与逻辑实例：HW probe 管共享资源，逻辑 probe attach HW 后注册 CSI/ISP subdev 和 stream video_device；mainpath 通过 video_register_device() 暴露用户态节点。

Source Insight：drivers/media/platform/rockchip/isp/hw.c → rkisp_hw_probe()；dev.c → rkisp_plat_probe()、rkisp_register_platform_subdevs()；capture.c → rkisp_register_stream_vdev()。
