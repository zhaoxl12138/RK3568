阶段 04 · 源码主线

RK3568 D-PHY：从 DTS 到 Media Graph

把 rockchip-csi2-dphy0 从“设备树里的一段配置”，追到 Platform probe、V4L2 Subdev、Async bound，以及 media-ctl -p 中真正可见的 Entity / Pad / Link。

本页目标：不只记函数名，而是能说明“谁创建对象、谁保存函数地址、谁在什么时候回调、最后用什么证据验证”。

先看完整总图 开始追源码 直接做调试验收 打开 00–06 陪读笔记
00 总图 01 HW Driver 02 逻辑 D-PHY 03 Subdev / Pads 04 Endpoint / Async 05 Bound / Link 06 调试验收
00

先纠正阅读起点：设备线和驱动线先各自准备，再在匹配处汇合

这不是普通 C 程序的单线调用链。DTS 负责形成设备，模块初始化负责注册驱动，两边谁先出现都可以由框架管理。

先记住：.probe = fn 只是保存函数地址；只有设备和驱动 compatible 匹配后，Platform 总线框架才会回调 probe。

赋值：保存地址/数据 注册：交给框架管理 框架回调：匹配后调用 直接调用：源码里能看到 fn() DTS 引用：描述对象关系

大白话

设备像“求职者档案”，驱动像“岗位能力说明”。两份资料都交给 Platform 总线框架，框架比较 compatible，合适才安排 probe 见面。

箭头类型

.probe = rockchip_csi2_dphy_hw_probe 是赋值；platform_driver_register() 是注册；真正进入 probe 是框架回调。

常见误区

“编译系统找到驱动并执行 probe”不准确。编译只决定代码有没有进入系统；注册、匹配和 probe 属于后续生命周期。

01

HW Driver：先把共享物理硬件准备好

本 BSP 先注册 HW Platform Driver。匹配物理节点后进入 HW probe，准备 MMIO、时钟、GRF 和 stream ops，最后再注册逻辑 D-PHY driver。

大白话

HW probe 像先把“公共机房”准备好：寄存器地址、时钟、GRF、开停能力都集中管理。它还没有建立 Camera Media Graph。

源码入口

Source Insight 先打开精确文件，再搜符号：

drivers/phy/rockchip/phy-rockchip-csi2-dphy.c

rockchip_csi2_dphy_hw_driver、rockchip_csi2_dphy_hw_probe

调试边界

csi2 dphy hw probe successfully! 只能证明物理 D-PHY 资源准备完成，不能证明逻辑 D-PHY、Sensor bound 或图像帧正常。

展开关键代码：为什么搜索不到谁直接调用 HW probe 
static struct platform_driver rockchip_csi2_dphy_hw_driver = {
    .probe = rockchip_csi2_dphy_hw_probe,
    .remove = rockchip_csi2_dphy_hw_remove,
    .driver = {
        .name = "rockchip-csi2-dphy-hw",
        .of_match_table = rockchip_csi2_dphy_hw_match_id,
    },
};

module_platform_driver(rockchip_csi2_dphy_hw_driver);
  • .probe = ... 只是结构体成员赋值，保存函数地址。
  • 宏生成模块 init/exit，初始化时把 driver 注册给 Platform 总线框架。
  • 匹配成功后框架通过函数指针回调，所以普通 Caller 搜索可能看不到直接调用者。
02

逻辑 D-PHY：第二次匹配后，通过 phandle 取回共享 HW 对象

这里不是同一个设备 probe 两次。物理 HW 节点和逻辑 csi2_dphy0 节点分别形成两个 platform_device、两个私有对象。

大白话

逻辑 D-PHY 像“Camera 管线里的一个工位”；物理 HW 像“共用机器”。工位只保存机器句柄，不会再次买一台机器或重复初始化寄存器。

对象关系

struct csi2_dphy_hw 管寄存器、时钟、GRF；struct csi2_dphy 管 V4L2 Subdev、Pads、Endpoint、Sensor 和 Media Graph。

调试边界

有 HW probe、没有逻辑 probe：优先检查逻辑节点是否 okay、compatible 是否匹配、逻辑 driver 是否已成功注册。

展开关键代码：DTS phandle 怎样变成 C 指针 
node = of_parse_phandle(dev->of_node, "rockchip,hw", 0);
pdev = of_find_device_by_node(node);
dphy_hw = platform_get_drvdata(pdev);
csi2dphy->dphy_hw = dphy_hw;
  • rockchip,hw = <&csi2_dphy_hw> 是静态引用，不是函数调用。
  • 真正的查找发生在逻辑 probe 的 attach_hw() 中。
  • platform_get_drvdata() 取回的是 HW probe 之前保存的私有对象。
03

V4L2 Subdev 与 Pads：让逻辑 D-PHY 具有 Camera 框架身份

驱动私有结构体仍然只是 Rockchip 自己认识的对象。只有初始化 v4l2_subdev、media_entity 和 pads，Media Controller 才能描述它。

大白话

v4l2_subdev_init() 像给 D-PHY 办“Camera 框架身份证”；media_entity_pads_init() 再给它登记两个端口。

ops 是什么

ops = operations。sd->ops = ops 保存能力表地址，未来 V4L2 按需调用；probe 阶段不会把所有回调执行一遍。

调试边界

media_entity_pads_init() 只建立 entity 对 pads 的所有权和编号，不创建 Sensor→D-PHY link。

展开关键代码：subdev_init 和 pads_init 分别做什么 
v4l2_subdev_init(&dphy->sd, &csi2_dphy_subdev_ops);

dphy->pads[CSI2_DPHY_RX_PAD_SINK].flags =
    MEDIA_PAD_FL_SINK | MEDIA_PAD_FL_MUST_CONNECT;
dphy->pads[CSI2_DPHY_RX_PAD_SOURCE].flags =
    MEDIA_PAD_FL_SOURCE | MEDIA_PAD_FL_MUST_CONNECT;

media_entity_pads_init(&dphy->sd.entity, 2, dphy->pads);
  • sd = sub-device，表示它不是最终给应用抓帧的 video node。
  • pad0 Sink 接收 IMX415，pad1 Source 输出给下游 RKISP CSI。
  • 此时端口已经存在，但上游 Sensor link 还要等 Async bound。
04

Endpoint 与 Async Notifier：把静态连接声明变成“等待谁”的条件

remote-endpoint 只描述板级连接。驱动解析 port@0 后，把远端 IMX415 fwnode 和 Lane 信息保存为 Async 等待项。

大白话

Async notifier 不是站在原地“等人”。它把 IMX415 的识别条件挂到 waiting 清单后就返回；以后对象出现，框架再通知。

源码入口

先搜 rockchip_csi2_dphy_fwnode_parse，再看：

v4l2_async_notifier_parse_fwnode_endpoints_by_port()

最后跟到 v4l2_async_subdev_notifier_register()。

调试边界

notifier 注册成功只代表“等待关系已经登记”，不能证明IMX415 已经匹配，更不能证明 Media Link 已经创建。

展开关键代码：解析 port@0 与登记等待关系 
v4l2_async_notifier_parse_fwnode_endpoints_by_port(
    dphy->dev, &dphy->notifier,
    sizeof(struct sensor_async_subdev),
    0, rockchip_csi2_dphy_fwnode_parse);

dphy->notifier.ops = &rockchip_csi2_dphy_async_ops;
v4l2_async_subdev_notifier_register(&dphy->sd,
                                    &dphy->notifier);
  • port = 0 表示只解析 D-PHY 的输入端。
  • parser 决定“等谁”和保存哪些 Lane 参数。
  • notifier ops 决定匹配成功后“做什么”，其中最关键的是 .bound。
05

Bound 与 Media Link：静态 endpoint 最终变成运行时图中的一条边

Sensor fwnode 匹配后，V4L2 Async 框架回调 notifier.ops->bound()。Rockchip 回调保存真实 Sensor subdev，并显式调用 media_create_pad_link()。

大白话

endpoint 是“图纸上说应该相连”；Async bound 是“运行时双方终于到齐”；media_create_pad_link() 才是“把软件拓扑里的线真正画出来”。

源码入口

Source Insight 精确搜：

rockchip_csi2_dphy_notifier_bound

然后跟到 media_create_pad_link()，逐个核对 Source entity/pad、Sink entity/pad 和 flags。

调试边界

[ENABLED] 证明软件拓扑存在并启用，不能证明物理 Lane 已有稳定数据，也不能单独证明应用已经收到帧。

展开关键代码：谁真正创建 Sensor → D-PHY 的 link 
sensor->sd = sd;

for (pad = 0; pad < sensor->sd->entity.num_pads; pad++)
    if (sensor->sd->entity.pads[pad].flags &
        MEDIA_PAD_FL_SOURCE)
        break;

media_create_pad_link(
    &sensor->sd->entity, pad,
    &dphy->sd.entity, CSI2_DPHY_RX_PAD_SINK,
    MEDIA_LNK_FL_ENABLED);
  • 先在 Sensor entity 中找到 Source pad，IMX415 实际为 pad0 Source。
  • D-PHY 的目标端是 pad0 Sink。
  • media_entity_pads_init() 和 media_create_pad_link() 是两件不同的事。
06

调试证据与面试验收：寻找最早缺失的一层

不要从“没有图”直接猜 Lane 或 ISP。按运行时 DTS、两个 probe、Async match、Media Graph、真实帧依次确认。

大白话

每条日志都像闯关盖章：上一关通过不等于后面全通过。Sensor ID 成功只证明 I2C 控制面；Media Link 正常只证明软件拓扑面。

板端命令

dmesg | grep -Ei 'csi2|dphy|imx415|rkisp'
media-ctl -p
v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=30

调试边界

Link 已是 [ENABLED] 但抓不到帧时，转入数据面检查：Sensor s_stream(1)、格式、Lane、link frequency、时钟、电源以及 CSI 错误计数。

误区：HW probe 直接调用逻辑 probe

实际是 HW probe 注册逻辑 driver，随后 Platform 总线框架再次匹配并回调逻辑 probe。

误区：DTS phandle 会调用 HW 驱动

phandle 只描述引用；逻辑 probe 用 node→platform_device→drvdata 取得对象。

误区：Async 会阻塞等待 Sensor

未匹配项进入 waiting 后立即返回，未来对象注册时再触发匹配。

误区：[ENABLED] 就代表稳定出图

它只证明 link 已建立和启用；真实数据还要靠 STREAMON、帧计数和抓帧证明。

面试表达：30 秒版本

RK3568 的 CSI2 D-PHY 驱动分成物理 HW 和逻辑 Camera 实例两层。HW Platform Driver 先准备寄存器、时钟、GRF 和共享能力，再注册逻辑 driver；Platform 总线框架第二次匹配后回调逻辑 probe，逻辑对象通过 rockchip,hw phandle 取得 HW drvdata。随后驱动初始化 V4L2 Subdev 和 Sink/Source Pads，把 port@0 endpoint 转成异步等待 IMX415 的条件；匹配成功后框架回调 .bound()，Rockchip 代码调用 media_create_pad_link() 建立 Sensor Source→D-PHY Sink。最后我按 DTS、probe、match、Media Graph、实际帧五层证据定位问题。
