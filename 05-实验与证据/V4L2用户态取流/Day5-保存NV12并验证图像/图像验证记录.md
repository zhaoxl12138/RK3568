## 一、保存一帧时的对象关系

```text
VIDIOC_DQBUF 返回
├─ buf.index = 0
│    └─ 本帧位于 buffers[0]
├─ buf.length = 1
│    └─ 当前 Buffer 有一个独立内存 Plane
└─ planes[0]
     ├─ bytesused = 12441600
     └─ data_offset = 0

应用登记表
└─ buffers[0]
     ├─ start[0]  → mmap 用户虚拟地址
     └─ length[0] = 12441600

真正写文件
└─ 从 start[0] + data_offset 开始
   写入 bytesused - data_offset 字节
```

`DQBUF` 没有复制一张新图。它只是把完成 Buffer 的描述和所有权交还应用；应用随后读取 Day3 已建立的 mmap 地址。

## 二、三个长度不要混淆

| 字段                      |      当前值 | 含义                         |
| ----------------------- | -------: | -------------------------- |
| `sizeimage`             | 12441600 | S_FMT 后驱动给出的该 Plane 最低容量要求 |
| `planes[0].length`      | 12441600 | QUERYBUF 返回的实际映射容量         |
| `planes[0].bytesused`   | 12441600 | DQBUF 后当前帧真正有效的数据长度        |
| `planes[0].data_offset` |        0 | 有效数据相对 mmap 首地址的起点         |

本次它们恰好相等，不代表所有格式和驱动都永远相等。尤其是 JPEG、H.264 等压缩数据，Buffer 容量通常固定，而每帧 `bytesused` 会变化。

保存代码因此按下面关系计算：

```c
data = buffers[buf.index].start[plane] + planes[plane].data_offset;
valid_bytes = planes[plane].bytesused - planes[plane].data_offset;
fwrite(data, 1, valid_bytes, output);
```

## 三、为什么当前 NV12 只有一个 Plane

当前节点使用的是 Multiplanar API，所以必须通过：

```c
struct v4l2_plane planes[VIDEO_MAX_PLANES];
buf.m.planes = planes;
```

但驱动返回：

```text
num_planes = 1
```

这表示 Y 区域和 UV 区域连续存放在同一个内存 Plane 中：

```text
一块 12441600 字节内存
├─ 前 3840×2160 字节：Y
└─ 后 3840×1080 字节：交错 UV
```

因此直接按 `bytesused` 保存 `plane[0]`，就得到完整 NV12 文件。

## 六、能证明什么，不能证明什么

当前证据能够证明：

- Sensor → D-PHY → CSI → RKISP → mainpath → `/dev/video0` 的数据链路能够输出真实图像。
- 应用正确使用 `buf.index`、mmap 地址和 `bytesused` 保存了一帧。

## 七、你的 Day5 验收题

### 1. 保存图像时，为什么应该使用 `bytesused`，而不是直接把整个 `length` 都写入文件？

我的回答：

只写当前帧的有效数据，避免把无效区域也保存进去。

> [!success]- 正确答案（回答后再展开）
> `length` 是 Buffer Plane 的总容量，`bytesused` 是当前完成帧真正有效的数据范围。二者当前相等只是本次 NV12 的结果；对齐、压缩格式或其他驱动中可能不同，直接写整个 length 可能把无效尾部数据也保存进去。

### 2. `DQBUF` 返回 `buf.index=2` 时，应用应该从哪里读取图像？

我的回答：

从第三个 Buffer，也就是 `buffers[2]` 对应的 mmap 地址开始读，有效长度看 `bytesused`。

> [!success]- 正确答案（回答后再展开）
> 应用应读取 `buffers[2].start[plane] + planes[plane].data_offset`，有效长度为 `bytesused - data_offset`。`buf.index` 把 DQBUF 的完成描述与 Day3 保存的 mmap 地址对应起来。

### 3. NV12 有 Y 和 UV 两部分，为什么当前只保存 `plane[0]` 也能得到完整图像？

我的回答：

Y 和 UV 连续放在同一个内存 Plane 中。Plane 可以理解为一块独立描述和映射的图像内存区域，但它不一定只保存一个颜色分量。

> [!success]- 正确答案（回答后再展开）
> 因为当前驱动返回 `num_planes=1`，Y 与交错 UV 连续存放在同一个内存 Plane 中。Multiplanar API 只是接口形式，不代表当前格式一定有两个独立内存 Plane。

### 4. 文件大小正确并且能转换成 PNG，能否单独证明画面完全正确？

我的回答：

能吧。

> [!success]- 正确答案（回答后再展开）
> 不能。它能证明长度和基本格式解释成立，但仍需实际查看颜色、亮度、画面方向、stride 错位、撕裂和内容；还不能证明长时间稳定性和 ISP 画质已经调好。

### 5. 如果转换后出现绿屏、图像横向错位或文件截断，分别优先检查什么？

我的回答：

绿屏应该是 UV 数据读写或顺序的问题；横向错位和文件截断可能与读取偏移有关。补充修正：横向错位优先检查 stride/`bytesperline`，文件截断优先检查 Plane 数、`bytesused` 和文件总长度。

> [!success]- 正确答案（回答后再展开）
> 绿屏或明显偏色优先检查 NV12/NV21 与 UV 顺序；横向错位优先检查 `bytesperline`、stride 和每行对齐；截断或撕裂优先检查宽高、Plane 数、`bytesused`、`data_offset` 和实际文件长度。
