# RK3568 + IMX415 Camera Bring-up｜三分钟讲解

## 0:00–0:30 项目目标

我基于 RK3568 开发板和 IMX415，重新梳理并验证了从硬件连接、DTS、I2C 驱动匹配，到 V4L2 Subdev 和 Media Graph 建链的 Camera Bring-up 主线。当前重点不是应用层展示，而是能够从代码和板端证据解释每个节点为什么出现、失败时该从哪一层检查。

## 0:30–1:20 Sensor 控制链

IMX415 挂在 I2C4 下。设备树节点提供 `compatible = "sony,imx415"`、地址 `0x1a`、时钟、RESET、POWER GPIO 和 endpoint。启用的 IMX415 I2C Driver 注册后，由 Linux 驱动模型完成匹配并进入 `imx415_probe()`；probe 获取 DTS 资源、执行上电、通过 I2C 读取 Sensor ID，再注册 V4L2 Sensor Subdev。源码入口是 `kernel/drivers/media/i2c/imx415.c`。

实板证据 `EVID-20260728-IMX415-RUNTIME` 显示运行时节点 `/i2c@fe5d0000/imx415@1a` 存在，client `4-001a-1` 已绑定 `imx415` 驱动，并读到 `0000e0`。这能证明控制链、基本供电和 I2C 通信可用，但不能单独证明 MIPI 图像稳定输出。

## 1:20–2:10 图像数据链

图像像素不经过 I2C，而是从 IMX415 的 Source Pad 通过四条 MIPI CSI-2 Data Lane 进入 RK3568 D-PHY。DTS 的双向 endpoint 描述静态拓扑；D-PHY Platform Driver 在 probe 中建立 V4L2 Subdev、pads 和 async notifier，Sensor subdev 到达后由 `.bound()` 创建 Media link。对应源码入口是 `kernel/drivers/phy/rockchip/phy-rockchip-csi2-dphy.c`。

实板证据 `EVID-20260728-CAMERA-DAY1` 中，`media-ctl -p` 显示 IMX415 `pad0 Source` 到 `rockchip-csi2-dphy0:0` 的链路为 `[ENABLED]`，并继续连接 CSI 和 RKISP。它能证明对象已注册、格式已传播、拓扑已建链；仍不能替代带校验值的连续抓帧和画面质量验证。

## 2:10–2:40 我的排障方法

我按层排查：先看电源、时钟和 RESET，再看 I2C client、驱动绑定和 Sensor ID，然后看 endpoint、D-PHY/CSI 错误与 Media Graph，最后才检查 RKISP、`/dev/videoX`、格式协商和 STREAMON。这样能避免看到 `/dev/video0` 就误判 Sensor 已经正常出流。

## 2:40–3:00 当前边界与下一步

目前阶段 00–03 已完成，阶段 04 D-PHY 源码学习中。下一步会补齐 Media Controller、RKISP 和 V4L2 用户态取流，并形成带命令、原始输出和文件哈希的抓帧证据。所有“我做过”的陈述都回链到源码位置或 `EVID-...` 证据，而不是只凭流程图复述。
