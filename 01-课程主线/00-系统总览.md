# RK3568 Camera 系统总览

## 为什么学习

先建立 Sensor、D-PHY、CSI-2、RKISP、Media Controller 与 `/dev/videoX` 的统一地图，后续追 DTS、源码和板端证据时才不会混淆硬件、驱动与框架对象。

## 在整条链路中的位置

本章是课程入口：控制流从 DTS 和驱动模型进入各模块，图像数据流从 IMX415 经 MIPI CSI-2 / D-PHY 进入 RKISP，最终到达视频节点。

## 输入 / 输出 / 软件身份 / 硬件身份

| 对象 | 输入 | 输出 | 软件身份 | 硬件身份 |
|---|---|---|---|---|
| IMX415 | I2C 配置、时钟、供电与复位 | RAW10 | I2C client、V4L2 subdev | 图像传感器 |
| D-PHY / CSI-2 | MIPI 差分信号 | RAW 数据流 | Platform device/driver、V4L2 subdev | SoC 接收物理层与协议接收器 |
| RKISP | RAW Bayer | 可供视频节点输出的图像 | V4L2/Media entity | ISP 硬件 |
| Video node | buffer 与开流请求 | 用户态帧 | V4L2 video device | 无独立硬件身份 |

## RK3568 当前对应

> 今天的核心成果：把 Camera 中容易混淆的“硬件、总线驱动、V4L2、Media Controller”分开，并能把它们重新串成一条可追代码的主线。
>
> 配套阅读：[[02-源码陪读/04-DPHY/00-源码陪读索引|D-PHY 从 DTS 到 Media Graph 源码陪读]]、[[04-MIPI-CSI2-DPHY|MIPI CSI-2 / D-PHY]]

#### 1. 先记住完整主线

##### 硬件数据流

```text
IMX415 Sensor
    ↓ RAW10 图像数据
MIPI CSI-2 D-PHY
    ↓
CSI-2 Receiver
    ↓
RKISP
    ↓
rkisp_mainpath
    ↓
/dev/video0
    ↓
OpenCV / GStreamer / YOLO
```

##### Linux 软件主线

```text
DTS 描述设备和连接
        ↓
Linux 创建设备对象
        ↓
I2C / Platform Driver 匹配
        ↓
probe() 初始化硬件
        ↓
驱动注册 V4L2 Subdev
        ↓
Media Controller 创建 Entity / Pad
        ↓
Async Framework 匹配上下游
        ↓
media_create_pad_link()
        ↓
形成 Camera Pipeline
        ↓
/dev/video0 给用户态取帧
```

这两条线要同时看：

- **硬件数据流**回答“图像从哪里流到哪里”。
- **Linux 软件主线**回答“内核如何发现、初始化并组织这些硬件”。

#### 2. 四类概念不要混在一起

| 层次 | 代表概念 | 解决的问题 | RK3568 当前实例 |
|---|---|---|---|
| 真实硬件 / 协议 | Sensor、D-PHY、CSI-2、ISP | 电气信号和图像数据怎样传输、处理 | IMX415、CSI2 D-PHY、RKISP |
| Linux 设备模型 | I2C、Platform、SPI、USB | Linux 通过什么总线找到并管理设备 | IMX415 是 I2C，D-PHY 是 Platform |
| Camera 功能框架 | V4L2、V4L2 Subdev | Camera 模块怎样被统一表示和控制 | Sensor、D-PHY、CSI、ISP Subdev |
| 拓扑管理框架 | Media Controller | 各个 Camera 模块怎样连接 | Entity、Pad、Link、Media Graph |

最容易错的地方是：

```text
I2C / Platform 不是 Camera 功能
V4L2 / Media Controller 也不是物理传输协议
CSI-2 / D-PHY 不是驱动类型
```

#### 3. Linux 驱动模型：谁负责找到设备

Linux 不会根据驱动文件名猜它是什么类型，而是看驱动注册到哪一种总线框架：

```c
struct platform_driver   // SoC 内部固定控制器
struct i2c_driver        // I2C 外设
struct spi_driver        // SPI 外设
struct usb_driver        // USB 外设
```

##### 当前 Camera 中的对应关系

```text
RK3568 D-PHY 控制器
    → platform_device
    → platform_driver

IMX415 Sensor
    → i2c_client
    → i2c_driver
```

所以：

> Platform Driver 通常负责 SoC 内部固定硬件控制器；挂在控制器总线上的具体外设，再使用 I2C、SPI、USB 等对应的驱动模型。

#### 4. DTS 是设备档案，不是驱动实现

DTS 主要描述：

```text
板子上有什么设备
设备地址在哪里
需要什么寄存器、时钟、GPIO、电源域
设备之间如何连接
```

例如 D-PHY：

```dts
csi2_dphy0: csi2-dphy0 {
    compatible = "rockchip,rk3568-csi2-dphy";
    rockchip,hw = <&csi2_dphy_hw>;
};
```

这里的 `compatible` 负责提供匹配标识：

```text
DTS 节点
    ↓
Platform Device
    ↓
compatible 与驱动 match 表比较
    ↓
匹配成功
    ↓
probe()
```

DTS 不会直接把节点标成“V4L2 设备”或“Camera Sensor”。这些身份由驱动代码决定：驱动在 `probe()` 中调用 V4L2 和 Media Controller 接口，才把硬件接入 Camera 框架。

#### 5. Linux 框架与厂商驱动的关系

Linux 提供规则和通用接口：

```text
Device Model
Platform Driver Framework
I2C Driver Framework
V4L2
Media Controller
Async Framework
```

厂商或社区驱动负责真正理解硬件：

```text
IMX415 Driver       → 读取 Sensor ID、写寄存器、设置曝光和开流
RK3568 D-PHY Driver → 配置 D-PHY 寄存器、管理 Lane 和数据接收
RK3568 ISP Driver   → 处理 RAW 图像并输出视频节点
```

驱动通过 Linux 提供的接口接入框架，例如：

```c
v4l2_subdev_init()
media_entity_pads_init()
v4l2_async_register_subdev()
media_create_pad_link()
```

一句话：

> Linux 定义统一规则，厂商驱动填写具体硬件行为。

#### 6. 一个模块有两个身份

##### IMX415

从 Linux 设备模型看：

```text
IMX415
    → I2C Device
    → I2C Driver
```

从 Camera 框架看：

```text
IMX415
    → V4L2 Sensor Subdev
    → /dev/v4l-subdev3
```

##### D-PHY

从 Linux 设备模型看：

```text
D-PHY
    → Platform Device
    → Platform Driver
```

从 Camera 框架看：

```text
D-PHY
    → V4L2 Subdev
    → Media Entity
    → Sink / Source Pad
```

因此：

```text
I2C / Platform
    解决“Linux 怎么找到和管理设备”

V4L2 / Media Controller
    解决“Camera 模块怎样统一表示和连接”
```

#### 7. V4L2 与 V4L2 Subdev

V4L2 是 `Video4Linux2`，属于 Linux 内核中的 Video / Camera 功能框架，不是 Rockchip 私有库，也不是用户态第三方库。

```text
Linux Kernel
    ↓
V4L2 Framework
    ↓
统一管理 Camera 和 Video 设备
```

Camera 流水线不是单一设备：

```text
Sensor → D-PHY → CSI → ISP
```

因此这些内部模块通常表示为 V4L2 Subdev：

```text
IMX415                  → /dev/v4l-subdev3
rockchip-csi2-dphy0     → /dev/v4l-subdev2
rkisp-csi-subdev        → /dev/v4l-subdev1
rkisp-isp-subdev        → /dev/v4l-subdev0
```

Subdev 主要负责：

```text
支持哪些格式和分辨率
有什么输入 / 输出端口
怎样设置曝光、增益和时序
怎样设置格式
怎样开流和停流
```

它不是主要给应用直接取 Frame Buffer 的节点；最终给用户态取图的是 `/dev/video0`。

#### 8. Media Controller：把模块连成图

V4L2 Subdev 能描述一个个模块，但还需要描述模块之间的连接，这由 Media Controller 完成。

核心对象只有三个：

```text
Entity = 一个 Camera 模块
Pad    = 模块的输入 / 输出端口
Link   = 两个 Pad 之间的连接
```

当前链路可以理解为：

```text
IMX415
  pad0: Source
       ↓
rockchip-csi2-dphy0
  pad0: Sink
  pad1: Source
       ↓
rkisp-csi-subdev
       ↓
rkisp-isp-subdev
       ↓
rkisp_mainpath
       ↓
/dev/video0
```

```bash
media-ctl -p
```

看到的就是 Media Controller 在运行时维护的 Entity / Pad / Link 拓扑。

#### 9. DTS endpoint 与 Media Graph 的区别

DTS 中的：

```dts
remote-endpoint = <&imx415_out>;
```

只是静态连接描述，表达：

> 这两个硬件端点应该连接。

运行时还要经过驱动和异步框架：

```text
DTS endpoint
    ↓
Driver probe()
    ↓
V4L2 Subdev 注册
    ↓
Media Entity / Pad 初始化
    ↓
Async match
    ↓
.bound()
    ↓
media_create_pad_link()
    ↓
运行时 Media Graph
```

所以不能把 `remote-endpoint` 理解成“DTS 编译时已经创建了 Media Link”。

#### 10. D-PHY 的两个对象：HW 与逻辑 D-PHY

RK3568 D-PHY 驱动拆成两个容易混淆的对象：

##### `csi2_dphy_hw`

表示底层真实硬件资源：

```text
寄存器
Clock
GRF
stream_on / stream_off
```

##### `csi2_dphy0`

表示 Camera 链路中的逻辑 D-PHY：

```text
Platform Device
V4L2 Subdev
Media Entity
Sink / Source Pad
Sensor 异步绑定关系
```

两者通过 DTS 关联：

```dts
rockchip,hw = <&csi2_dphy_hw>;
```

驱动中的关系大致是：

```text
of_parse_phandle()
    ↓
of_find_device_by_node()
    ↓
platform_get_drvdata()
    ↓
dphy->dphy_hw
```

也就是：DTS 中的静态 phandle，最终变成 C 结构体之间的指针关系。

#### 11. IMX415 与 D-PHY 的共同驱动模板

虽然两者的底层总线不同：

```text
IMX415 → I2C Driver
D-PHY  → Platform Driver
```

但进入 Camera 框架后的套路相近：

```text
Driver Match
    ↓
probe()
    ↓
初始化时钟、GPIO、寄存器等硬件资源
    ↓
初始化 V4L2 Subdev
    ↓
初始化 Media Entity / Pad
    ↓
注册 Async
    ↓
匹配上下游
    ↓
创建 Media Link
```

真正的差别在于：

```text
各自初始化什么硬件
各自提供几个 Pad
各自有哪些 ops
如何与上下游绑定
```

#### 12. 当前最值得记住的面试表达

> RK3568 Camera 需要分三层理解。第一层是 Linux 设备模型：IMX415 挂在 I2C 总线上，D-PHY、CSI 和 ISP 这类 SoC 内部控制器通常由 Platform Driver 管理。第二层是 Camera 功能框架：Sensor、D-PHY、CSI、ISP 都可以表示为 V4L2 Subdev。第三层是 Media Controller：通过 Entity、Pad 和 Link 把这些 Subdev 组织成完整的 Camera Pipeline。DTS 只描述设备资源和静态连接，驱动在 probe 中初始化硬件、注册 Subdev，异步框架匹配上下游后，再由 `.bound()` 调用 `media_create_pad_link()` 建立运行时链路，最后通过 `/dev/video0` 给用户态取帧。

#### 14. 最后只记这几句话

```text
DTS
= 描述硬件和连接关系

I2C / Platform
= Linux 找到并管理设备的方式

Driver
= 真正懂具体硬件如何操作

probe()
= 驱动初始化设备的入口

V4L2
= Linux 对 Camera / Video 设备的统一功能框架

V4L2 Subdev
= Sensor、D-PHY、CSI、ISP 等内部模块的软件表示

Media Controller
= 管理 Entity / Pad / Link，组成 Camera 拓扑

/dev/video0
= 用户态获取图像 Buffer 的 V4L2 Video Node
```

## 实板验证

当前证据包括运行时 I2C client、IMX415 Sensor ID、Media Graph 和抓帧结果。它们分别证明链路的不同层次，任何单项都不能替代完整开流验证。

## 常见故障

先按供电/时钟/复位、I2C 匹配与 ID、endpoint 与异步绑定、D-PHY/CSI、RKISP、video node 分层定位，不从 `/dev/video0` 缺失直接跳到某个驱动函数。

## 面试表达

RK3568 Camera 不是单个驱动，而是由 Sensor、MIPI 接收、ISP 和 V4L2/Media 框架组成的 pipeline；DTS 描述设备和连接，驱动模型完成匹配与 probe，运行时 Media Graph 表达数据链。
