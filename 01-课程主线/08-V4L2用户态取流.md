# V4L2 用户态取流

> 学习状态：未开始。已有实板输出作为证据，本阶段将把命令与内核调用链对齐。

## 为什么学习

`/dev/video0` 只是入口。真正取到一帧，需要格式协商、申请 buffer、入队、开流、等待硬件填充、出队和重新入队。

## 本阶段只解决三个问题

1. `open / ioctl / video_ioctl2` 如何把用户请求分发给 RKISP capture 驱动。
2. `REQBUFS / QUERYBUF / QBUF / STREAMON / DQBUF` 分别改变了什么队列状态。
3. `Video Capture Multiplanar` 与 NV12 多平面 buffer 对应用程序意味着什么。

## 用户态到内核的主线

```text
open(/dev/video0)
  -> VIDIOC_S_FMT
  -> VIDIOC_REQBUFS
  -> VIDIOC_QBUF
  -> VIDIOC_STREAMON
  -> poll / VIDIOC_DQBUF
  -> 处理帧
  -> VIDIOC_QBUF
```

## 验收边界

格式查询成功不能证明 buffer 能流动；`STREAMON` 返回成功也不能保证每帧内容有效。必须结合 `DQBUF`、序号/时间戳、文件大小和图像内容判断。

## 面试表达

V4L2 ioctl 负责命令分发，VB2 管理 buffer 生命周期；应用先协商格式并申请、入队 buffer，`STREAMON` 后由驱动和硬件填充，`DQBUF` 取回完成帧，再循环入队。
